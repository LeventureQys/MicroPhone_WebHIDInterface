# DFU 协议符合性评审 — 《DFU固件升级通讯协议说明_20261026》

> 评审日期：2026-10-26
> 评审对象：`Document/Protocol/DFU固件升级通讯协议说明_20261026.md`（下称「DFU 协议 1026」）
> 对照实现：`src/renderer/src/device/dfu/**`（`frame` / `image` / `session` / `controller`）、`device/link.ts`、`device/webhid-transport.ts`
> 对照材料：`Document/Protocol/Bootloader/source/user/FirmwareUpgrade/Dfu.Program.c`、`Com.DataProcess.c`、`Tools/Py/Firmware_4_BootUpdater_Build.py`、出厂包 `INNO SoftEmbe_Bootloader(PD100UGen2) MCU [内部使用].bin`
> 方法：协议逐条对照代码；用固件源码核对信息帧布局；对出厂包逐帧解析并与本仓编码器逐字节对拍；`vitest run tests/unit/dfu` 95 例
> 取证：`artifacts/real2/dfu-*.log`

## 0. 结论

**帧层、镜像层、状态语义都对得上；主机侧的「进入 DFU 之后」这一段没跟上新协议。**

| 部分 | 结论 | 依据 |
|---|---|---|
| 触发进 DFU 的帧（`0x10` 写 `0x1008=1`） | ✅ 逐字节一致 | 本仓编码 = `00 10 00 0A 10 08 00 01 8D 09`，与协议 §3.1 完全相同 |
| SigmaBus 帧格式 / Len / 地址 / Cmd / SigmaCRC | ✅ | `dfu/frame.ts` 与协议 §5.1 同构；出厂包 84 帧复算全对 |
| 信息帧字段布局 / 大端败（ModelCode 可读串） | ✅ | 固件 `DfuProgramInfoCheck()` 从 `data+70/73/77` 取 Ver/Len/Checksum，与本仓一致 |
| Gamma（密钥 / 仅前 8 KB）与 32 位小端字累加和 | ✅ | 出厂包解密后向量表与校验和逐字节对拍通过 |
| 块大小 256 B、整帧 265 B、5 个 HID 报文 | ✅ | 出厂包块长 `256×81 + 248` |
| 状态帧 `[0x01][CHIP_ID][status]` 与 0x01–0x05 语义 | ✅ | `decodeDfuStatus` + `session` 分支逐一对应 |
| 收到 `0x05` 后停止发帧、等设备复位 | ✅ | `enterSettling()` 禁止后续发帧 |
| **进 DFU 后设备复位重新枚举** | ❌ **主机没等、也没重开设备** | `DfuSession.run()` 在 ACK 后立刻发信息帧；`DeviceLink` 全程用同一个 HID 句柄 |
| **收尾重连** | ❌ 设计与实现不一致 | 设计 §5.8 第 6 条要求"重新打开设备"，`WebHidTransport.resume()` 只是恢复喂字节 + `sync()` |
| **设备停在 Bootloader 时再升级（重试/救砖）** | ❌ 走不通 | `DeviceLink.attach()` 必须先完成参数协议同步，Bootloader 不说 Modbus |
| 型号预检 | ⚠ 依赖设备信息区 | 真机 V0.0.2 的信息区全 0 → `JYM001` 包会被预检拒绝（对应第二轮 F8'） |
| 块大小 512 / 1024 | ⚠ 未支持 | `parseImage` 只接受 256，协议 §5.3 说打包工具可选 |
| 块间超时 | ⚠ 1500 ms > 设备的 ~1000 ms | 设备会先主动发 `status=0x02`，主机按"代码错误"整轮重来 |
| 信息帧长度 | ⚠ 文档 85/94，实际 81/90 | 固件只读 81 B；出厂包 = 81 B。**文档数字有误**（见 §2） |
| 包首触发帧形态 | ✅ 已兼容两种 | 旧 SigmaBus 帧与新的 Modbus 帧都收（本轮改动，见 §4） |

## 1. 协议三段与实现的对应

| 协议阶段 | 协议规定的动作 | 本仓实现 | 结论 |
|---|---|---|---|
| ① 进 DFU | `0x10` 写 `0x1008=1`，等 `ACK 0x0000` | `main.ts`→`FirmwareController.start()`→`DfuSession.enterDfu()`，帧字节一致，ACK 最多 2 次 | ✅ |
| ② 设备复位 | 约 200 ms 后复位，1–3 s 重新枚举 | **没有等待，也没有重开设备**，直接发信息帧到旧句柄 | ❌ P0 |
| ③ 信息帧 | `DFU_CMD=0x02`，等 `status=0x03` | `probe()`：`encodeDfuInfoFrame` + 3 次重试、每次 1.5 s | ✅（帧）；⚠（发送时机） |
| ④ 代码块 | `DFU_CMD=0x03`，≤256 B，逐块等应答 | `writeBlocks()`：每块一发一等，末块收 `0x05` | ✅ |
| ⑤ 收尾 | 设备 1 s 后写状态字并复位，主机不再发帧 | `enterSettling()` 停发帧；等 `resumeAfterDfu()` 回读 | ⚠ 回读用的是旧句柄 |
| ⑥ 升级后 | 设备进新固件，重新枚举 | `resumeAfterDfu()` → `transport.resume()` → `session.sync()`（旧句柄） | ❌ P0 |

## 2. 文档自身需要修的三处

### 2.1 信息帧长度：文档 85 B / 94 B，实际 81 B / 90 B

- 文档 §5.2 写「Payload 固定 85 字节」「信息帧总长 = 9 + 85 = 94 B」，§6 示例给的是 `C4 5E 00 00 0B 02 00 …`（`0x5E = 94`）。
- 但字段表自己是 6+64+3+4+4 = **81 B**（偏移 0–80），固件 `DfuProgramInfoCheck()` 只读到 `data + 81` 为止，`len` 参数**根本没用到**；出厂包实测信息帧 `C4 5A 00 00 0B 02 00 …`，`Len = 0x5A = 90`。
- 打包脚本 `Firmware_4_BootUpdater_Build.py` 里 `head` 拼的也是 6+64+3+8 = 81 B。
- 建议：文档改回 81 / 90；若要保留 4 B 尾巴（例如给头部 CRC），需在字段表里写明偏移 81–84 的含义。

### 2.2 §3.1 说打包脚本已换新触发帧，但仓内脚本副本还是旧帧

`Document/Protocol/Bootloader/Tools/Py/Firmware_4_BootUpdater_Build.py` 的 `EnterDfu[11]` 仍是 `C4 0B 00 00 03 08 10 01 00 15 FF`。文档说"两个脚本已于 2026-10-26 同步更新"，本仓只有 Bootloader 侧副本，且是旧的。**需要厂商确认新脚本的实际产物**，最好直接给一个用新脚本打出来的 `.bin`，否则"新格式包"只能纸上验证。

### 2.3 §5.1 的帧图与 §7 常量自洽，但没写"包首触发帧有两种形态"

建议在 §5 开头补一句：包首可能是 `C4…03` 或 `00 10 00 0A…`，解析时按首字节判别，其余两段不变。

## 3. 实现侧对不上的地方（按严重度）

### P0-1 进 DFU 后没有"等设备重新枚举再说话"

- 现状：`DfuSession.run()` 拿到 EnterDfu 的 ACK 后，立刻进入 `probing` 并发信息帧；`controller` 的 `send` 走 `link.transport()` 里的**同一个** `HIDDevice` 句柄。
- 协议事实：ACK 之后约 200 ms 设备复位，USB 重新枚举（1–3 s，协议 §1 步骤 ③、§6 步骤 3）。复位后旧 `HIDDevice` 已断开，`sendReport` 会 reject；即使抢在 200 ms 窗口内发出去，新 MainApp 也不再解析 SigmaBus 帧（§3.1）——这一帧无论如何都到不了 Bootloader。
- 后果：`probe()` 3 次 × 1.5 s 全超时 → `probeFailed`/`enterTimeout`，**真机 DFU 第一步就失败**。
- 修法（建议）：`enterDfu` 之后插入 `waitForReenumeration()`：先 `WebHidSession.refresh()`（`getDevices()` 重新枚举，VID/PID 与 Report ID 都不变），拿到同一 `deviceId` 的新句柄 → `openDevice` → 重建/替换 `WebHidTransport` 句柄 → 重新挂 `onInputBytes` → 再进 `probing`。窗口 5 s、轮询 200 ms，超时报 `enterTimeout`。

### P0-2 收尾 `resumeAfterDfu` 没重开设备（与自己设计文档不一致）

- 设计 §5.8 第 6 条写的是「`resumeAfterDfu`：重新打开设备（DFU 后设备 `deviceId` 不变，但需要 `device.open()` 复位）→ 全量回读」。
- 实现 `WebHidTransport.resume()` 只做了 `_suspended = false` + `session.sync()`，没有重新 `open`，句柄还是复位前那个。
- 后果：即使升级成功，收尾回读会失败 → `_fail('device')` → 界面报错、版本校验拿不到设备，用户看到"升级失败"但设备其实已经是新固件。
- 修法：与 P0-1 共用 `waitForReenumeration()`，在 `resume()` 前重开；`DeviceLink.resumeAfterDfu()` 负责替换 transport 句柄。

### P1-1 设备停在 Bootloader 时无法再升级（救砖路径缺失）

- 现状：`FirmwareController.replugAndRetry()` → `link.attach(deviceId)` → `transport.open()` → `readAll()` 必须走参数协议全量回读。Bootloader 只说 SigmaBus（§5.1、§8.2），回读必然失败 → `_fail('device')` → `transport === null` → `start()` 直接返回 `noDevice`。
- 协议事实：升级失败时设备已预置 `EndFlag=FAIL`，**每次复位都留在 Bootloader**（§2.2），只有再刷一次才能出来——正是最需要上位机的时刻。
- 修法：给 `DeviceLink` 加一个"只开设备、不同步参数"的通道（或让 `attach` 支持 `skipSync`），DFU 入口在 `link.transport() === null` 时也能用该通道发 SigmaBus 帧；预检的型号比对在没有 `DeviceSnapshot` 时放行到设备侧（Bootloader 自己会回 `0x01`）。

### P1-2 型号预检依赖设备信息区，当前固件全 0 → 直接拒绝

- `preflight()` 用 `device.modelCode` 与包内 ModelCode 比对；真机 V0.0.2 的信息区 `0x0000–0x0002` 全 0（第二轮 F8'），于是 `JYM001` 包一律被判 `mismatch`。
- 协议 §5.2：Bootloader 用 Flash 信息区（`0x39000`）的 ModelCode 校验，同样是"空值则只认 `000000` / `Bootld`"。
- 结论：**固件不填型号区，DFU 就无法用正常包**。这条与第二轮 F8' 是同一件事，优先级要提到 DFU 之前。

### P1-3 块大小只支持 256 B

- 协议 §5.3：打包工具默认 256 B，可选 256/512/1024（接收缓冲 1024，单帧上限约 1017 B）。
- 本仓 `parseImage` 要求"非末块必须是 256 B、末块 ≤256 B"，`encodeDfuBlockFrame` 也硬限 256。
- 影响：厂商若用 512/1024 打包会被预检拒绝（`reject.blockSize`）。出厂包是 256，短期无碍；建议在协议里把"本机型固定 256"写死，或者实现 512/1024（还要评估设备 OUT 缓冲只有 4×64 B 槽的风险）。

### P2-1 块间超时比设备长

- 协议 §5.3 第 5 步：块间超时约 1 s，超时**设备主动**发 `status=0x02`。
- 本仓 `TIMING.dfuBlockTimeoutMs = 1500`：设备会在 1 s 先发 `0x02`，主机把它当"代码错误"整轮重来——结论相同，但日志会写成"设备报错"而不是"超时"。
- 建议：降到 1200 ms 并保留"收到 0x02 = 整轮重来"的分支，或明确记为"设备 0x02 即超时信号"。

### P2-2 进入 DFU 的帧已按新协议，但包首旧帧仍被当成"必须"

- 本轮已放宽（§4），旧包与新包都能解析；但如果将来厂商把包首彻底去掉，`parseImage` 仍会拒绝。建议在协议里把"包首触发帧"定为可选字段。

## 5. 建议的修复顺序（真机前必须做）

| # | 事项 | 判据 |
|---|---|---|
| 1 | 固件填设备信息区（型号/固件版本/VID/PID） | 连接后 `modelCode = JYM001`；`preflight` 不再报 `mismatch` |
| 2 | 主机加"等重新枚举 + 重开设备"（P0-1/P0-2） | 虚拟设备需同步扩展：进 DFU 后关闭旧句柄、延迟后以同 VID/PID 重新出现；单测断言"信息帧只在重新打开后才发" |
| 3 | 主机加"Bootloader 直连"通道（P1-1） | 设备停在 Bootloader 时，断开重连后仍能选包并升级 |
| 4 | 块间超时改 1200 ms（P2-1） | 拔线 1 s 场景：日志出现"设备 status=0x02"，整轮重来 1 次 |
| 5 | 真机首刷（**风险最高**） | 先用 `000000` 通配包（跳过型号校验）试一次；失败则设备停在 Bootloader，用 J-Link（`third_party/设备相关/Release/`）救回 |

> 真机首刷前建议先确认：J-Link + `JLink_Windows_V696.exe` 与 `A0_Save_Final.JLinkScript` 可用；否则失败即成砖，只能返厂。

## 6. 已核对正确的细节（备查）

- 触发帧：`00 10 00 0A 10 08 00 01 8D 09` = `UnitID 00 / Func 10 / Len 000A / Addr 1008 / Val 0001 / CRC 8D 09`，本仓 `encodeFrame(0x10, encodeRandWrite([{addr:0x1008,raw:1}]))` 逐字节相同。
- SigmaBus：`C4 | LenL LenH | Addr | Cmd | DFU_CMD | CHIP_ID | Payload | CRCL CRCH`，`Len = Payload + 9`；本仓 `length = 7 + data.length`（`data` 含 DFU_CMD+CHIP_ID）等价。
- 信息帧偏移（相对"不含 DFU_CMD/CHIP_ID 的 81 B 头"）：ModelCode 0..5、ModelName 6..69、Ver 70..72、FwLength 73..76（小端）、FwChecksum 77..80（小端）——与固件 `pt = data + 6 + 64` 完全一致。
- 块帧：`7 + 2 + n`，256 B → 265 B → 5 个 HID 报文；末块可短（出厂包 248）。
- 状态帧：`C4 0A 00 00 0B 01 00 <status> <CRC>`，`status` 在载荷第 3 字节。
- Gamma：密钥 `0x63 0xBB 0x9C 0x1C` 按字节序、偏置 `0xA3`、半字节交换、只前 8 KB；出厂包解密后 `SP=0x200041B8 / Reset=0x00004265`。
- 校验和：4 字节小端字累加 mod 2³²，作用在**解密后**明文；出厂包 `0x4E0621AF` 复算一致。
- 出厂包逐帧：`84` 帧（首帧 11 B、信息帧 90 B、81×265 B、末块 257 B），本仓 `encodeInfoFrame`/`encodeBlockFrame` 重编码逐字节相同（`tests/unit/dfu/golden.test.ts`）。
