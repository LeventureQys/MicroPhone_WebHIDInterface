# DFU 固件升级通讯协议说明

> 本文档依据现有固件代码（MainApp / Bootloader 两个工程）梳理，描述 USB-HID 通道下固件升级（DFU）的完整上下位机通讯过程。
>
> 适用工程：JYM001（M001）MainApp 与 Bootloader
> 整理日期：2026-10-26
> 主要代码依据：
> `MainApp/source/user/FirmwareUpgrade/Fw.Upgrade.c`、`MainApp/source/user/Comm/Com.DataProcess.c`、

## 一、总体流程

整个升级分为三个阶段：**MainApp 触发 → 复位跳转 Bootloader → Bootloader 内完成固件传输**。

```
上位机                         MainApp                          Bootloader
  │                              │                                 │
  │ ①写参数0x1008=1 (Func 0x10)  │                                 │
  ├─────────────────────────────>│                                 │
  │ ②ACK(0x02, 无错误)           │ 延时100ms→静音/UI关闭            │
  │<─────────────────────────────┤ 写状态字{A5,00,01,00}→Flash      │
  │                              │ RAM魔数0x20007FFC=0x12345678     │
  │                              │ NVIC_SystemReset ──┐            │
  │                              │                  │ 复位         │
  │                              │                  ↓             │
  │                              │        BootCheck()读状态字Byte1=0x00
  │                              │        → 留在Bootloader，USB重新枚举
  │ ③固件信息帧 (Cmd 0x0B, DFU_CMD=0x02)                          │
  ├──────────────────────────────────────────────────────────────>│
  │ ④应答 status=0x03(继续)                                       │ 校验ModelCode，预写END_FAIL
  │<──────────────────────────────────────────────────────────────┤
  │ ⑤代码块帧×N (Cmd 0x0B, DFU_CMD=0x03, ≤256B/块)                 │
  ├──────────────────────────────────────────────────────────────>│ Gamma解密(前8K)→写Flash→累加校验
  │ ⑥每块应答 0x03(继续)…最后一块应答 0x05(成功)                    │
  │<──────────────────────────────────────────────────────────────┤
  │                              │   ⑦置END_SUCCESS/跳APP标志→复位──┤
  │                              │<── BootCheck=0xFF → 校验APP栈顶 → 跳转0x8000 运行新固件
```

## 二、Flash 分区与 DFU 状态字节

### 2.1 Flash 分区（SctConfig.h，两工程一致）

| 地址 | 分区 | 说明 |
|---|---|---|
| `0x00000000` | Bootloader | 引导程序，`FLASH_BL_ADDR` |
| `0x00008000` | MainApp | 应用程序，`FLASH_APP_ADDR`（向量表起始） |
| `0x00038000` | DFU 状态字节 | `FLASH_DFU_SB_ADDR`，4 字节 |
| `0x00039000` | 固件信息区 | `FLASH_FW_INFO_ADDR`（Model Code / Model Name / SN） |

Flash 页大小 `MCU_FLASH_PAGE_BYTES_SIZE = 4096` 字节。

### 2.2 DFU 状态字节（跨复位握手）

存放于 `0x00038000`，共 **4 字节**，MainApp 与 Bootloader 通过它协商复位后的跳转目标：

| Byte | 名称 | 取值 | 说明 |
|:-:|---|---|---|
| 0 | Init1stFlag | `0xFF`=首次初始化（空白）/ `0xA5`=已初始化 | 出厂空白(0xFF)时 Bootloader 初始化后强制进 DFU |
| 1 | **BlJumpTo** | **`0x00`=跳 DFU / `0xFF`=跳 APP** | `BootCheck()` 只依据这一字节判断 |
| 2 | StartFlag | `0x01`=升级开始 / `0x00`=清除 | MainApp 进 DFU 时置 1，Bootloader 初始化即清零 |
| 3 | EndFlag | `0x02`=成功 / `0x01`=失败 / `0x00`=清除 | **`0x01`(失败)使 Bootloader 每次复位都滞留 DFU**，防变砖 |

宏定义位于 `Bootloader/source/user/FirmwareUpgrade/Dfu.Core.h`：
`DFU_SB_1ST_INIT(0xFF) / DFU_SB_1ST_INIT_CLR(0xA5)`、`BL_JUMP_TO_DFU(0x00) / BL_JUMP_TO_APP(0xFF)`、`DFU_START(0x01) / DFU_START_CLR(0x00)`、`DFU_END_SUCCESS(0x02) / DFU_END_FAIL(0x01) / DFU_END_CLR(0x00)`。

## 三、阶段 1：上位机令 MainApp 进入 DFU（写参数 0x1008）

### 3.1 触发指令（Modbus 帧格式）

上位机通过**随机写参数**（Func `0x10`）把配置参数 `PARAM_DFU`（地址 `0x1008`）写为非零值。按《Modbus通讯协议说明_20261022》帧规则（`UnitID + Func + Len(大端,整帧总长=Data+6) + Data(大端) + CRC-16(低字节在前)`）组帧：

```
00 10 00 0A 10 08 00 01 8D 09
│  │  └─整帧总长10──┘ └0x1008┘ └─值=1─┘ └CRC16┘
│  Func=0x10(随机写参数)          （大端）  （大端）  低字节在前
UnitID=0x00
```

+ 数据段大端：参数地址 `0x1008` → `10 08`，参数值 `0x0001` → `00 01`；
+ `Len = 4(Data) + 6 = 0x000A`（16 位大端，计入 CRC）；
+ CRC-16（多项式 `0xA001`、初值 `0xFFFF`）覆盖 `00 10 00 0A 10 08 00 01` = `0x098D`，低字节先发 → `8D 09`；
+ 承载于 HID OUT 报文（Report ID `0x51`），报文内容：`51 00 10 00 0A 10 08 00 01 8D 09`；
+ 设备应答成功 ACK（`0x02` 功能码，固定帧）：`00 02 00 08 00 00 F8 19`，经 HID IN 报文（Report ID `0x11`）返回：`11 00 02 00 08 00 00 F8 19`。

> ✅ **实施状态（2026-10-26）**：MainApp 通讯层（`Com.HidRx.c`/`Com.DataProcess.c/.h`）已按新 Modbus 帧完成改造并编译通过，本节新帧即为主流程实际生效格式；**MainApp 不再接受旧 `0xC4` SigmaBus 帧**。
> 升级打包脚本 `Firmware_4_Updater_Build.py`（MainApp）与 `Firmware_4_BootUpdater_Build.py`（Bootloader）生成的头部进入帧已同步替换为上述新帧（触发帧发给 MainApp；Bootloader 传输帧不变）。
> **Bootloader 阶段（第五章）仍是旧 SigmaBus 帧，本次未改造、不随 MainApp 协议升级改变**。

### 3.2 MainApp 内部处理链

1. `ComParamRandWrite()` → `Mem.ParamWrite.Rand()` 写入 `Config->DFU` → `ComConfigParamProc()` 发现地址为 0x1008 且值非零 → 调用 `Fwu.Start()`（仅置启动标志并开 100 ms 定时）；
2. 处理完成后**先回 `0x02` ACK（新帧 `00 02 00 08 00 00 F8 19`，数据段 `0x0000` 无错误）**，保证上位机在设备复位前收到成功应答；
3. 主循环 `FwuStartProcess()` 定时到期后依次执行：
   - 关闭 UI 显示、DSP 静音，延时 100 ms；
   - `FwuJumpToDfu()`：状态字节 `{A5, 0x00, 0x01, 0x00}` 写入 Flash `0x38000`；
   - `UserEnterUpdateMode()`：打开全部 RAM 时钟（防掉电丢失）→ 写魔数 `0x12345678` 到 RAM `0x20007FFC`（需与烧写 xml 中信息匹配）→ `NVIC_SystemReset()` 软复位。

### 3.3 备用进入方式

| 方式 | 条件 | 入口 |
|---|---|---|
| 硬件按键 | 开机时 P0.0 拉低 | `BootCheck()` 内 GPIO 检测，与状态字无关 |
| RAM 魔数 | `0x20007FFC == 0x12345678` 后复位 | `UserEnterUpdateMode()` 写入，配合烧写工具使用 |
| 效果器调试通道 | HID 参数通道地址 `0x3FFF` | `UserFunctionHidParaCheck()` → `UserEnterUpdateMode()` |

## 四、阶段 2：复位后跳转判定（BootCheck）

复位后先执行 `startup_a0.s` 的 `Reset_Handler`：调用 `BootCheck()`——

- 返回 `0` → `RUN_DFU_ROM`，继续执行 Bootloader 的 `main()`；
- 返回 `0x00008000` → 先校验 APP 向量表首字（栈顶值 `& 0x1FFE0000 == 0x10000000`，即位于 RAM 范围，栈顶合法才跳转），然后 `LDR SP / BX reset_handler` 跳入 MainApp。

`BootCheck()` 判断优先级：**P0.0 按键（硬件方式）> 状态字 Byte1**。MainApp 请求升级时已写 Byte1=`0x00`，本次复位必然滞留 Bootloader。

Bootloader `main()` 中 `Dfu.Init()` 随后执行：

- 读状态字；若为出厂首次（Byte0=0xFF）→ 写 `{A5, 0x00, 0x00, 0x00}`（首次强制停留 DFU）；
- 否则清 `StartFlag`；若 `EndFlag==DFU_END_FAIL` 则保持 Byte1=`0x00`（后续任何复位都留在 DFU，直到升级成功），否则恢复 Byte1=`0xFF`；
- 之后进入 `Com.Task() / Dfu.Task()` 轮询主循环。

USB 重新枚举为 HID 设备（描述符与 MainApp 相同），Report ID 仍为 **主机→设备 0x51（OUT）/ 设备→主机 0x11（IN）**，报文 64 字节（1 B ID + 63 B 内容）。

## 五、阶段 3：Bootloader 中的 DFU 通讯协议

### 5.1 帧格式（旧 SigmaBus 帧，Cmd=0x0B）

> ⚠️ **注意**：DFU 传输阶段使用的是 **0xC4 SigmaBus 旧帧格式**（现已仅存于 Bootloader；MainApp 已切换为新 Modbus 帧），与《Modbus通讯协议说明_20261022》的帧（无 0xC4、大端数据段、CRC-16）不同：本帧带 0xC4 起始符、Len 为**小端**、校验为**求和补码 SigmaCRC**（非 Modbus CRC-16），且新文档功能码表未定义 0x0B。Bootloader 未列入本次改造范围，**上位机升级模块的传输阶段必须仍按本节格式组帧。**

```
┌────┬───────────┬──────────┬─────────┬──────────┬─────────────┬──────────┬─────────────┐
│ C4 │ LenL LenH │ Addr     │ Cmd     │ DFU_CMD  │ CHIP_ID     │ Payload… │ CRCL CRCH   │
└────┴───────────┴──────────┴─────────┴──────────┴─────────────┴──────────┴─────────────┘
 起始符  整帧总长   设备地址0x00 0x0B(DFU) 见5.2/5.3   固定0x00       见下      SigmaCRC
        = Payload长 + 9（含DFU_CMD与CHIP_ID两字节及帧头尾）
```

- **SigmaCRC**：帧内校验字段之前所有字节（从 C4 起）求和，取 16 位补码 `(~sum + 1) & 0xFFFF`，**低字节在前**。
- **DFU_CMD**（`Com.DataProcess.h`）：`0x01`=查询当前状态、`0x02`=新固件信息、`0x03`=代码块。
- 超长帧由多个 HID 报文按字节流续传（每报文 63 B 内容），接收端以 Len 与 300 ms 接收超时判定帧边界。

**设备应答统一格式**：Cmd `0x0B` 帧，Payload 固定 3 字节 `[0x01][CHIP_ID][status]`：

| status | 含义 |
|:-:|---|
| `0x01` | 固件信息错误（ModelCode 不匹配等） |
| `0x02` | 固件代码错误（写入失败 / 未收到信息帧先发代码 / 块间超时） |
| `0x03` | 升级继续（信息帧通过 / 中间代码块写完，等待下一块） |
| `0x04` | 升级失败（最终校验和不符） |
| `0x05` | 升级成功（最后一块且校验和正确） |

### 5.2 第一步：固件信息帧（DFU_CMD=0x02）

Payload 固定 **85 字节**（即升级 .bin 文件的帧头，设备端 `DfuProgramInfoCheck()` 解析）：

| 偏移 | 字段 | 长度 | 说明 |
|:-:|---|:-:|---|
| 0 | ModelCode | 6 B | `"Bootld"`=升级 Bootloader 本体（写向 `0x00000000`）；`"000000"`=通用升级；其余必须等于本机 DevInfo[0..2] 逐字节拆出的机型码（当前机型 `"JYM001"`）。注：MainApp 的 DevInfo 已改为大端打包（首字符在高字节），Bootloader `DfuProgramInfoCheck()` 已同步改为**先取高字节**展开，打包脚本 modelCode 直接用可读字符串 `"JYM001"` 即可匹配 |
| 6 | ModelName | 64 B | 保留区，代码跳过不校验（补 0） |
| 70 | VerX / VerY / VerZ | 3 B | 固件版本号，各 1 字节 |
| 73 | FirmwareLength | 4 B | **小端**，固件代码总字节数 |
| 77 | FirmwareChecksum | 4 B | **小端**，全部代码数据（含 4 字节补齐）按 4 字节小端字**累加和 mod 2³²**（即打包脚本 `crc32Calc`，实质为加法校验和，非多项式 CRC32） |

信息帧总长 = 9 + 85 = 94 B，需 2 个 HID 报文传输。

设备校验通过后的动作：`DfuStep=1`；`IapAddress` 置 `0x00008000`（APP 升级）或 `0x00000000`（Bootld 升级）；清累计器；**先将 EndFlag 预写为 `DFU_END_FAIL`（Byte3=0x01）**——此后若掉电或中断，任何复位都会滞留 DFU，防变砖；随后应答 `status=0x03 继续`。

### 5.3 第二步：固件代码块帧（DFU_CMD=0x03，循环发送）

每帧 Payload = 固件数据分块。**打包工具默认 256 B/块**（可选 256/512/1024；接收缓冲 `COM_CP_BUF_SIZE=1024`，故单帧 Payload 上限约 1017 B）。每块 256 B 时整帧 265 B，占 5 个 HID 报文。

设备对每块依次处理（`DfuProgram()`）：

1. 数据拷入页缓冲 `IapArray`；
2. **Gamma 解密**：仅对累计接收 ≤ 8 KB 的部分逐字节解密（密钥 `0x1C9CBB63`；算法：`tmp = b - 0xA3` → 半字节交换 → 异或密钥字节；与上位机脚本 `GammaEncrypt` 严格互逆，加密同样只作用于前 8 KB）；
3. `Iap.Write` 顺序写入 Flash，`IapAddress += len`；
4. 累加校验和（与 5.2 FirmwareChecksum 同算法）；进度值 +ProgressIncrement；
5. 已收字节数 < `FirmwareLength` → 应答 `0x03 继续`，并启动**块间超时**（约 1 s，扫描式定时）——超时未收到下一块，设备**主动**发一帧 `status=0x02 代码错误`；
6. 已收字节数 ≥ `FirmwareLength` → 比对总校验和：一致应答 **`0x05 升级成功`** 并置完成标志；不一致应答 `0x04 升级失败`。两种情况均清 `DfuStep`（不断电可拔插 USB 重新升级）。

### 5.4 第三步：结束与跳转

上位机收到 `0x05` 后无需再发任何数据。设备端 `DfuTask()`：延时 1 s → `DfuTerminate()` 写状态字 `{A5, 0xFF(BL_JUMP_TO_APP), 0x00, 0x02(DFU_END_SUCCESS)}` → `NVIC_SystemReset()`。

下次复位 `BootCheck()` 读 Byte1=`0xFF` → 校验 APP 栈顶合法 → 跳转 `0x00008000` 运行新固件，USB 重新枚举，升级完成。

> 升级成功后 Bootloader 不再运行；MainApp 启动时 ModelCode 若与 Flash 信息区不一致会触发参数表恢复出厂逻辑（`MemParamsInit` 机型校验）。

## 六、上位机操作序列与报文示例

完整升级一个 MainApp（机型码 JYM001，示例数据为说明性质）：

| 步骤 | 方向 | 内容 | 说明 |
|:-:|---|---|---|
| 1 | 主机→设备 | `00 10 00 0A 10 08 00 01 8D 09`（HID `0x51`，Modbus 新帧） | 写 0x1008=1 进 DFU（MainApp 已按新帧改造；旧固件为 `C4 0B 00 00 03 08 10 01 00 15 FF`） |
| 2 | 设备→主机 | `00 02 00 08 00 00 F8 19`（HID `0x11`，ACK 无错误） | MainApp ACK 后约 200 ms 内复位 |
| 3 | — | 等待 USB 重新枚举（约 1~3 s） | 此后所有帧走 Bootloader SigmaBus 格式 |
| 4 | 主机→设备 | 信息帧：`C4 5E 00 00 0B 02 00 │ 'J''Y''M''0''0''1' + 64B(0) + VerX VerY VerZ + FwLen(4B小端) + Chksum(4B小端) │ CRC` | DFU_CMD=0x02 |
| 5 | 设备→主机 | `… 0B │ 01 00 03 │ …` | status=0x03，可以开始发代码 |
| 6 | 主机→设备 | 代码块帧 ×N：`C4 09+Ln 00 00 0B 03 00 │ 256B密文 │ CRC` | **逐块发送，每块必须等到 0x03 再发下一块**（块间超时约 1 s） |
| 7 | 设备→主机 | 中间块均回 `01 00 03`；最后一块回 `01 00 05` | 0x05=升级成功 |
| 8 | — | 等约 2 s 设备自动重启进新固件 | 无第 9 步 |

异常分支：

- 步骤 5 收到 `0x01`（信息错误）：ModelCode 不匹配，终止；
- 步骤 7 中途收到 `0x02`（代码错误/超时）或最终 `0x04`（校验失败）：设备已预置 END_FAIL，**重新上电仍滞留 DFU**，可从步骤 4 重新升级；
- 升级 Bootloader 本体：信息帧 ModelCode 用 `"Bootld"`，代码写向 `0x00000000`，流程相同（当前 Bootloader 在应用段，升级由通用 Bootld 文件完成）。

升级包文件：`Firmware_4_Updater_Build.py`（MainApp 固件）/ `Firmware_4_BootUpdater_Build.py`（Bootloader 本体）由 Keil hex 自动生成 `.bin`（结构 = 进入 DFU 帧 + 信息帧 94 B + N×代码块帧），上位机可按字节流逐帧透传 HID 0x51；**两个脚本的进入 DFU 帧已于 2026-10-26 同步更新为 §3.1 的新 Modbus 帧**（信息帧/代码块帧仍为 Bootloader 解析的旧 SigmaBus 帧）。

## 八、与新版 Modbus 协议的关系（待办提示）

《Modbus通讯协议说明_20261022.md》规划的新帧格式（无 0xC4、大端数据段、Modbus CRC-16）对 DFU 流程的覆盖情况：

1. **触发进入 DFU（阶段 1）**：已按新协议记载并完成代码实现（§3.1，Func `0x10` 写 `0x1008`，帧 `00 10 00 0A 10 08 00 01 8D 09`），MainApp 已不再解析旧帧；升级打包脚本（MainApp/Bootloader 两侧）头部触发帧已同步替换为新帧；
2. **传输阶段（阶段 3，Bootloader）**：新文档功能码表中没有 0x0B（DFU），Bootloader 完全按旧 SigmaBus 帧实现且**不随上位机协议升级改变**——上位机升级模块必须对 DFU 通道单独保留旧格式组帧；
3. Bootloader 内参数读（0x0000~0x000A 机型码）与写 0x1008（仅回 ACK）的兼容处理，同样沿用旧帧；
4. 若希望 DFU 全程统一新帧，需下一代 Bootloader 同步改造通讯层，并更新本文档与升级打包脚本。
