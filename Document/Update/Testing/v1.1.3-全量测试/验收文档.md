## 5. 最终结论判定规则

1. **P0 一票否决**：只要缺陷清单里有任何 P0 未修复（或有 P0 修复但未全量复测），本轮结论 **不通过**。
2. **门禁一票否决**：G1–G7 任一失败 = **不通过**（对应 N1–N8）。允许的唯一例外：缺陷清单写明「阻塞原因 + 责任方」且被用户明确接受，此时该项记「阻塞」而不是「通过」。
3. **功能项**：P1–P8 / U1–U17 / R1–R12 / S1–S5 按「通过 / 失败 / 阻塞」逐项判定；**阻塞项不得默认通过**，必须写阻塞原因 + 解除条件 + 责任方（S10）。
4. **未执行项**：§3 的五项与 V4 一律不参与通过率计算，也**不得**计入"通过"数量。
5. **快照 vs 工作树**（S9）：正式结论取快照（含 `baseline+fix-N` 叠加）；工作树 Final Run 只作差异附录。工作树若退步 → 缺陷清单单列「最终树回归」；若变好 → 记「已被外部修复（未经本会话复测）」，不改快照结论。
6. **结论表述**：
   - 全部 G1–G7 通过 + 无 P0 + 功能项无 fail → **通过**（遗留 P2/P3 列清单）；
   - 有 P1 未修 → **不通过**（除非用户书面接受并写明遗留）；
   - 有 blocked 项 → 结论写「**有条件通过 / 不通过**」必须二选一，并单列阻塞清单，禁止含糊。
7. **证据完整性**：任一 `通过` 项的 `evidence` 缺失或为空 → 该项降级为「阻塞（证据不全）」，由 `SubStage_7_1` §3 的校验脚本判定。
