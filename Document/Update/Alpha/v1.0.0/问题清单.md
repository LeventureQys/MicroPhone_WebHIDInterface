### 置顶区（待用户确认，阶段阻塞）

#### Q1. 技术栈与实现语言：原生 JS、原生 TS，还是引入框架
- 问题描述：仓库当前只有文档，无任何代码，技术栈完全空白。需求要求高交互 EQ 曲线（拖拽调 14 段参数）＋ 多面板参数控制 ＋ 后续 WebHID 通信。此选择贯穿全部源码，改判会引发全量返工。
- 建议方案：**Vite + 原生 TypeScript（无框架）**。EQ 曲线用 Canvas 分层渲染（直接对齐参照项目架构），参数面板用原生 DOM + 模板函数；TS 把协议参数范围表固化成类型和常量（36 个标量 + 14 段 EQ），避免字段名与单位手写时拼错；WebHID 需要直接持有 canvas / HTMLElement 句柄，框架在此无收益。
- 备选方案：
  1. **原生 JS（对齐参照项目）**：可与参照项目逐文件互抄，迁移成本最低；代价是协议字段无类型护栏，14 段 EQ × 4 参数 + 3BandDrc × 17 参数全靠人工校对。
  2. **React + TS + Vite**：面板组件化、状态管理现成；代价是引自建 canvas 组件的生命周期适配，且引入运行时体积与状态同步复杂度，与 toC 上位机的"一个窗口一组控件"场景不匹配。
- 风险预警：选 TS 需要一次类型声明投入（约 200 行），但之后所有参数范围校验由编译器兜底；选 JS 则需靠单元测试覆盖范围校验，测试量更大。**需用户决策**。
- 置信度：82%
- 分区归属：置顶区
- 归入原因：架构选型，选错即全量返工。

回复：请你按照推荐方式进行吧

#### Q2. 交付形态：纯浏览器站点，还是现在就预留桌面应用壳
- 问题描述：产品是 toC 商业上位机，最终大概率要以安装包交付；但 Alpha v1.0.0 需求只要求 UI，且 WebHID 在浏览器中要求 `https` 或 `localhost` 安全上下文，双击 `file://` 打开会直接失败。形态决定构建产物、启动方式与验收手段。
- 建议方案：**纯浏览器站点（Vite dev server + 静态 build 产物），不做桌面壳**。设备访问统一走自建 `Transport` 抽象层，浏览器实现走 `navigator.hid`，Alpha 阶段用 `MockTransport` 假数据；将来接 Electron/Tauri 只需新增一个 Transport 实现，UI 与参数层零改动。
- 备选方案：
  1. **现在就上 Electron 壳**：可直接用 `file://` 加载、能上系统级 API；代价是引入主进程/打包链路，与"仅 UI 设计"的阶段目标不成比例，且验证周期变长。
  2. **Tauri**：产物体积小；代价是 Rust 工具链与本轮无设备联调的需求无交集。
- 风险预警：仅浏览器形态下，用户必须通过 `npm run dev` 或本地静态服务器访问，双击 HTML 不可用；这一点会写进交付说明。**需用户决策**。
- 置信度：78%
- 分区归属：置顶区
- 归入原因：影响构建产物与验收流程，后期切换成本高。

回复：还是要加一个Electron壳，因为这个主要是需要让用户双击运行的上位机软件，当然，请你提前考虑好跨平台

### 自决区（不阻塞）

#### Q4. 自决方案：EQ 曲线引擎以参照项目架构为蓝本移植（Canvas 分层）
- 问题描述：需要高帧率、可拖拽、对数频率轴、14 段叠加的曲线视图。
- 自决方案：移植参照项目已验证的分层方案——`CoordinateMapper`（对数频率 ↔ 像素）、RBJ biquad + BLT Butterworth 频响计算、`CanvasRenderer` + `GridLayer/LabelLayer/CurveLayer/HandleLayer` 四层绘制、`requestAnimationFrame` 脏标记渲染、DPR 自适应。参数范围与类型枚举改由本仓 `效果器参数范围.xlsx` 驱动。
- 自决理由：参照项目为 MIT 许可，可合法借鉴并在文件头保留版权归属；该方案已在同类需求中验证，重写无收益。置信度 92%。
- 风险预警：参照项目滤波类型为 `peak/lowShelf/highShelf/lowPass/highPass`，本仓协议枚举为 `0.PEAK / 1.LS / 2.HS / 3.LPF / 4.HPF`，需一层稳定映射；映射表进领域常量表，防两侧漂移。

#### Q5. 自决方案：14 段硬件 EQ 建模、7 段上位机可调
- 问题描述：参数表注明「EQ(14段)」，备注列写明「7段开放在上位机，7段内部调音」。
- 自决方案：数据模型按 14 段建立（`bands[0..13]`），UI 只渲染 7 个可拖拽节点（`bands[0..6]`）；曲线计算包含 14 段全部贡献（内部 7 段默认增益 0，故不影响形状）；另设只读列表标注「内部调音段 7–13」。这样将来开放全部 14 段时，仅需改一个可见性开关。
- 自决理由：建模成本一致，但可避免"只建 7 段"导致的返工。置信度 88%。
- 风险预警：若内部 7 段实际不可读（下位机不返回），只读列表需改为「不显示」。Alpha 无联调，先按可显示处理。

#### Q6. 自决方案：电平表与实时数据由 Mock 数据源驱动
- 问题描述：Alpha 阶段无下位机，但需求 1 要求"显示电平实时数据"。
- 自决方案：`MockTransport` 以 60Hz 定时器产生拟真电平曲线（含起音/释放包络、峰值保持、-60dBFS 噪声底），可一键切换到「静音 / 说话 / 音乐」三档模拟；连接状态区分「未连接 / 模拟中 / 已连接」三态并在顶栏显示。
- 自决理由：无硬件条件下，动画质量直接决定 UI 说服力；三档场景也便于验收取证。置信度 88%。
- 风险预警：Mock 数据只用于 UI 演示，不得进入任何"已同步下位机"的状态判断路径，避免后续接入时误信。

#### Q7. 自决方案：通信层先立契约、后接设备
- 问题描述：需求 2 要求"参数实时写入下位机"，Alpha 不做联调。
- 自决方案：定义 `Transport` 接口（`open/close/send/subscribe/onStateChange`）与 `HidProtocol` 帧结构占位（报告 ID、参数字节、长度校验），Alpha 只实现 `MockTransport`；`WebHidTransport` 留文件骨架与 TODO 注释，不实现字节编解码。
- 自决理由：接口先定，UI 与参数层不被设备细节污染；联调阶段只补实现。置信度 90%。
- 风险预警：帧结构未拿到 HID 报告描述符前不能定稿，Alpha 阶段的 `HidProtocol` 仅作占位，不做字节序假设。

#### Q8. 自决方案：语义未明的协议字段只展示原名，不臆造标签
- 问题描述：`Comp.Rate`（1–100，默认 6）在压缩器已有 MakeUpGain/Threshold/Attack/Release/KneeWidth 的情况下语义不明，可能是 ratio；`NoiseGate.ratio` 标注为"扩展比（如2.0表示2:1）"且范围为 0.05–0.999，与常规比值语义相反。
- 自决方案：UI 标签统一「协议字段名 + 单位」，不为这两个字段编造中文语义；`NoiseGate.ratio` 按参数表原文范围与步进实现，不做倒数换算。
- 自决理由：猜语义比不写标签更坏；后续拿到协议说明一处改文案即可。置信度 85%。
- 风险预警：客户端可能觉得这两个控件"看不懂"。若确认语义，需要一并确认是否换显示格式（比值 / 百分比）。

#### Q9. 自决方案：桌面优先，1280×800 起
- 问题描述：上位机软件以桌面窗口为主，需求未提移动端。
- 自决方案：主布局 1280 起双列（主视图 + 右侧参数栏），≥1600 三列扩展；≤1050 折叠为单列，≤680 仅保证不破版。仅做 CSS 响应式，不做移动端专门交互。
- 自决理由：与参照项目一致，且上位机场景无触屏优先需求。置信度 90%。
- 风险预警：EQ 曲线在窄屏下节点会拥挤，需在断点处降低节点半径。

#### Q10. 自决方案：7 段可调 EQ 的默认频率按对数几何分布
- 问题描述：参数表只给单段默认值（Freq 1000 / Gain 0 / Q 0.7 / Type PEAK），未给 7 段的默认频率落点。
- 自决方案（定稿）：14 段全部 PEAK、Gain 0、Q 0.7；可调段 `0..6` 按对数等距铺满 20 Hz–20 kHz（`freq[k] = round(20 × 10^(0.5k))` → 20 / 63 / 200 / 632 / 2000 / 6325 / 20000 Hz），内部段 `7..13` 插在相邻可调段之间（36 / 112 / 356 / 1122 / 3556 / 11220 / 17825 Hz）。
- 自决理由：与硬件通常的 1/1 倍频程布局一致，且落在参数范围内。置信度 82%。
- 风险预警：若下位机实际默认频点不同，接入时需按下位机返回值覆盖；届时只改默认常量。

#### Q11. 自决方案：依赖只走 npm 官方源，不引 GitHub 直连依赖

### 自决区（v2 新引出）

#### Q13. 自决方案：三端构建用 electron-vite，主进程只做窗口与 WebHID 权限
- 问题描述：Electron 需要 main / preload / renderer 三套构建，手工拼 vite 配置易在打包后出现路径与 ESM/CJS 混用问题。
- 自决方案：用 `electron-vite` 统一三端构建（它同时产出 main、preload、renderer，并处理 `__dirname`/ESM 差异）；`package.json` 的 `main` 指向 `out/main/index.js`；打包用 `electron-builder`。
- 自决理由：这是 Electron + Vite 的标准组合，避免自建双构建管线。置信度 88%。
- 风险预警：`electron-vite` 与 Electron 版本的兼容性必须在阶段三首日实测；不通过则退回"vite 构建 renderer + esbuild 单独打 main/preload"的两段式。

#### Q14. 自决方案：同时产出安装包与免安装包，验收以双击运行为准
- 问题描述：用户诉求是"用户双击运行"。
- 自决方案：`electron-builder` 配置 `nsis`（装机版，含桌面快捷方式）与 `portable`（单文件免安装）两种 Windows 产物；macOS 配 `dmg`、Linux 配 `AppImage`。Alpha 验收证据用 **portable exe 双击启动 + 主窗口可见**，另附 NSIS 产物生成成功记录。
- 自决理由：两种产物共用一套配置，边际成本低；portable 最适合"双击就能跑"的验收动作。置信度 88%。
- 风险预警：`electron-builder` 打包需下载 `winCodeSign`/`nsis` 资源，走 GitHub 会超时，必须配镜像（见 `AGENTS.md` 已知坑 6）。

#### Q15. 自决方案：单窗口 + 左侧模块导航的工作台结构
- 问题描述：36 个标量参数（另有 14 段 EQ）分属 7 个模块，单页竖排会拉出 4 屏以上。
- 自决方案：单窗口，顶栏（品牌 / 连接状态 / 语言切换 / 快照）+ 左导轨（电平 / 输入 / EQ / 动态 / 分频 DRC / 设置）+ 主内容区。默认进「电平」页：输入输出电平表 + 关键参数摘要 + 迷你 EQ 概览；「EQ」页为全宽曲线工作台 + 7 段列表。
- 自决理由：上位机类软件的常规信息架构，模块切换零加载。置信度 80%。
- 风险预警：这是产品结构判断而非纯技术选择；阶段二的设计文档会给出完整线框描述，届时可否决并重排，重排成本限于布局层。

#### Q16. 自决方案：i18n 自建字典，不引第三方框架
- 问题描述：需中英双语切换。
- 自决方案：`src/i18n/` 下 `zh.ts` / `en.ts` 两份扁平键值字典（键名 `module.field.label` 风格），`t(key)` + `subscribe`；DOM 文案通过 `data-i18n` 属性批量刷新，动态文本用 `t()` 直接取值。缺失键回落到 key 本身并在控制台警告。
- 自决理由：文案量约 150 条，引 i18next 属净负担；自建实现可在 vitest 里直接测缺失键。置信度 92%。
- 风险预警：切换语言时若某处用 `textContent` 硬写中文会漏刷；阶段二契约要求所有文案只经 `t()` 出口。

#### Q17. 自决方案：默认语言跟随系统，手动选择持久化
- 问题描述：默认语言未指定。
- 自决方案：首启读 `navigator.language`，`zh*` → 中文，其余 → 英文；顶栏切换后写 `localStorage['micstudio.lang']`，后续启动优先读该键。
- 自决理由：符合双语产品惯例，且无需 IPC。置信度 88%。
- 风险预警：Electron 打包后 `navigator.language` 反映 Chromium 区域设置，可能与系统语言不同；若出现错判，改由主进程 `app.getLocale()` 通过 preload 透传。

#### Q18. 自决方案：Electron 安全基线按官方默认收紧
- 问题描述：上位机要访问 USB HID 设备，壳的安全配置若过松会留下注入面。
- 自决方案：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、`webSecurity: true`；preload 只经 `contextBridge` 暴露 `{ appVersion, platform, locale, pickHidDevice, onHidDeviceSelected }`；主进程实现 `session.setDevicePermissionHandler` 与 `select-hid-device` 事件处理（Alpha 阶段不调用，仅保证不被默认拒绝逻辑卡死）。
- 自决理由：官方推荐基线，且为联调阶段预留 WebHID 通路。置信度 90%。
- 风险预警：`sandbox: true` 下 preload 只能用受限 API，若需 Node 能力要改 `sandbox: false` 并加重隔离，属联调阶段决策。

#### Q19. 自决方案：macOS / Linux 只保证代码与配置跨平台，产物不在本轮验证范围
- 问题描述：开发机是 Windows 11（活动桌面会话 Session 1），无 macOS 与 Linux 环境；用户要求"提前考虑好跨平台"。
- 自决方案：源码不做平台相关分支（除 preload 暴露的 `platform` 字段）；`electron-builder` 配好 `mac`（dmg，需要 mac 机器出包）与 `linux`（AppImage）目标；窗口使用系统原生边框与标题栏，不写 Windows 特有的 frame 定制；字体栈不依赖平台专有字体。验收报告把 macOS/Linux 产物列为「未验证（无环境）」。
- 自决理由：如实标注边界，不让"配好了"冒充"验过了"。置信度 90%。
- 风险预警：macOS 需要签名/公证才能给终端用户安装，Linux 需要 `.desktop` 与图标规范，两者都是后续版本的活。**此项需用户在验收时认可"未验证"的边界**。

## v3 补充（阶段三实现期新引出，2026-10-17）

### 置顶区（阶段阻塞，需用户决策）

#### Q20. portable / nsis 产物在本机沙箱不可验证
- 问题描述：`electron-builder --win nsis` 报 `MicStudio Setup <ver>.exe process failed 2`；`MicStudio-1.0.0-alpha.0-portable.exe`（69 MB，`--win portable` 生成成功）双击后立即退出、`%TEMP%` 下不留解压目录。根因是 NSIS 安装/自解压要在 `%TEMP%` 下展开并拉起子进程，本机沙箱对此有限制（同源现象：Chromium 在 `%TEMP%` 下报 `Code Cache ... 拒绝访问 (0x5)`）。
- 建议方案：**以 `release/win-unpacked/MicStudio.exe` 作为本轮可运行交付证据**（已验证：窗口创建、renderer ready、`capturePage` 出图、`--hold=12000` 存活 12.2 秒后退出码 0）；portable 与 nsis 标为**未验证**，交付说明里写清"安装包需在真机验证"。
- 备选方案：
  1. 把 portable 的解压目录改到非 `%TEMP%`（需自定义 NSIS 脚本，electron-builder 不直接支持）——成本高且仍受同一执行限制。
  2. 改用 `electron-builder` 的 `dir` 目标 + 自写打包脚本（zip）—— 绕开 NSIS，但就不是"双击安装"形态了。
- 风险预警：若真机上 portable 也不可用，则"双击运行"需求未闭环，需要改用安装包形态重新验证。**需用户决策**（是否接受本轮交付以 win-unpacked 为运行证据）。
- 置信度：根因判断 75%，产品本体可用性 95%。
- 分区归属：置顶区

### 自决区

#### Q21. 自决方案：字典键补齐
- 问题描述：视图层用到 `meter.title`/`meter.subtitle`/`eq.badge`/`eq.bandTitle`/`drc.conflict`/`topbar.connectUnavailable` 六个键，2.3 首版未包含；`drc.cond.*` 原为"低频压缩"等静态文案，无法表达 `fc1`/`fc2` 占位。
- 自决方案：中英字典各补 6 键，`drc.cond.*` 改为 `freq < {fc1} Hz` / `{fc1} Hz < freq < {fc2} Hz` / `freq > {fc2} Hz`。`Record<DictKey, string>` 保证两侧键集合编译期一致。
- 自决理由：纯文案补齐，不改变架构。置信度 95%。

#### Q22. 自决方案：语言切换强制重建当前视图
- 问题描述：首版 `router.go(current)` 在路由未变时直接返回，导致切换语言后卡片标题与参数标签仍是旧语言（导航与顶栏已更新）。
- 自决方案：Router 增加 `reload()`（销毁并重建当前视图），shell 在 `lang` 变化时调用它。
- 自决理由：文案由 `t()` 在构建时求值，重建是唯一可靠刷法。置信度 95%。已验证：`artifacts/shot-input-en.png` 全英文无残留。

#### Q23. 自决方案：导航高亮订阅 store
- 问题描述：首版导轨只在构建时同步一次高亮，路由切换后高亮不动。
- 自决方案：`createNavRail` 订阅 `store.onChange` 更新 `is-active`，并把取消订阅挂到节点 `destroy` 上；shell 重建 chrome 时先逐个 `destroy`。
- 自决理由：避免每次切页重建导轨，也避免订阅泄漏。置信度 95%。

#### Q24. 自决方案：主进程新增 `--hold=<ms>` 诊断参数
- 问题描述：打包产物是常驻 GUI 进程，自动化验证时外部命令会被子进程 stdout 句柄拖住；桌面截屏在本机不可用。
- 自决方案：主进程支持 `--hold=<ms>`（存活指定毫秒后 `app.exit(0)`）与 `--exec-file=<path>`（注入交互脚本），配合 `--screenshot` 完成"窗口创建 → 存活 → 出图"三段取证；主进程同时把启动过程写入 `<userData>/startup.log`。
- 自决理由：把不可观测的 GUI 启动变成可留证的文件证据，且不影响正常双击运行（无参数即常规模式）。置信度 90%。
