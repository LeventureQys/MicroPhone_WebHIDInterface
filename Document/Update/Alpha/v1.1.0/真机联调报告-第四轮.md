## 1. 设备与固件身份

`scripts/probes/real4-state.js` / `real4-reports.js` → `artifacts/real4/state.log`、`reports.png`

```
productName "USB Audio Device"   vendorId 0x0A67   productId 0x0010   serialNumber null
collections: [{ usagePage 0xFF01, usage 0x0001,
                inputReports:  0x10 / 0x11 (63 B each),
                outputReports: 0x50 / 0x51 (63 B each) }]
```

- 设备处于 **App 模式**：`0x13` 读 `0x2000` 正常回 `20 00 00 01 00 00`（`real4-state` 的 `mode = app(modbus)`）。
- 应用固定用 **IN `0x11` / OUT `0x51`**；`0x10` / `0x50` 是描述符里声明但固件未使用的报告 ID（写 `0x50` 无回执；静置 4 s 无主动上报）。
- 信息区（`0x0000–0x003D`，62 词）**全 0**：型号 `""`、名称空、固件 `0.0.0.0`、`VID/PID=0x0000/0x0000`、SN 空。因此应用顶栏显示「设备型号不匹配」告警（设计允许，不阻断）。
- 配置区（`0x1000–0x100D`，14 词）**全 0**：心跳 `0x1000=0`（表内默认 700）、`0x1002` 系统预设总数 0、`0x1007` 通讯错误 0（表内范围 1–5）。
- 预设区（`0x2000–0x2071`）除场景写过的字段外**全 0**；`0x2000` 校验和 0、`0x2001` 预设有效标志 0、EQ 段 `enable/type/freq/q` 全 0（§3.4）。

> 这就是「型号/固件/序列号读不出来」和「EQ 曲线看起来不对」的共同根因：**设备没有出厂预设，也没有信息区数据**。主机的 `sync()` 照实把它读成 0，UI 按 0 夹紧显示（例如 EQ 频率夹到 20 Hz），不是上位机解码错。

### 3.2 诊断自检

连续 4 次（`app-check`、`stress` 两次、`idle` 最后一次）三步全绿；`0x2025` 前三次读到 1，最后一次读到 2（`stress` 末尾应用了「会议」场景，encLevel=2）：

```
通过 · sync      · 回读全量完成
通过 · read      · 0x2025 = 1（最后一次为 2）
通过 · writeBack · 写回原值并读回一致
```

`stress` 里两次自检之间只隔 1 次 6.2 s 等待，**没有出现第二轮报告里的「0x13 抢发被 0x12 应答认领」**，坑 26 的竞态修复在真机上成立。

### 3.3 高级参数与只读拦截

- 抽屉里 `[data-param]` 共 **40** 个（gain / noisegate / comp / limit / drc3 等），加上「环境降噪」卡里未带 `data-param` 的 `enc.OnOff` 开关与 `enc.Level` 四档，共 **42 项**。
- `gain.Mic`（`0x2023`）与 `gain.Hp`（`0x205A`）渲染为 `.pfield--readonly`，**子控件数量 0**，显示「只读 + 0」。

### 3.5 空闲 60 s

## 4. 连续写与写 Flash 时延（坑 27 复测）

### 4.1 应用级：20 次连续写

`real4-stress.js`：连上设备后，把「降噪强度」滑杆在 45/55 之间来回拖 20 次（间隔 380 ms），再等 5 s。

| 指标 | 结果 |
|---|---|
| 每次 DOM 更新耗时 | 0.2–0.5 ms |
| 20 次写期间顶栏 | 20/20 采样「已连接 / 已同步」，无提示条 |
| 出/入帧 | 561 / 561（含轮询） |
| `timeouts` / `retries` / `crc` | **0 / 0 / 0** |
| `droppedPolls` | 369（写后 600 ms 轮询让位，预期行为） |
| 写后轮询恢复 | 2 s 内 95 帧（≈21 ms/帧） |
| 紧接着自检 ×2 | 均 3/3；自检后点「会议」场景仍「已同步」 |

**结论**：2026-10-27 的四处主机侧修复（`writeTimeoutMs=3000`、`writeRetries=1`、`writeSettleMs=600`、`writeGraceMs=8000`）在真机上没有引入回归；连续写 20 次没有超时、没有重发、没有误判断连。

### 4.2 协议级：写 ACK 时延

`real4-limits.js` / `real4-write-eq.js` / `real4-flash-stall.js`，裸 HID：

| 用例 | 样本 | ACK 时延 | 超时 | 多回执 |
|---|---|---|---|---|
| `0x2025` 写 1/2 交替 ×20 | 20 | 4.1 / 4.9 / 9.8 ms（min/median/max） | 0 | 0 |
| EQ Gain `0x202A` 360/350 ×12 | 12 | 4.3 / 9.6 / 11.1 ms | 0 | 0 |
| DRC PreGain `0x2063` 0/100 ×12 | 12 | 4.2 / 9.9 / 10.4 ms | 0 | 0 |
| 8 帧连写（场景式）×4 轮 | 32 | 单帧 5.9–10.9 ms，8 帧合计 **76.5–80.4 ms** | 0 | 0 |
| 单写后**立即读** `0x2057` ×12 | 12 | 写 2.4–8.9 ms，读 6.1–10.7 ms | 0 | — |
| 8 连写后立即读 ×4 | 4 | 读 8.0–10.9 ms | 0 | — |

**结论**：在本机当前固件/状态下，**写参数没有可观测的 Flash 停顿**（单帧 ACK 2.4–11.1 ms，写后读也没有被拉长），用户 2026-10-27 反馈的「调参数卡顿」本轮**不复现**。不同轮次的抖动在 2.4–11.1 ms 之间，单帧从未超过 12 ms。

### 4.3 边界：为什么还不能给“落盘”打包票

预设区 `0x2000`（校验和）= 0、`0x2001`（预设有效标志）= 0。固件可能因此**只把参数写进 RAM / 不落 Flash**，也可能落 Flash 但很快返回 ACK。主机侧无法区分。要确认落盘，需要：

1. 固件把预设区初始化成有效状态（`validFlag=1`、校验和正确）；或
2. 手动改参数 → 断电重启 → 重新连接回读（清单 ⑬，需要人工配合）。

## 5. 协议符合性与固件边界

### 5.1 读容量

| 请求 | 结果 |
|---|---|
| `0x13` `0x2000` × 114 | ✅ 238 B 帧，22.2 ms，114 词 |
| `0x13` `0x2000` × 118 | ✅ 246 B 帧，18.6 ms，118 词（`0x2072..0x2075` 也在内，全 0） |
| `0x13` `0x2000` × 119 / 120 / 126 | `ACK 0x0005`（约 4–11 ms），不再回超长帧 |
| `0x12` 118 个地址 | ✅ 478 B 帧，51.3 ms，118 条（4 个报文） |
| `0x12` 119 个地址 | `ACK 0x0005` |
| `0x12` 124 / 125 个地址 | 两次采样均 `ACK 0x0005`（请求 5 个报文） |
| `0x12` 126 / 127 个地址 | **不稳定**：第一轮 127 回 `ACK 0x0005`、126 无回执；复跑时 126/127 都无回执（3 s 超时） |

**上限是 118 个寄存器**（不是帧容量 126）。118 是设备实际区间的上界，合理；119+ 用 `ACK 0x0005`（数据错）而不是 `0x0002`（长度错），语义可商榷，但至少不再回 >512 B 的帧。`0x12` 的 5 报文请求（124–127 地址，>252 B）会偶发“连 ACK 都没有”，更像收帧缓冲/解析边界问题，建议固件侧一起看。

> 取证口径：`real4-proto.js` 的 `readFull` 只认 `0x13` 数据帧，所以 119/120/130 在 `proto.log` 里显示 `ok:false`；`ACK 0x0005` 由 `real4-limits.js` 的通用收帧确认（`limits.log`）。

### 5.2 地址校验

| 地址 | 结果 |
|---|---|
| `0x2076` / `0x2077` | `ACK 0x0005`（拒绝）✅ |
| `0x3000` | ❌ 回 `0x13` 数据帧（12 B），3 次采样值在 `0x2520` / `0x2025` / `0x2001` / `0x0120` 之间变化 |
| `0x4000` | ❌ 同上，值在 `0x0120` / `0x2001` 之间跳变 |

写 `0x3000` 会正确回 `ACK 0x0005`，但**读**会返回未初始化内存（3 次采样值不稳定）。这是本轮新确认的固件缺陷：地址校验大概率只检查了低位/区间的一端，越界索引仍然参与取值。

### 5.3 只读 / 范围

| 用例 | 期望 | 实测 |
|---|---|---|
| 写只读 `0x2023`（MIC 音量）= 55 | `ACK 0x0004` | **`ACK 0x0000`**，读回 55；已写回 0 |
| 写 `0x2025`（降噪强度，域 0–3）= 5 | `ACK 0x0005` | **`ACK 0x0000`**，读回 5；已写回 1 |
| 写 `0x2025` = 999 | `ACK 0x0005` | **`ACK 0x0000`**，读回 999；已写回 1 |
| 写未知 `0x3000` = 1 | `ACK 0x0005` | `ACK 0x0005` ✅ |

主机侧对只读项仍然**零出帧**（界面没有控件）；但设备侧不校验，任何能发帧的工具都能改只读/越界值。

### 5.4 拒绝路径

| 用例 | 回执 |
|---|---|
| UnitID `0x01` 的读请求 | 1.4 s 窗口内 **17 条 ACK**（`0x0001`/`0x0002` 交替） |
| Len=4 的读请求 | 1.4 s 窗口内 **17 条 ACK**（`0x0002`/`0x0001`） |
| 坏 CRC 的读请求 | 3 条 ACK（`0x0002`/`0x0001`） |
| 未知功能码 `0x20` | **静默**（1.6 s 无任何回执） |

第二轮记录的「一次请求 18 条 ACK」仍在（本轮 17 条，量级相同）。主机侧靠「已上总线的请求不丢 + 超时」能扛过去，但这属于固件应修的通信噪声。

### 5.5 电平

- `0x2057` 连读 10 次，10/10 为 0。
- 静置 4 s / 空闲 60 s 内**没有任何 `0x10` 主动上报**（Report ID 统计只有 `0x11` 的应答）。
- 主机 20 ms 轮询正常（60 s 内 2802 帧），但拿不到非 0 电平。清单 ⑨（电平标定）因此仍无法做。

### 5.6 设备信息 / 配置 / 预设

| 区 | 词数 | 结果 |
|---|---|---|

## 8. 给固件方的清单（按优先级）

1. **P0：初始化设备信息区与预设区**（`0x0000–0x003D`、`0x2000–0x2071`）。至少写入：型号 `JYM001`、设备名、固件版本、VID/PID、SN；预设 `validFlag=1`、`checksum` 正确、EQ 7 段 `enable/type/freq/q` 与表内默认一致、NoiseGate/Comp/DRC 默认值。否则上位机永远显示“型号不匹配/固件 0.0.0.0”，EQ 段处于关闭状态，且无法判断参数是否落盘。
2. **P0：确认参数写入是否真的落 Flash**。当前 20 次写 ACK 4–6 ms、`validFlag=0`；请给出“写参数 → 落盘”的时序与标志位，或说明是否需要写 `0x1004 SaveNo`。
3. **P1：拒绝路径只回一条 ACK**。UnitID 失配 / Len 错现在会喷 17 条，且会吞掉后一条合法请求；建议按协议回一条 `0x0001`/`0x0002` 后清空接收缓冲。
4. **P1：只读 / 范围校验**。`0x2023`（只读）与 `0x2025`（0–3）目前都接受越界值。
5. **P1：读地址校验**。`0x3000` / `0x4000` 返回未初始化内存；应按 `0x0005` 拒绝（`0x2076` 已经做对，可复用同一段判断）。
6. **P1：电平 `0x2057`**。给出真实电平值或周期上报；现在恒 0，上位机电平表无法标定。
7. **P2：`0x12` 5 报文请求（124–127 地址）偶发无回执**，以及未知功能码静默。
8. **P2：Bootloader 写 Flash 挂死**（首刷记录 §3）。修好前不做 DFU。

## 10. 下一步建议

1. **固件**按 §8 的 P0/P1 修一轮，尤其是信息区/预设区初始化与落盘时序；
2. 固件给出新包后，先做「改参数 → 断电 → 重连回读」（清单 ⑬），确认落盘；

4. 主机侧本轮无需改代码；若要提升空白设备的可用性，可考虑「信息区全 0 时 UI 回退到表内默认值并标注设备未初始化」，但这会掩盖固件问题，建议先由固件修复。
