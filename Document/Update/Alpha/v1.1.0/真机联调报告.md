# 真机联调报告 — Alpha v1.1.0（首轮，M001 真机）

> 日期：2026-10-26　设备：M001 麦克风（`VID 0x0A67 / PID 0x0010`，新固件「支持参数协议」）
> 上位机：本仓 `main@7a2195c` + 本次 3 处修复（§4）　环境：Windows + Electron 33.4.11 + 原生 WebHID
> 取证目录：`artifacts/real/`（每项一张截图 + 一份探针日志）；探针源码：`scripts/probes/real-hid-*.js`

## 0. 结论摘要

真机已经**识别、打开、收发报文全部通**，但**参数链路目前无法完成同步**，卡点是固件侧的一个解析器缺陷，且该缺陷与 v1.1.0 虚拟下位机当初踩的是同一个坑（设计 §12 R-14 / SubStage 2.1 §256）。

| 结论 | 状态 | 一句话 |
|---|---|---|
| 设备枚举与描述符 | ✅ | `Usage Page 0xFF01 / Usage 0x01`，IN `0x11` / OUT `0x51` 各 63 B，与设计一致 |
| 报文往返 | ✅ | 应答延迟 3–15 ms，CRC/Len/多包重组全部正确（98 B 请求跨 2 报文也是通的） |
| 参数同步 `sync()` | ❌ | 第 1 条回读成功，第 2 条被固件对「补位零」回的假 ACK 抢答 → `ACK 0x0002` → 链路进 error |
| 写入 | ⚠ | 整帧（62 B）写入稳定生效并回 `ACK 0x0000`；只要补位多到解析器错位就整段失效 |
| 设备信息 / 预设默认值 | ❌ | 0x0000–0x003D 全 0；0x2000–0x2071 全 0（可写、可读回，但没有出厂值） |
| 电平 | ⚠ | 读 `0x2057` 恒 0；设备另以 `0x10` 帧主动推送 `0x2057 = 0`，周期 ≈ 167 ms；上位机已能接住推送 |
| DFU | ⏸ | 本轮**故意未做**：同步都不通，写 `0x1008` 的风险不可控（见 §5） |

**唯一 P0**：固件不丢弃 63 B 报文尾部的 `0x00` 补位，并把解析器拖进「错位→闭锁」状态。修掉它，其余结论才有意义。

## 1. 设备身份（实测）

`scripts/probes/real-hid-enumerate.js` → `artifacts/real/enumerate.log`

```
vendorId 0x0A67  productId 0x0010  productName "USB Audio Device"  serialNumber null
collections: [{ usagePage 0xFF01, usage 0x0001, inputReports 2, outputReports 2 }]
```

两条附带事实（与既有笔记冲突，已同步到 `AGENTS.md`）：

1. **Electron 33.4.11 的 `HIDDevice` 有 `collections`**，且 `getDevices()` / `requestDevice()` 都带。原判断「Electron 的 `HIDDevice` 不含 collections、主进程只能粗筛」作废——`shared/webhid-whitelist.ts` 的 usage 复核在真机上其实是可用的。
2. `getDevices()` 会把**系统里所有 HID 设备**列出来（键盘 / 鼠标 / 灯效 / 我们这台），因为主进程 `setDevicePermissionHandler` 对 `hid` 一律放行。设备抽屉因此出现 11 行，需要用户自己认领。建议 v1.1.1 用 `collections` 按白名单过滤（§6-R2）。

## 2. 联调结果（应用侧）

`scripts/probes/real-app-link.js` → `artifacts/real/app-link.png`（截图里诊断卡就是失败现场）

```
22:15:37.084 → 00 13 00 0A 20 00 00 72 71 2E        读 0x2000..0x2071 (114)
22:15:37.101 ← 00 13 00 EE 20 00 00 72 00 00 00 00  读回 0x2000..0x2071 (114)   ← 正常，17 ms
22:15:37.101 → 00 12 00 62 00 00 00 01 00 02 00 03  读设备信息 46 地址            ← sync 第 2 条
22:15:37.104 ← 00 02 00 08 00 02 79 D8              ACK 0x0002 长度错             ← 3 ms 后抢答
22:15:37.105 → 00 12 00 62 …                        请求失败：设备返回 长度错（0x0002）
22:15:37.105 →                                      进入 error
```

- 第 1 条（预设区 114 词，请求帧 10 B，补位 53 B）**成功**；正是这条请求的尾部补位让固件吐出 13 条假 ACK。
- 第 2 条（设备信息 46 地址，请求帧 98 B 跨 2 报文）刚发出 3 ms 就被其中一条假 ACK「接住」，`ParamSession` 按协议把 `0x0002` 判为该请求的失败 → `sync()` reject → `failFatal` → 顶栏「同步失败」。
- 应用侧行为符合设计（`S-h`：`0x02` 可终止任何在途请求），**不是上位机 bug**。

## 3. 固件缺陷清单

按严重度排序。每条给「现象 / 证据 / 影响 / 建议」。「补位」= 需求 C1 要求出站帧发满 63 B、尾部补 `0x00`。

### F1（P0，根因）尾部补位 `0x00` 被当成帧来解析

- **现象**：每个请求之后，设备额外送出 `floor(补位字节/4)` 条 `ACK 0x0002`（偶发混 `0x0001`）。
- **证据**（`real-hid-pad-boundary.js`，同一地址重复写，仅改补位长度）：

  | 请求帧 | 补位 | 回执总数 | 其中 `0x0000` | 额外错误 ACK |
  |---|---|---|---|---|
  | 14 B | 49 | 13 | 1 | 12 |
  | 38 B | 25 | 7 | 1 | 6 |
  | 50 B | 13 | 4 | 1 | 3 |
  | 58 B | 5 | 2 | 1 | 1 |
  | 62 B | 1 | 1 | 1 | 0 |

  额外 ACK 数严格等于 `floor(补位/4)`，说明固件从帧尾继续按 4 字节步进「解析」零，并把 `Len = 0` 判成长度错。
- **影响**：ACK 通道不可用。协议没有请求序号，上位机无法区分「这条 ACK 属于哪次请求」，补位产生的假 ACK 必然污染后续请求的判定（§2 的失败就是这么来的）。
- **建议**：照抄虚拟下位机的实现（`tools/vdevice/device-stack.mjs` 的 `#drain`）：`Len === 0` → 整段丢弃；剩余不足 4 B 且全 `0x00` → 丢弃；`Len` 非法 → 清空累积器后回 `ACK_LEN_ERR`。这条在 v1.1.0 就已经写进设计（§12 R-14：「不处理补位会在每个请求后多回一个 ACK `0x0002`」）。

### F2（P0）解析器错位后闭锁，只在约 1.5 s 静默后自愈

- **现象**：一次请求之后，紧接着的请求**完全不被应答**；设备改为每个 USB IN 轮次（实测 9–15 ms）回一条 `ACK 0x0002` / `0x0001`，持续到总线静默。
- **证据**：
  - `real-hid-raw-inbound.js`：① 干净读 62 B → 2 报文应答（7 / 11 ms）；② 立刻再发同形请求 → 500 ms 内 56 条报文，**全部是 ACK，没有任何数据帧**；③ 同样；④ 静默 3 s 后再发 → 恢复正常。
  - `real-hid-gap.js`：两次干净读之间的静默取 0 / 20 / 50 / 100 / 200 / 400 / 800 ms，**第二条请求 7/7 全部失联**（每次约 54 条 ACK）；取 1500 ms 时 2/2 成功。
- **影响**：`sync()` 固定两条请求背靠背（`真实响应 17 ms`），必然踩中；参数轮询（设计 20 ms）更不可能成立。
- **建议**：除了 F1 的补位丢弃，再加两道保险：① 帧尾不足 4 B 的残留一律丢弃（不要留在累积器里等下一包）；② 加帧间超时（建议 20–50 ms 无新报文即清累积器），把「错位」限制在单次请求内而不是闭锁。

### F3（P1）设备信息区 0x0000–0x003D 全 0

- **证据**：46 个信息地址随机读 → `modelCode` / `deviceName` / 固件版本 / `fwType` / VID / PID / SN / `comErrAck` 全为 0（`real-hid-handshake.js`、`real-hid-params.js`）。
- **影响**：顶栏与诊断卡无法显示型号、固件版本、序列号；`device/warn.modelMismatch` 会一直挂着（型号码 `""` ≠ `JYM001`）；DFU 前无法核对版本。
- **建议**：填真实值。至少 `0x000B–0x000E`（固件 4 词）、`0x0016/0x0017`（VID/PID）、`0x0000–0x0002`（型号码）、`0x001E` 起 SN。

### F4（P1）预设区 0x2000–0x2071 全 0（没有出厂默认值）

- **证据**：`0x13` 连续读 114 词 → 全 0；`0x2001 validFlag` = 0；`0x2000 checksum` = 0。写入后能读回（F1 修好后），说明 RAM 在、默认值没灌。
- **影响**：界面回读后会把 EQ 频点显示成 0 Hz、增益 0、噪声门阈值 0 dB 等非法/无意义值（`toRaw/fromRaw` 会夹紧，但数值是错的）。
- **建议**：上电加载参数表默认值（`M001参数表V0.1.xlsx` 的 G 列原始值），并置 `0x2001 = 1`。

### F5（P1）`0x2057` 电平恒 0，且只走主动推送

- **证据**：`real-hid-throughput.js` 空闲 2 s → 12 条 `00 10 00 0A 20 57 00 00 73 DB`（`0x10` 帧推 `0x2057 = 0`），平均间隔 167 ms；单独读 `0x2057` 也回 0。
- **影响**：电平表在真机上永远静止。另外**设备用 `0x10`（随机写）帧上报**，与设计里「上位机轮询 `0x12` 读 `0x2057`」的假设不同——上位机本轮已补上对 `0x10` 的接收（§4）。
- **建议**：确认采样通路（是否有输入源 / 是否需要使能）；把推送周期定死并写进协议（例如 30–50 Hz），上位机据此把轮询降为兜底。

### F6（P2）没有权限表与范围校验

- **证据**（均为干净 62 B 帧，`real-hid-ack-clean.js`）：

  | 用例 | 固件回执 | 结果 |
  |---|---|---|
  | 写只读 `0x2023`（gain.Mic） | `0x0000` | 被接受（本次写的是原值 0，未产生副作用） |
  | 写只读 `0x205A`（gain.Hp） | `0x0000` | 被接受 |
  | 写「不参与读写」`0x1000`（心跳） | `0x0000` | 被接受，读回 = 1 |
  | 写未映射 `0x9000` | **无任何回执** | 静默丢弃 |
  | 写超范围 `0x2025 = 5`（域 0–3） | `0x0000` | 被接受，读回 = 5 |

- **影响**：`0x0004`（只读错）与 `0x0005`（超范围）永远不会出现，`ACK` 语义形同虚设；未映射地址静默 → 上位机只能吃满 500 ms × 3 超时。
- **建议**：按寄存器表的 `R/W` 列与 `min/max` 列建表校验；拒绝时分别回 `0x0004` / `0x0005`；未知地址回 `0x0001`。

### F7（P3）只认 `UnitID = 0x00`

- **证据**：`real-hid-experiments.js` 用 `UnitID` 0 / 1 / 2 / 3 / 0xFF 读同一组地址：只有 `0x00` 有数据应答，其余只回 ACK（`0xFF` 完全静默）。
- **影响**：无（本产品单机地址 0）。记录备查：若将来多机挂在同一 HID 通道，需要实现 `UnitID` 过滤。

### F8（P3）IN 通道吞吐偏低

- **证据**：空闲推送 ≈ 6 帧/s（167 ms/帧）；故障期 ACK 输出 ≈ 60–110 帧/s（9–15 ms/帧）。
- **影响**：**推送时**的低帧率说明主循环/上报节奏慢；设计里 20 ms 轮询（50 次/s）需要固件确认能否承受。建议：电平改为设备主动推送（30–50 Hz），上位机轮询降频为兜底。

## 6. 遗留与建议

- **R1（固件，阻断）**：F1 + F2。这两条不修，参数链路在真机上不可用。
- **R2（上位机）**：真机设备列表按 `collections` 过滤（Electron 已提供 usage page），避免把键盘/鼠标列成可连接设备。
- **R3（上位机/协议）**：电平改「推送为主、轮询兜底」后，`TIMING.pollIntervalMs = 20` 与设计 §5.5 的 50 Hz 假设需要一并改口径（本轮不动，等固件把推送频率定下来）。
- **R4（固件）**：F3/F4 决定界面能不能显示真实型号与默认值，建议与 F1 一起发版。
- **R5（待确认）**：写参数后掉电是否保留（联调清单 ⑬）——本轮无法验证（没有可控断电），需要固件确认是否要写 `0x1004 SaveNo`。
