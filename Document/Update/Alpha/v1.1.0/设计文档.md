# 设计文档 — Alpha v1.1.0（下位机联调与固件升级）

> 版本：Alpha v1.1.0
> 依据：`Document/Update/Alpha/v1.1.0/需求文档.md`（下称**需求**）、`Document/Update/Alpha/v1.1.0/问题清单.md`（下称**问题清单**，置顶区已清空）

## 1. 背景与目标

v1.0.0 只交付界面层：`AppStore` 是状态唯一写入口，参数改动经 `Transport` 出站，实际走 `MockTransport`；`device/protocol.ts` 是 3 行占位，`device/webhid-transport.ts` 全方法抛 `WEBHID_NOT_IMPLEMENTED`，`domain/params.ts` 的 36 项没有寄存器地址。

v1.1.0 要把「参数双向读写」与「固件升级」两条链路在**没有真机**的条件下做到可联调：

1. 参数协议的帧编解码、寄存器映射与标定、串行传输层、上电回读、电平轮询全部落地；
2. DFU 的镜像预检、协议流、安全护栏全部落地；
3. 用一套自研**虚拟下位机**（Python 桥 + Node 侧车）跑通全流程与全部故障分支；
4. 真机到位后只改「通道 = native」+ 确认 report ID，不再改协议代码。

问题清单已定案的四条约束（本文全部遵守）：

| 定案 | 本文落点 |
|---|---|
| Q1 DFU 用 SigmaBus 旧协议，帧层策略可替换 | §5.8/§5.9/§5.10；只实现一套实现，不写第二套死代码 |
| Q2 寄存器表为唯一真值（含默认值原始值） | §5.2/§5.3 |
| Q3 默认 Mock + 显式标记 | §5.5/§5.6/§6.3 |
| Q4 不做保存入口 | §5.7 只读回显 `0x2000`；§9 边界 |

## 4. 系统结构与数据流

```
┌──────────────────────────── src/main（主进程） ────────────────────────────┐
│ window / menu / startup.log                                                │
│ webhid.ts   select-hid-device → 白名单放行（默认 usagePage 0xFF01）        │
│ ipc.ts      白名单下发 / platformInfo / DFU 期间禁止睡眠与拦截退出          │
└────────────────────────────────────────────────────────────────────────────┘
                                   ↕ preload（contextBridge：window.micstudio）
┌─────────────────────────── src/renderer（渲染进程，唯一业务层）────────────┐
│ ui/views/console-view   ← AppStore.onChange                                │
│ ui/views/device-view    ← DeviceLink + WebHidSession + DiagnosticsHub      │
│ ui/views/firmware-view  ← FirmwareController(DfuRunner)                    │
│ ui/views/settings-view  ← 通道配置（localStorage）                          │
│ ui/topbar                ← AppStore.sync + channel.kind + link.status      │
│                                                                            │
│ AppStore（唯一写入口）── setParam ──► ChannelTransport ──► WebHidTransport │
│      ▲  applyEcho / setSync                          │ ParamSession        │
│      └───────────────────────────────────────────────┘  写入队列/合并/轮询│
│                                                          │                 │
│ device/link.ts：WebHidSession（发现/开关）→ attach → 回读 → ready          │
│ device/dfu/**：DfuRunner（帧/镜像/会话），与 ParamSession 互斥              │
└────────────────────────────────────────────────────────────────────────────┘
        │ navigator.hid（真机）                      │ navigator.hid（虚拟，webhid-kit polyfill）
        ▼                                            ▼
   真机 HID（本版本不验收）                  ws://127.0.0.1:8765/ws
                                                     │ webhid-bridge.v1
                                             virtual_hid（Python，子模块，只读）
                                                     ↕ hid.outputReport / device.setInput
                                             tools/vdevice 侧车（Node，本仓新增）
```

关键不变量：

1. **AppStore 是唯一状态写入口**：UI 只调 setter；设备回读经 `applyEcho` 进 store，不经过 `setParam`（避免回写设备形成环）。
2. **一问一答**：`ParamSession` 任意时刻最多一个未完成请求（ACK 不带 Func/地址，无法配对）。
3. **默认值只作兜底**：`sync === 'ready'` 后所有参数值来自回读（C5/C4）。
4. **DFU 与参数链路互斥**：进入 DFU 前 `DeviceLink.suspendForDfu()`（停止轮询与写队列），退出后 `resumeAfterDfu()`。
5. **协议层纯函数**：`device/proto/**`、`device/dfu/frame.ts`、`device/dfu/image.ts` 不引用 DOM / 定时器 / WebHID，可在 Node 与浏览器同时运行。

### 5.1 `device/protocol.ts`（常量层，改写现有文件）

```ts

  readonly in: number;

export interface ParamFrame {
  readonly unitId: number;
  readonly func: number;
  readonly data: Uint8Array;    // 不含 Len 与 CRC
}
export interface DecodeResult {
  readonly frames: readonly ParamFrame[];
  readonly rest: Uint8Array;    // 未消费字节（半帧）
  readonly issues: readonly DecodeIssue[];
}

export function encodeFrame(func: number, data: Uint8Array, unitId?: number): Uint8Array;
export function decodeStream(buffer: Uint8Array, expectedUnitId?: number): DecodeResult;
export function frameLength(frame: ParamFrame): number;   // data.length + 6
```

**流式拆帧算法（必须照此实现，单测逐条断言）**：

0. **补位零规则（pad-skip）**：`rest` 里出现连续两个 `0x00` 时（`buf[0] === 0x00 && buf[1] === 0x00`），丢弃 1 个前导 `0x00` 并**不记 issue**，重复直到不满足或缓冲不足 2 字节。依据：`UnitID = 0x00` + `Func = 0x00` 不可能是合法帧（`0x00` 不是任何功能码），而发送方每帧末尾按 63 B 补 `0x00`（C1），所以帧结束后紧跟的零一定是补位。这条规则让"一帧 + 若干补位零"不产生任何 issue；同时保留"单个前导 `0x00`"（可能是下一帧被报文边界切开的 UnitID）。
1. `rest` 不足 4 字节 → 全部留作 `rest`，结束。
2. 读 `len = (buf[2] << 8) | buf[3]`。
3. `len < 6` → 记 `length` issue，丢弃 1 字节，回到 0（重同步）。
4. `len > 512` → 记 `capacity` issue，丢弃 1 字节，回到 0。
5. `len > buf.length` → 未收全，`rest = buf`，结束。
6. `unitId = buf[0]`，若传了 `expectedUnitId` 且不等 → 记 `unit` issue，丢弃 1 字节，回到 0。
7. `func = buf[1]`，不在 `{0x02,0x10,0x11,0x12,0x13}` → 记 `func` issue，丢弃 1 字节，回到 0。
8. 校验 CRC（覆盖 `buf[0..len-3]`，与 `buf[len-2] | buf[len-1]<<8` 比）→ 不等记 `crc` issue，丢弃 1 字节，回到 0。
9. 产出一帧（`data = buf.slice(4, len-2)`），`buf = buf.slice(len)`，回到 0。

`encodeFrame`：`Len = data.length + 6`，`Len` 大端在 `Func` 之后，CRC 覆盖 `UnitID..Data` 末字节，低字节先发。`data.length + 6 > 512` 时抛 `RangeError`（调用方必须在此之前拦住）。

行为契约（逐条可测）：

| 编号 | 规则 |
|---|---|
| S-a | 任意时刻最多一个未完成请求；新请求按 FIFO 排队，`queueDepth` 反映排队数 |
| S-b | 写节流：`write()` 把条目并入待发表（同 addr 覆盖旧值），`writeThrottleMs` 后打包发出；打包时同批内地址相邻且同属预设区的条目合成一条 `0x11`，其余走 `0x10` |
| S-c | 单请求超时 `requestTimeoutMs`；超时/`ACK_CHECKSUM_ERR`/`ACK_DEV_ADDR_ERR` 重试，最多 `requestRetries` 次；`ACK_READ_ONLY_ERR`/`ACK_DATA_ERR`/`ACK_LEN_ERR` 不重试 |
| S-d | 同一请求连续 3 次失败（即首轮 + 2 次重试）→ `phase = 'error'`，清空队列，派发 `onError({kind:'timeout'...})` 或对应 ACK 映射的错误；此后 `write()` 静默丢弃并计入 `droppedPolls` 之外的计数器（见 S-h） |
| S-e | `sync()`：一条 `0x13` 读 `0x2000` 起 114 个 → 丢弃 `LEVEL_ADDR` 的值（R4-8）→ 逐 addr 派发 `onEcho`；再发**一条** `0x12` 随机读 **46 个地址**（`0x0000`–`0x0005`、`0x000B`–`0x000F`、`0x0016`、`0x0017`、`0x001E`–`0x003D`、`0x1007`）组 `DeviceSnapshot`（请求数据 92 B、响应 184 B，远小于 506 B 与 126 地址上限；见 §12 R-13）；全部成功后 `phase = 'ready'` 并开启轮询；任一失败按 S-c 重试，最终失败 → `error` |
| S-f | 轮询：`phase === 'ready'` 且 `setPolling(true)` 时每 `pollIntervalMs` 发一条 `0x12` 读 `LEVEL_ADDR`；队列里有写请求时本轮跳过（不排队）；在途超过 `pollTimeoutMs` 未回 → 丢弃该次并 `droppedPolls++`，不发新轮询直到下一次 tick |
| S-g | 入站解析用 `decodeStream`；`issues` 逐条计入 `crcErrors`（`problem === 'crc'`）或诊断 warn；未消费部分留到下次拼接。补位 `0x00` 由 §5.4.2 步骤 0 消解，**不产生 issue、不进诊断**，`rest` 最多残留单个 `0x00` |
| S-h | **应答归属**：在途为读（`0x12`/`0x13`）时，读响应帧即为应答；在途为写（`0x10`/`0x11`）时，`0x02` 即为应答。**`0x02` ACK 可终止任何在途请求**（参数协议 A.3：错误一律以 ACK 上报，见 §12 R-15）：`0x0000` → 正常完成；`0x0004`/`0x0005`/`0x0002` → 不重试，按 `readOnly`/`range`/`len` 结束该请求；`0x0001`/`0x0003` → 按 S-c 重试。既不是 ACK、也不匹配在途类型的帧 → 记 `unexpected` warn 并丢弃，不改变在途状态 |
| S-i | 诊断：每条出站帧与入站帧各一条 `DiagEntry`；环形缓冲定长 `ringSize`，超出丢最旧 |
| S-j | `phase === 'error'` 后调用 `write()`：直接丢弃并派发一次 `onError({kind:'disconnected'})`（同一次 error 状态只派发一次）；`read()` 直接 reject；`sync()` 允许从 `error` 重新发起（重连语义） |
| S-k | `dispose()` 清空所有定时器；在途与排队请求的 Promise 以 `disconnected` reject（避免 `await` 永久挂起）；之后任何方法调用都不再派发事件、不再调用 `send` |
| S-l | 异常隔离：`send` 抛错或返回 rejected Promise → 按通道错误处理（`phase='error'`、`onError({kind:'disconnected'})`、停轮询），**异常不外抛** |
| S-m | 统计合并：统计变化后用微任务（`queueMicrotask`）去重再派发 `onStats`，不要每帧一次回调 |

export const SIGMA_ACK_CHECKSUM_ERR = 0x0003;

export interface SigmaFrame {
  readonly addr: number;
  readonly cmd: number;
  readonly data: Uint8Array;    // 载荷（DFU 时首字节是 DFU_CMD，次字节 CHIP_ID）
}
export type SigmaProblem = 'start' | 'length' | 'capacity' | 'crc' | 'addr';
export interface SigmaIssue { readonly problem: SigmaProblem; readonly offset: number; readonly detail: string }
export interface SigmaDecodeResult {
  readonly frames: readonly SigmaFrame[];
  readonly rest: Uint8Array;
  readonly issues: readonly SigmaIssue[];
}
/** 16 位累加取反加一：((~(sum(frame[0..n-3])) & 0xFFFF) + 1) & 0xFFFF，低字节先发 */
export function sigmaCrc(bytes: Uint8Array): number;
export function encodeSigmaFrame(cmd: number, data: Uint8Array, addr?: number): Uint8Array;
export function decodeSigmaStream(buffer: Uint8Array): SigmaDecodeResult;
export function encodeDfuInfoFrame(info: DfuInfo): Uint8Array;      // 90 B
export function encodeDfuBlockFrame(data: Uint8Array): Uint8Array;   // 7 + n + 2；n ∈ [1,256]（末块可短，出厂包末块 248）
export function decodeDfuStatus(frame: SigmaFrame): { status: number } | null;
export function decodeSigmaAck(frame: SigmaFrame): { err: number } | null;   // err = data[0] | data[1] << 8（SigmaBus 数据小端）
```

`decodeSigmaStream` 的重同步规则与 §5.4.2 同构：找不到 `0xC4` 时逐字节跳过并记 `start`；`len < 9` 或 `len > 1022`（`MAX_SIGMA_FRAME`）记 issue 后丢 1 字节；CRC 不符记 `crc` 后丢 1 字节；`addr !== 0` 记 `addr` 后丢弃该帧。`cmd` 按 `cmd & 0x7F` 归一（DFU 材料 §1.2：CRC 通过后 bit7 被忽略）。

**SigmaBus ACK 的错误码是 16 位小端**：实测帧 `C4 09 00 00 02 01 00 30 FF` 表示 `DEV_ADDR_ERR = 0x0001`、`C4 09 00 00 02 03 00 2E FF` 表示 `CHECKSUM_ERR = 0x0003`（DFU 材料 §2.5）。按大端解析会让本模块导出的 `SIGMA_ACK_*` 常量永远匹配不上，验收文档一律以 `0x0001`/`0x0003` 为准。

export const GAMMA_BYTES = 8192;
export const BLOCK_BYTES = 256;

export const BOOT_MAX_BYTES = 0x8000;     // 32 KB
export const BOOT_MODEL_CODE = 'Bootld';

export function gammaDecrypt(bytes: Uint8Array): Uint8Array;   // 只处理前 8192 B、4 字节粒度
export function gammaEncrypt(bytes: Uint8Array): Uint8Array;   // 逆运算，供测试与打包工具用

export function encodeInfoFrame(info: DfuInfo): Uint8Array;
export function encodeBlockFrame(block: Uint8Array): Uint8Array;
```

`parseImage` 校验顺序（任一失败即返回 `{ ok:false }`，**不抛异常**；顺序经 4.1 实现与单测固定，见 §12 变更记录）：

1. `decodeSigmaStream` 解析全文；有任何 `issues` → `frame`（含 `crc` 时用 `crc`），或 `rest` 非空（末帧被截断）→ `frame`。
2. 帧序列形状：`frames[0]` 必须是 `CMD=0x03` 写 `0x1008=1`（EnterDfu）；**不存在任何** `DFU_CMD=0x02` 信息帧 → `infoCount`；信息帧存在但不在 `frames[1]` → `frame`；其余帧必须全部 `DFU_CMD=0x03` 且块长度 ∈ `[1,256]` → 违者 `frame`；有 EnterDfu + Info 但无任何数据块 → `frame`。
3. 每个非末块的数据长度必须为 256；全部块（含末块）必须 4 字节对齐 → 违者 `blockSize` / `notAligned`。
4. `modelCode` 必须为 6 个可打印 ASCII（`0x20..0x7E`）→ 违者 `modelMissing`。
5. `FwLength ≤ (modelCode === 'Bootld' ? BOOT_MAX_BYTES : APP_MAX_BYTES)` → 违者 `limitExceeded`（**上界检查先于长度一致性**：这样 R6-3 的"把 `FwLength` 改成 `0x40000` 就拒绝"成立于只伪造声明长度的包）。
6. `FwLength` 必须等于全部块数据总长 → 违者 `lengthMismatch`。
7. `sum32LittleEndianWords(gammaDecrypt(cipher)) === FwChecksum` → 违者 `checksumMismatch`。

对拍（单测与自检脚本共用）：`encodeInfoFrame(info)` 与 `encodeBlockFrame(block)` 的输出必须与包内 `frames[1..]` 逐字节一致；不一致时 `parseImage` 仍返回 `ok:true`，但 `DfuRunner` 在发送前会重新编码，**对拍只作为测试断言**，不在运行时拒绝（运行时拒绝会掩盖编码 bug 的表现，见任务书 4.1 的测试要求）。

流程契约：

| 阶段 | 行为 |
|---|---|
| preflight | `parseImage` + 型号匹配（`deviceModelCode()` 与 `info.modelCode` 比对；`info.modelCode === '000000'` 视为通配）+ `Bootld` 拒绝（R6-9，除非 `allowBootld: true` 由自检脚本注入） |
| entering | 用参数协议帧 `00 10 00 0A 10 08 00 01 8D 09` 写 `0x1008=1`，等 `0x02 ACK 0x0000`，超时 `requestTimeoutMs`（共 2 次尝试）；ACK 不能证明已进 DFU，只当作"已发出"。**帧格式依据**：需求 R6-3 原文"写 `0x1008 = 1`（参数协议）→ 等 ACK"、需求 A.7 示例帧、Q1 定案（App 模式 = 新参数协议）。DFU 材料 §2.1 里出厂包首帧 `C4 0B 00 00 03 08 10 01 00 15 FF` 是**厂商旧工具**的写法，不适用于本仓 App 模式；若真机 App 只认 SigmaBus，症状是 `entering` 两次超时（安全失败，不写坏设备），已进《真机联调清单》⑩ |
| probing | 发 `DFU_CMD=0x02` 信息帧，等 `0x0B` 状态帧；`0x03` → 进 `writing`；`0x01` → `statusInfo` 失败；超时 → 重试，最多 `dfuProbeAttempts` |
| writing | 逐块发 `DFU_CMD=0x03`（265 B → 5 个 63 B 报文），每块等一个状态帧：`0x03` 继续；`0x05` → `settling`；`0x04` → `statusFail`；`0x02` → 歧义态；超时 → 歧义态 |
| 歧义态 | **不补发单块**：整轮从 `probing` 重来（重发信息帧复位设备指针），`round++`；超过 `dfuRoundRestarts` → `restartExhausted` |
| settling | 收到 `0x05` 后停止发送，等 `dfuSettleTimeoutMs`（期间不向设备发任何帧），由调用方（`FirmwareController`）经 `DeviceLink.resumeAfterDfu()` 触发重连与回读 |
| verifying | 回读固件版本 `0x000B`–`0x000D` 与型号码，比对 `info.version`（`000000` 通配镜像跳过比对）；不一致 → `verify` 失败但保留"设备已在跑同型号固件"的说明 |

`SIGMA_ACK_CHECKSUM_ERR`（`C4 09 00 00 02 03 00 2E FF`）语义是"该帧被丢弃、Flash 指针未前进"→ 允许重发同一块（与"歧义态整轮重来"不同），但为简化和安全，**本版本也按整轮重来处理**（多花时间、不会写坏），在诊断日志里注明实际遇到的是 ACK 校验错而不是超时。

#### 5.14.3 故障注入规则

配置形状（`faults` 数组，按顺序匹配第一条命中的规则）：

```jsonc
{ "on": { "mode": "app"|"bootloader"|"any", "func": 18, "dfuCmd": 3, "nth": 3, "phase": "info"|"block"|"any" },
  "action": "drop"|"delay"|"dropAck"|"crcError"|"ackError"|"powerLoss"|"disconnect"|"sticky",
  "ms": 200, "code": 5, "times": 1 }
```

| action | 语义 |
|---|---|
| `drop` | 该入站帧不产生任何应答（模拟丢帧） |
| `delay` | 推迟 `ms` 后再应答（侧车内部定时队列，不阻塞事件循环） |
| `dropAck` | 正常处理（状态前进）但不回任何报告 |
| `crcError` | 应答帧最后两字节 CRC 置错 |
| `ackError` | 参数协议应答 `0x02` 带指定 `code`；DFU 模式回 `CMD 0x02` 的 SigmaBus ACK |
| `powerLoss` | 之后所有入站帧不再处理，模式固定 bootloader，直到 `POST /control/mode {mode:'app'}` |
| `disconnect` | 持续 `ms` 内对所有入站帧不答（模拟掉线），之后恢复 |
| `sticky` | 把上一次应答的尾部与新应答拼在同一条 63 B 报告里（模拟帧粘连，考验上位机的流式拆帧） |

`nth` 指"第 n 次命中该类帧"（从 1 起）；`times` 缺省 1，`0` 表示永久。

#### 5.14.5 模式切换与"掉线"

- `app` 模式收到 `0x10` 写 `0x1008=1`：先回 `0x02 ACK 0x0000`，置 `mode='bootloader'`（可注入 `delay`）。
- `bootloader` 模式：只解析 SigmaBus；参数协议帧一律不答（真实设备在 DFU 里也不会答参数帧）。
- DFU `0x05` 成功：把固件版本寄存器写成镜像 `Ver`（`Ver` 全 0 时写 `0.0.1` 以体现"版本已变"，并在 `stats` 里标注 `versionSynthetic: true`），随后切回 `app`。
- `disconnect` 故障：侧车对该时间窗内所有帧不答，**不关闭 WS**（桥接无设备注销接口，见问题清单 §3.4）；上位机的掉线判定来自请求超时。

## 6. 关键算法

### 6.1 CRC-16（参数协议）

```
crc = 0xFFFF
for b of bytes: crc ^= b; repeat 8: crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : crc >> 1
发送：Lo = crc & 0xFF 先发，Hi = crc >> 8
```
自检向量（8 条，见需求附录 A.6，本轮已逐条复算通过）：`00 02 00 08 00 05 → 38 1A` 等。

### 6.2 SigmaCRC（DFU）

```
sum = Σ frame[0 .. len-3]（8 位累加）
crc = ((~sum & 0xFFFF) + 1) & 0xFFFF，低字节先发
```

### 6.3 标定换算

```ts
toRaw(spec, value)   = clamp(round((value - add) / mul), rawMin, rawMax)   // kind==='linear'
                     = clamp(round(value), rawMin, rawMax)                // kind==='raw'
fromRaw(spec, raw)   = raw * mul + add                                    // kind==='linear'
                     = raw                                                // kind==='raw'
rawMin / rawMax      = toRawRound(min) / toRawRound(max)（由 spec.min/max 反算并四舍五入到整数）
```

- 浮点误差：`toRaw` 前先把 `value` 量化到 `step`（复用 `domain/values.ts:quantize` 的算法；但 `device/registers.ts` 必须**零 import**（验收 B7），故在文件内自带同算法的 `snap()`：`min + round((v-min)/step)*step` + `toFixed(6)` 归一 + 夹紧，`step <= 0` 时直接夹紧返回），结果再用 `Number(x.toFixed(6))` 归一。
- `fromRaw(toRaw(v))` 在步进内允许 ±1 个原始值误差（R2-2）。

### 6.4 写合并与节流（S-b）

```
write([{id,value}]) → {addr, raw}
  pending: Map<addr, raw> = 合并（同 addr 覆盖）
  窗口 writeThrottleMs 到期：
    按 addr 升序，把连续相邻（+1）且同属 preset 区的分组：
      组长度 ≥ 2 → encodeSeqWrite(首址, 值数组)
      组长度 == 1 → encodeRandWrite([{addr, raw}])
    分组成的帧按顺序入队（S-a 串行发送）
```
2 秒 / 120 次写 → 20 个窗口 → ≤ 20 条帧（R3-6）。

### 6.5 电平映射与峰值保持（R5）

```
inputRms  = clamp(raw / 256, 0, 1) * 96 - 96        // -96..0 dBFS（线性假设，Q4 待确认）
inputPeak = max(inputRms, prevPeak - 300ms 内线性衰减 3 dB? 否：见下)
```

峰值保持取值与 v1.0.0 的 `MeterCanvas` 内部逻辑**不重复实现**：transport 只给 `inputPeak = inputRms`，由 `MeterCanvas` 的既有峰值保持（`HOLD_MS 1200` / `HOLD_DECAY_DB_PER_SEC 20`）负责显示；需求 R5-4 的"本地 300 ms 衰减"由电平采样在 transport 侧的 `inputPeak = max(inputRms, prev * decay)` 实现，`decay` 按 300 ms 线性回落到当前 RMS。两者取其一：**采用 transport 侧实现**（`inputPeak` 送出去就是峰值包络），`MeterCanvas` 继续做显示侧的保持动画。

`outputRms/outputPeak` 固定 `-96` 且 `outputValid: false`；界面显示 `—`（R5-4）。

### 6.6 Gamma 加解密（DFU）

```
加密（前 min(len,8192) 字节，按 4 字节一组）：
  for i: c[i] = nibbleSwap(p[i] ^ keyByte[i % 4]) + 0xA3   (mod 256)
  keyByte = [0x63, 0xBB, 0x9C, 0x1C]（KEY = 0x1C9CBB63 的小端字节）
解密：p[i] = nibbleSwap(c[i] - 0xA3) ^ keyByte[i % 4]
```
本轮已用出厂包验证：`gammaDecrypt(cipher)` 的首 8 字节 = `B8 41 00 20 65 42 00 00`（`SP=0x200041B8`、`Reset=0x00004265`），`sum32LittleEndianWords(plain) = 0x4E0621AF`。

### 6.7 DFU 进度权重

`percent = 5·(entering|probing 完成?1:0) + 5·(probe 成功?1:0) + 85·(已发块数 / 总块数) + 5·(settling+verifying 完成?1:0)`，取整到 0…100。
