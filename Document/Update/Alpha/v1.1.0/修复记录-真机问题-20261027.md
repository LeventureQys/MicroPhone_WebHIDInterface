## 1. 问题 1 + 5：写 Flash 卡顿 / 偶发「断连」

### 1.1 根因（主机侧视角）

真机写参数后，固件把参数落 Flash；写 Flash 期间主循环不响应 USB（首刷记录 §3 已确认 USB 中断仍活、主循环停摆）。主机侧原来的三个时间参数会叠加放大这个问题：

1. `ParamSession` 所有请求共用 `requestTimeoutMs = 500`：写 ACK 被 Flash 延迟超过 500 ms 就判超时；
2. 超时后按 `requestRetries = 2` 重发**同一条写**：重发又触发一次落盘，越调越卡；
3. `WebHidTransport` 入站看门狗只看"2 s 没有 IN 报告"：落 Flash 的静默被当成拔线，直接 `error` → 界面回到演示数据（用户看到的"断连"）。

### 1.2 修复

| 改动 | 值 / 行为 | 为什么 |
|---|---|---|
| `TIMING.writeTimeoutMs` | **3000 ms** | 写 ACK 单独等，覆盖一次 4 KB 扇区擦除 + 页写的最坏耗时；读/轮询仍 500/200 ms |
| `TIMING.writeRetries` | **1** | 写超时最多重发 1 次；校验错/地址错仍按 `requestRetries = 2`（设备活着，只是帧坏了） |
| `TIMING.writeSettleMs` | **600 ms** | 写回执后暂停电平轮询，别在落 Flash 窗口里塞请求 |
| `TIMING.writeGraceMs` | **8000 ms** | 从最后一次写帧算起，设备静默这么久不算掉线；真实拔线仍由 HID `disconnect` 事件立即上报 |
| `ParamSession.writeActivityWithin(ms)` | 新公开方法 | 通道层据此判断"静默是不是正在落 Flash" |
| `ParamSession.retryLimitFor()` | 写 + 超时 → `writeRetries`；其余 → `requestRetries` | 不再让"落 Flash 慢"触发写重发风暴 |
| `WebHidTransport._checkWatchdog()` | 同时看本地写时刻与会话写帧时刻 | 覆盖排队与重发，宽限内只重新排下一拍 |
| `WebHidTransport.suspend()` 期间 `disconnect` | 忽略 | DFU 期间设备复位重枚举是预期动作，不能把升级通道拆掉 |

### 1.3 边界

- **不能消除固件侧音频卡顿本身**：Flash 写期间 DSP/音频是否断，取决于固件是否把擦写等待放进 RAM 或关中断。主机侧只能保证"不误判掉线、不重发落盘、不在写 Flash 时添乱"。
- 若真机仍然断连：先看诊断卡 `timeouts`/`retries`。`retries` 明显上涨 = 设备落 Flash 慢；错误来自 HID `disconnect` = 物理断开/设备复位，另查固件。

## 2. 问题 4：DFU 进 Bootloader 后接不上

### 2.1 原来的流程（错在哪）

```
App 模式：0x10 写 0x1008=1 → 等 ACK
        ↓
设备约 200 ms 后复位，1–3 s 重新枚举成 Bootloader（旧 HIDDevice 失效）
        ↓
主机（修复前）：仍拿旧句柄发 SigmaBus 信息帧 → 3 次探测全超时 → probeFailed
        ↓
用户重开上位机：attach() 先做参数全量回读 → Bootloader 不说 Modbus → 失败
        → transport 被 dispose、预检拿不到型号 → 选包被拒 → 无法救砖
```

### 2.2 修复后的流程

```
App 模式：0x10 写 0x1008=1 → 等 ACK
        ↓
DfuSession.reconnect → DeviceLink.awaitReenumeration()
        → session.refresh() 轮询新句柄（同 deviceId 优先，id 漂移按 VID/PID 找）
        → session.openDevice(newId) → WebHidTransport.reopen(newHandle)
        → 再发信息帧（此时才可能收到 0x03）
        ↓
逐块写入 → 0x05 → settling
        ↓
resumeAfterDfu：同样先 awaitReenumeration() 再 transport.resume()
        → 全量回读 → 版本比对
```

如果是"升级中断后重开上位机"：

1. 设备停在 Bootloader（每次复位都留在那里，见 DFU 协议 §2.2）；
2. 用户点「打开设备」→ `attach()` 参数同步失败 → `_failSync()`：
   - **保留** transport 与入站监听；
   - `store.sync = 'error'`；
   - 设备页错误框显示"设备没有回应参数同步，可能停在升级模式；可直接打开固件升级继续"；
3. 用户打开固件抽屉 → 选包 → `preflight` 在 `deviceModelCode() === null` 时**放行**；
4. `start()` 发 `0x1008=1` 无人应答（Bootloader 不认 Modbus）→ 直接发信息帧 → 设备回到升级流程。

### 2.3 具体改动

| 文件 | 改动 |
|---|---|
| `device/webhid-transport.ts` | `device` 改为私有可变 + getter；新增 `reopen(handle)`：摘旧监听、dispose 参数会话、换句柄、重挂入站监听，**不建会话/不回读**（Bootloader 不说 Modbus）；`open()` 拆成 `_bindDevice()` + `_startSession()`，`resume()` 在会话为空时补建；`_fail()` 在句柄仍开时保留监听 |
| `device/link.ts` | 新增 `awaitReenumeration()`：`refresh()` + `_findReplacement()` + `transport.reopen()`，窗口 8 s、间隔 200 ms；`resumeAfterDfu()` 先重枚举再 `resume()`；`attach()` 参数同步失败走 `_failSync()` 保通道；`_handleDrop()` 在 `status === 'dfu'` 或 `_attaching` 时不动通道 |
| `device/dfu/session.ts` | `DfuError.kind` 增 `reenumerate`；`DfuSessionOptions.reconnect` 在 EnterDfu ACK 后、信息帧前调用；失败派发 `reenumerate` 且不发信息帧；`preflight` 对 `deviceModelCode() === null` 放行；`dfuSettleTimeoutMs` 10 s → 20 s |
| `device/dfu/controller.ts` | 把 `link.awaitReenumeration()` 接进 `reconnect`；`FirmwareLink` 增可选 `awaitReenumeration?()` |
| `device/webhid/types.ts` | `WebHidErrorCode` 增 `'sync'` |
| `ui/views/device-view.ts` | 错误框补链路层错误（`_failSync` 的 `sync`）；订阅 `link.onChange` |
| `i18n/{zh,en}.ts` | `device.error.sync`、`device.warn.bootloader`、`fw.error.reenumerate` |

### 2.4 真机复测注意

- 首次进 DFU：点开始后，界面应出现"进入升级模式"并短暂等待（重枚举），**不应**立刻 `probeFailed`；
- 若仍然失败，看诊断卡：
  - 有 `EnterDfu 没有 ACK` + `reenumerate` → 设备没重新出现（USB 复位/驱动/VID-PID 变化）；
  - 有 `DFU info 探测超时` → 句柄已换但 Bootloader 不回状态帧，查固件；
- 救砖路径：设备停在 Bootloader 时，设备页「打开」应显示参数同步失败但**设备行仍是已打开**，固件抽屉可选包。

- 现状：主机每 20 ms 轮询 `0x2057`（`ParamSession.pollTick`），同时兼容设备用 `0x10` 主动推 `0x2057`（`handlePush` → `onLevel`）；
- 用户明确"暂时不加，上报时间久显示效果不好"，本轮**没有**新增固件上报路径；

## 6. 风险与未解决

1. **真机重枚举的句柄形态未验证**：假设 `getDevices()` 在复位后返回新的 `HIDDevice`，且 Bootloader 的 VID/PID 与 App 一致（真机联调报告如此记录）。若固件改了 VID/PID，`_findReplacement()` 的 VID/PID 回退也找不到，需要更新匹配规则。
2. **拿不到型号就放行**：把型号校验交给 Bootloader 的 Flash 信息区。首刷记录里该信息区为空（`JYM001` 包会被 `INFO_ERR` 拒绝），所以救砖仍可能卡在固件侧；主机侧已不再提前拒绝，至少能看到设备返回的 `0x01`。
3. **写 ACK 丢失的歧义**：写超时只重发 1 次（避免反复落盘）。若两次 ACK 都丢，设备侧可能已经写入但主机报失败；重连回读或再调一次即可对齐。协议没有请求序号，主机无法区分"没写进去"和"写了但 ACK 丢了"。
4. **写 Flash 的音频卡顿**：主机侧只能避免误判/重发；真正的音频断流要固件把擦写等待放进 RAM 或关中断（见首刷记录 §8）。
5. **灯光参数**：缺协议材料，未实现。
6. **没有硬件**：本轮所有结论都需真机复测确认。

## 7. 建议的真机复测顺序

1. **参数写 Flash（问题 1/5）**：连设备 → 拖一个可调参数几个来回 → 观察诊断卡 `timeouts/retries` 是否明显上涨、顶栏是否保持"已同步"；同时听耳机/录音是否卡顿。若仍断连，复制诊断日志（含最后 10 条出/入帧）回来。
2. **DFU 首次进入（问题 4 前半）**：选包 → 勾确认 → 开始；观察是否出现"进入升级模式"等待后继续出块，而不是立刻 `probeFailed`。
3. **DFU 中断恢复（问题 4 后半）**：升级失败/断电后设备停在 Bootloader → 关掉上位机重开 → 设备页点「打开」（预期参数同步失败但设备行仍打开）→ 固件抽屉选同一个包 → 开始；预期能直接发信息帧并继续。
4. **真拔线**：任意时刻拔线，预期立即"连接异常"（不等 8 s 宽限），重插后手动重连。
