## 5. 本轮发现的固件问题

按严重度排序。**协议条款出处**一栏给的是协议 1026 / 评审 v3 的条目，方便直接发给固件。

### 5.1（P0）只读与范围校验完全没做

`real2-errors.js` → `artifacts/real2/errors.json`

| 用例 | 期望（协议 §6） | 实测 |
|---|---|---|
| 写只读 `0x2023` gain.Mic = 原值 | `0x0004` | `0x0000` |
| 写只读 `0x205A` gain.Hp = 原值 | `0x0004` | `0x0000` |
| 写只读 `0x000B` 固件版本 = **7** | `0x0004` | `0x0000`，**回读 = 7**（真的落值了） |
| 写「不参与读写」`0x1000` 心跳 = 700 | `0x0004` | `0x0000`，回读 = 700 |
| 写 `0x2025` encLevel = **5**（域 0–3） | `0x0005` | `0x0000`，并回推 `0x2025 = 5` |

- 影响：`0x0004` / `0x0005` 在真机上永远不会出现，上位机的"只读"「超范围」提示只能靠本地拦截；固件侧的数据可以被任意写坏（本轮写 `0x000B=7` 已复原为 0）。
- 条款：协议 §6 映射表（评审 P1-2 建议补全 6 行）；评审 §6-Q7。

### 5.2（P0）读路径不校验地址，写路径只校验到 0x2075

| 用例 | 期望 | 实测 |
|---|---|---|
| `0x12` 读未映射 `0x9000` | `0x0005` | **回数据帧** `0x9000 = 0` |
| `0x12` 读 `0x3000`（参数表无此块） | `0x0005` | 回数据帧（0） |
| `0x12` 读 `0x2072`（参数表止于 `0x2071`） | `0x0005` | 回数据帧 |
| `0x12` 读 `0x2024 + 0x9000`（一好一坏） | `0x0005`，不回半帧 | 回整帧（含 `0x9000 = 0`） |
| `0x13` 从 `0x2070` 连读 4（越过 `0x2071`） | `0x0005` | 回数据帧 |
| `0x11` 从 `0x2070` 连写 4（越过 `0x2071`） | `0x0005` | `0x0000` |
| `0x10` 写未映射 `0x9000` | `0x0005` | ✅ `0x0005`（写路径这里是对的） |

- 结论：**写路径按块校验（0x0005）成立，读路径完全没校验**；写路径的有效上界是 `0x2075`，不是 `0x2071`。
- 条款：协议 §5 `0x12`「任一地址超出参数表回 `CP_ACK_DATA_ERR`（不回半帧数据）」；评审 P1-1。

### 5.3（P0）UnitID 失配 = 首轮 F1 的"复活"，一请求 18 条 ACK

`real2-defects.js` D1/D1b。一次 `UnitID=0x01` 的 `0x12` 读，设备回 **18 条 8 B ACK**（4 ms 一条，共约 72 ms）：

```
4 ms  00 02 00 08 00 01 39 D9 …      ACK 0x0001（设备地址错）
8 ms  00 02 00 08 00 01 39 D9 …      ACK 0x0001
12 ms 00 02 00 08 00 02 79 D8 …      ACK 0x0002（长度错 → 补位零被当成帧）
16 ms / 20 ms 0x0001                  又两条地址错
24 ms 起连续 12 条 0x0002             解析器在补位零上继续按 4 B 步进
```

- 之后发一条**合法**请求：被这串 ACK 抢答/吞掉，18 条回执全落在它头上，`0x13` 数据帧没有出现。
- 静默 200 ms 后再发：恢复正常（能自愈，但不是"一请求一应答"）。
- 对比：`UnitID = 0xFF` 时**完全静默**（0 条回执）——两种失配行为不一致。
- 根因与首轮 F1 相同：**地址错/长度错的返回路径没有消费掉整条报文（含补位）**。正常请求路径已经修好（§4.1），拒绝路径没修。
- 条款：协议 §7 `ADDR` 状态「失配则回 `CP_ACK_DEV_ADDR_ERR`」+ 评审 §3-P0-1 第 6 条「一请求一应答：不得多发、不得少发」。

### 5.4（P1）未知功能码静默不回包

`0x20`（不在 0x10–0x13 / 0x02 之内）→ **0 条回执**，之后合法请求正常。

- 违反协议 §6「下位机不得静默不回包」；评审 P1-2 建议「未知功能码回 `0x0002`」。

### 5.5（P1）`0x12` 超容量时返回 514 B 超长帧，而不是 `0x0002`

`real2-defects.js` D2：`0x12` 读 127 个地址（请求 260 B / 5 报文），设备照样组帧：

```
00 12 02 02 20 00 00 00 20 01 00 00 …     ← Len = 0x0202 = 514 B
```

- 514 B > 单帧上限 512 B（评审 P0-2），上位机 `decodeStream` 只能按 `len > 512` 丢弃 → 表现成"超时 → 3 次重试 → 链路 error"。
- 正确行为：`0x12` 单帧最多 126 个地址（504 B 数据 / 510 B 帧），超限回 `CP_ACK_LEN_ERR`。
- `0x13` 251 词那次回的是 `0x0005`（区间越界先命中），说明容量检查根本没做，只是被地址校验挡了。

### 5.6（P1）地址区间：固件用 118，参数表与上位机用 114

`real2-defects.js` D4/D5，写 `0x1111` 再回读：

| 地址 | 写回执 | 回读 | 说明 |
|---|---|---|---|
| `0x2070` / `0x2071` | `0x0000` | `0x1111` | 参数表内（114 项的最后两个） |
| `0x2072` / `0x2073` / `0x2074` / `0x2075` | `0x0000` | `0x1111` | **参数表里不存在，固件却接受并持久化** |
| `0x2076` / `0x2080` / `0x2100` / `0x2FFF` | `0x0005` | — | 越界 |

- **这就是评审 §6-Q3 的答案：固件按 `0x2000..0x2075`（118 项）实现，即协议 1026 第 175 行的数字，而不是寄存器表的 114 项 / `0x2071`。**
- 影响：固件的"越界校验"对 `0x2072..0x2075` 是漏的；若上位机误用这四个地址，不会收到 `0x0005`。
- 另有不对称：读 `0x003E`、`0x100E` 会回 `0x0005`（信息区/配置区按块校验），但读 `0x3000`/`0x9000` 却回数据——读路径的块选择没做。
- 建议：统一到 `0x2000..0x2071`（评审 P1-1 裁决），或协议正式改成 118 并同步参数表与上位机常量（`PRESET_COUNT`）。

### 5.7（P1）`0x10` 主动上报只在"写之后"回推，没有周期电平

| 场景 | 观测 |
|---|---|
| 空闲 1.5 s / 3 s | **0 条上报**（首轮 V0.0.1 是 167 ms 一条 `0x2057=0`） |
| 写 `0x2022=1` | ACK + 一条 `0x10`：`20 22 00 01`（11 ms 后） |
| 写 `0x2022=0` | ACK + `20 22 00 00` |
| `0x11` 连写 `0x2024=1,0x2025=2,0x2026=1` | ACK + 一条合并上报 `20 24 00 01 20 25 00 02`（只含变化的？见下） |
| 读 `0x2057` | 恒 0；无推送 |

- 结论：V0.0.2 把 `0x10` 上报改成了**写回显**（值变化即推），不再有周期电平推送。对界面友好（写后设备侧一致），但**电平表在真机上仍然没有数据源**（`0x2057` 抽不到或未使能）。
- 与协议 P1-4 的五条待定项对照，现在能答上两条：①推送时机 = 仅设备侧值变化（写回显）；②`0x2057` 读可用但恒 0。剩下：推送周期（电平）、能否关、与请求混排的规则、写→推竞态（本轮未观察到"写 1 推 0"的竞态，推送值与写入值一致）。
- 建议：`0x2057` 的采样通路（是否有输入源 / 是否需要使能）必须给答复，否则需求 R5-2 的 50 Hz 电平无法验收。

### 5.8（P1）设备信息区与预设默认值仍全 0（首轮 F3/F4 未修）

- `0x0000–0x003D` 62 词全 0 → 型号/设备名/固件版本/类型/VID/PID/SN/`comErrAck` 都读不出；应用只能显示 `0.0.0.0` 与「设备型号不匹配」。
- `0x2000–0x2071` 114 词全 0 → EQ 的 freq/Q 读回 0，界面曲线失真（场景只写 gain，`enable/type/freq` 一直是 0，因为"只写差异"不会替用户补齐）。
- 建议：按 `M001参数表V0.1.xlsx` G 列灌默认值并置 `0x2001 = 1`；至少先把 `0x000B–0x000E`（固件版本）、`0x0016/0x0017`（VID/PID）填上，否则后续每一轮联调都无法确认固件版本。

## 6. 应用级链路（上位机 × 真机）

### 6.1 修复前的现场（可复现）

`real-app-link.js` → `artifacts/real2/app-link.log`

```
22:54:51.887 → 00 12 00 08 20 57 61 E4          读 0x2057（20 ms 电平轮询）
22:54:51.889 → 00 13 00 0A 20 00 00 72 71 2E    读 0x2000..0x2071 (114)   ← sync 第一条
22:54:51.891 ← 00 12 00 0A 20 57 00 00 50 1B    轮询的应答，被 sync 的 0x13 认领
22:54:51.892 → 进入 error：预设回读应答不是连续读响应
```

- 第一次连接（`attach`）时的 `sync()` 成功；点「一键自检」再 `sync()` 就失败。
- 原因不在固件：`ParamSession.cancelWork()` 把**已经发到总线上**的轮询请求直接丢弃（只调 `onFail`），协议又没有请求序号，于是轮询的回包被新一轮的 `0x13` 认领，`link.ts` 判定"不是连续读响应"。
- 首轮把同类现象归因于固件假 ACK；本轮固件修好后该现象仍在，说明它还有上位机这一半。

## 7. 本轮上位机改动

### 7.1 `ParamSession` 竞态修复（`src/renderer/src/device/proto/session.ts`）

| # | 改动 | 说明 |
|---|---|---|
| S1 | `cancelWork()` → `Promise<void> \| null` | 队列/待发表照旧直接丢；**在途请求不能丢**：标记 `abandoned`，返回"等它回包或超时"的 Promise；总线空闲时返回 `null`，`sync()` 开头保持同步执行（原有 39 条用例的行为不变） |
| S2 | `Inflight` 增 `abandoned` / `drain` / `releaseDrain` | 遗弃请求的应答到达时只释放槽位、不回调 `onOk`；超时不重发 |
| S3 | `sync()` 代次 `syncGeneration` | 被新 sync 取代的旧 sync 不得再改相位、不得再派发致命错误 |
| S4 | `drainingSync` 压住轮询 | 等回包期间相位还是 `ready`，否则轮询会插到两轮之间 |
| S5 | 四个出口统一走 `releaseInflight()` | `settle` / `completeWithError` / `requestTimeout` / `failFatal` / `dispose` |

新增两条单测（`tests/unit/proto/session.test.ts`）：

1. 「在途轮询的应答不得被新 sync 的 0x13 认领」——断言轮询挂起时 sync 一条帧都不发；轮询回包后才发 `0x13`，且该回包只用来释放槽位。
2. 「在途请求超时也不重发：只释放槽位让新 sync 继续」——模拟轮询丢应答，验证超时后 sync 继续、`retries` 不增加。

### 7.2 文案纠偏

`device.alphaNotice`（中/英）原写「真机通道尚未验证」，与事实不符，改为「参数读写已在真机 M001 上跑通（2026-10-26 第二轮联调）；固件升级仍未上真机」。
