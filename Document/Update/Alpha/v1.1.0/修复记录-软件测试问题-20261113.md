## 1. 耳机音量跳动

**症状**：主界面「耳机增益」数字持续跳动。

**根因**：`0x205A`（耳机增益）/ `0x2023`（麦克风增益）是设备 ADC 检出的**实时值**，同一档位每次回读会差 1–3；`DeviceLink` 原来把每一帧回读 / `0x10` 上报原样回填 `AppStore`，界面自然跟着跳。这不是协议或映射错误，上位机也不该去写只读寄存器。

**修复**：新增 `device/gain-filter.ts` 的 `ReadonlyGainFilter`：对 `gain.Mic` / `gain.Hp` 取最近 5 次采样的**中位数**，并加 1 个单位死区；真实换档在 2–3 帧内跟上，±2 的抖动被吃掉。过滤只作用于这两个只读 id，`attach()` 时清空窗口。

**验证**：`tests/unit/gain-filter.test.ts` 4 例；`tests/unit/link.test.ts`「smooths noisy read-only gain echoes instead of jittering the display」——连续 9 帧 ±2 噪声时显示值最多变 1 次，连续 5 帧真实变化后跟上。

## 2. 频繁查询 USB 状态 / 获取描述符

**症状**：后台持续查询 USB 连接状态，并反复获取设备描述符。

**根因**：`AutoConnector` 每 1.5 s 调 `WebHidSession.probeNative()` → `getNativeDevices()`；上游 `getNativeDevices()` 会对 `navigator.hid.getDevices()` 返回的**每一台** HID（系统里的键盘、鼠标、灯效）构造 `NativeHidHandle`，而构造函数里 `computeLayout(device.collections)` 会解析报告描述符。设备没插或用户暂停时，这个动作每秒半次地空转。

**修复**：
1. `WebHidKit` 新增 `probeNative(vendorId, productId)`：只调 `navigator.hid.getDevices()`，按 VID/PID 过滤后返回 `{vendorId, productId, productName, opened}`，**不构造句柄、不读 collections/描述符**。
2. 新增 `watchNative(cb)`：订阅 `navigator.hid` 的 `connect` / `disconnect`，插拔立即触发检查（300 ms 合并，防一次插拔连发两条）。
3. `AutoConnector` 默认轮询 1.5 s → **5 s 兜底**，插拔事件可用时不再依赖轮询；退避上限 15 s → 30 s。
4. `WebHidSession.probeNative(target?)` 带 target 时走存在性探测，不带时仍列全部（单测 / 诊断）。

**验证**：`tests/unit/webhid-kit.test.ts`「probes by VID/PID without parsing descriptors…」（给 `collections` 装 getter 抛错，探测仍成功）；`tests/unit/auto-connect.test.ts`「probes only the target VID/PID…」「subscribes to USB hot-plug events and unbinds on stop」。

## 3. 频繁调音效参数把设备压死

**症状**：录音 + 放音同时快速连续拖参数，设备无回应、灯不变化、按键与旋钮失效；只能重开 app。

**根因**：`ParamSession` 的写合并是**固定 120 ms 窗口**——拖拽期间每 120 ms 仍然会出一条写帧（≈8 帧/s），而真机每次写参数都可能落 Flash（参见 `AGENTS.md` 已知坑 27）。固件在写 Flash 时主循环停摆，连续写叠加上去就把设备压死。

**修复**（`device/proto/session.ts` + `timing.ts`）：
- `writeThrottleMs` 120 → **300 ms**，并改为**尾沿触发**：每次 `write()` 都重置合并计时器。一次连续拖拽只在停手 300 ms 后出 **1 帧**（写的是最后的值）。
- 新增 `writeGapMs = 200`：一次 flush 排出多组写帧时，相邻写帧至少隔 200 ms；读请求不受这条限制。
- 新增 `writePauseAfterTimeoutMs = 1000`：写超时后暂停新的写帧 1 s，避免设备正卡在 Flash 里还被继续压。
- 原有 `writeTimeoutMs=3000` / `writeRetries=1` / `writeSettleMs=600` / `writeGraceMs=8000` 保留。

**验证**：`tests/unit/proto/session.test.ts`「waits for the user to stop before sending a write frame (trailing edge)」（60 次 ×16 ms 的拖拽期间 0 帧，停手后 1 帧且值为最后值）、「spaces consecutive write frames by writeGapMs」；原 T07 用例仍满足 ≤20 帧。`tests/unit/{transport,link}.test.ts` 的定时器推进同步到新窗口。

**真机复测待做**：本机没有 M001 硬件，无法确认"设备不再卡死"的听感/灯效表现；建议按此顺序复测：播放 440 Hz + 录音 → 连续拖 `噪声门阈值` 10 s → 观察诊断卡 `outFrames` 在拖拽期间不增长、松手后只 +1，`timeouts` 不增长。

- 音色：原声 / **人声增强**（原「人声」）/ 温暖 / 明亮 / **自定义**；删除「音乐」。

### 4.4 所有音效模块的 bypass

| 模块 | 协议使能位 | 实现 |
|---|---|---|
| 环境降噪 | `0x2024 encOnOff` | 真实使能位 |
| 压缩器 | `0x204A compEnable` | 真实使能位（开关） |
| 限制器 / 防爆音 | `0x2051 limitEnable` | 真实使能位（开关） |
| 噪声门 | 无 | `setBypass('noisegate')`：阈值钉 -91 dB，快照恢复 |

## 5. 三分频动态无法调节

**上位机侧核查**：用 CDP 在真实界面上对 `drc3.fc1` / `drc3.low.threshold` 做**真实鼠标拖拽**，数值从 -80 → -19 正常联动滑杆、数字框、读数；`恢复推荐分频点` 能写 1000/3000 并清掉冲突。因此 "无法调节" 不是控件失效。

**真正的问题线索**：
1. 参数表默认 `fc1 = fc2 = 50`，中频段宽度为 0；界面原来只在 `fc1 > fc2` 标冲突，相等时看不出来。现在相等也标黄并给出推荐值。
2. 更根本的可能是固件：第六轮联调（`真机联调报告-第六轮.md` §7.1）发现固件预设初始化整体右移 2 字——`0x205D..0x2073` 等于参数表 `0x205B..0x2071` 的默认值序列（23/23）。协议读写按地址无偏移，但**若 DSP 按结构体取值，`0x205B` 起的 NoiseGate/3BandDrc 参数会落到错误字段**，听感自然"调不动"。

**结论**：上位机已经保证"能写、能回读、退化分频有提示、可旁通 A/B"；是否真正改变 DSP 输出要等固件确认结构体偏移并复测。这是固件侧问题，不在本次上位机代码可修范围。
