## 3. 42 项参数读写对账（本轮核心）

### 3.1 界面显示值 ⇄ 寄存器真值：42/42

方法：`real6-app-params.js` 抓 `[data-param]` 的 `.pfield-value` / 只读 `strong` / 开关 `checked` / 分段 `is-active`，加上工作台的 `enc.OnOff`/`enc.Level`；`real6-compare.mjs` 用 `registers.ts` 的 `findRegister/findRaw/fromRaw` 把裸 HID 原始值反算成 `values.ts:formatValue()` 应有的文本，逐项比对。

```
ok 42/42
EQ 7 段：全部一致
```

抽样（设备原始值 → 界面）：

| 参数 | 地址 | raw | 界面 |
|---|---|---|---|
| `gain.Mic`（只读） | `0x2023` | 97 | 97 |
| `gain.Hp`（只读） | `0x205A` | 34 | 34 |
| `noisegate.threshold_db` | `0x205B` | 1 | -90 dB |
| `comp.Threshold` | `0x204C` | 580 | -2 dB |
| `comp.Attack` | `0x204D` | 5 | 0.0005 s |
| `drc3.fc1` / `fc2` | `0x2061/0x2062` | 6 / 60 | 6 Hz / 60 Hz |
| `drc3.low.ratio` | `0x2067` | 3 | 1（表下限夹紧） |

> 这证明**上位机的标定、量化、夹紧、格式化与协议回读链路没有偏差**；参数“看起来不对”只可能来自设备里的原始值本身（§7）。

### 3.2 逐项写入 → 裸 HID 回读：40/40

### 6.1 拒绝路径：从“喷 17 条”到“3 条 / 1 条”

|---|---|---|
| UnitID `0x01` 的合法读 | **3** | `0x0001, 0x0001, 0x0003` |
| 坏 CRC | **1** | `0x0003` |
| Len 错（`0x13` 数据段 3 B） | **1** | `0x0002` |
| 未知功能码 `0x20` | **0（静默）** | — |

> 坏 CRC / 长度错已经规范；UnitID 失配仍会追加 2 条（其中一条还是 `0x0003` 校验错），说明拒绝后仍继续按 4 B 步进吃补位零。协议 §6“不得静默不回包”对未知功能码仍未满足。

### 6.2 只读 / 范围校验

| 用例 | 期望 | 实测 |
|---|---|---|
| 写只读 `0x2023 = 50` | `ACK 0x0004` | `ACK 0x0000`，读回 50（已还原 97） |
| 写 `0x2025 = 9`（域 0–3） | `ACK 0x0005` | `ACK 0x0000`，读回 9（已还原） |
| 写 `0x2025 = 999`（历史） | `ACK 0x0005` | 同上（未复测，行为一致） |
| 写未知 `0x3000 = 1`（历史） | `ACK 0x0005` | `ACK 0x0005` ✅ |

### 6.3 读容量与地址边界

| 请求 | 结果 |
|---|---|
| `0x13 0x2000×114` | ✅ 238 B |
| `0x13 0x2000×118` | ✅ 246 B，118 词 |
| `0x13` ×119 / 120 / 126 | ✅ `ACK 0x0005`（1 条，4–11 ms） |
| `0x12` 118 地址 | ✅ 504 B，49 ms，118 对 |
| `0x12` 119 / 124 / 125 / 126 / 127 地址 | ✅ 全部 `ACK 0x0005`（本轮未出现“5 报文无回执”） |
| `0x13 0x2076` | ✅ `ACK 0x0005`（3/3） |
| `0x13 0x3000` | ❌ `0x13` 数据帧，值在 8193 / 288 间跳（3/3） |
| `0x13 0x4000` | ❌ 同上（288 / 8193） |

> `0x2072..0x2075` 仍按“118 词区间”合法应答（`0x0005,0x0001,0,0`），与参数表 114 项的口径冲突仍在；上位机按 114 读，不受影响。

### 6.4 非法高地址

`0x3000/0x4000` 读回 `30 00 00 01 20 01` / `30 00 00 01 01 20` 这类未初始化内存，值随采样变化；写同一地址会正确回 `0x0005`。说明读路径的地址校验只覆盖了区间一端。

### 6.5 `0x10` 设备→主机上报语义（V0.0.4 复测）

| 操作 | 回执 | 500 ms 内后续 |
|---|---|---|
| 写 `0x2024`（值变化） | `ACK 0x0000` | **`0x10` 上报**：`20 24 00 00 20 25 00 02`（固定带 `0x2024`+`0x2025` 两个字） |
| 写 `0x205B`（其它参数） | `ACK 0x0000` | 无 |
| 再写 `0x2024` 同值（无变化） | `ACK 0x0000` | 无 |

> 与第三轮结论一致：**只在 `0x2024`/`0x2025` 真的变化时**，设备在 ACK 后推一条 `0x10`，内容是这两个字；与写是否用 `0x10`/`0x11` 无关。上位机 `_applyEcho` 按“镜像更新、不回写”处理，不形成写环。

### 6.6 电平

- `0x2057` 20 次采样全 0；8 s 空闲零 `0x10` 上报。
- 应用侧 20 ms 轮询正常（60 s 内约 2800 帧），但拿不到非 0 值，清单 ⑨（电平标定）仍无法做。

### 6.7 写时延

裸 HID 写 `0x205D` 5 次：ACK 3 / 4 / 6 / 3 / 4 ms；恢复写 5 ms。写后立即读 `0x2057` 均 1 帧返回。与第四轮 4–11 ms 同量级，**无可观测的 Flash 停顿**。

## 7. 固件侧发现（本轮新增，按影响排序）

### 7.1 预设初始化整体右移 2 字（P1，需固件确认）

V0.0.4 初始化预设区时，`0x205D–0x2073` 的 23 个字**恰好等于参数表 `0x205B–0x2071` 的默认值序列**，且 `0x2072/0x2073 = 5/1` 正是表尾 `0x2070/0x2071` 的默认值：

```
表默认 0x205B..0x2071: 0, 50, 5, 5, 6, 60, 50, 50, 0, 0, 1, 5, 1, 0, 0, 1, 5, 1, 0, 0, 1, 5, 1
设备   0x205D..0x2073: 0, 50, 5, 5, 6, 60, 50, 50, 0, 0, 1, 5, 1, 0, 0, 1, 5, 1, 0, 0, 1, 5, 1   ✅ 23/23
设备   0x205B/0x205C: 1, 1（不在该序列里）
```

含义：从 `0x205B` 起，**固件的默认值布局比参数表/协议地址映射少/多了 2 个字（4 B）**。可能原因：固件的预设结构体在 NoiseGate 前多了两个字段，或初始化循环的起始地址错位。读/写路径按地址是无偏移的（§3.2 全部命中），但**固件 DSP 侧是否也按同一偏移取字段无法从协议侧确认**——如果 DSP 用结构体覆盖，`0x205B` 起的阈值/比率/DRC 参数会被解释到错误的字段。请固件方核对结构体布局与协议地址表。

> 本轮已把设备按参数表默认值还原（§11），还原后 `0x205B=0, 0x205C=50, …, 0x2071=1`，`0x2072..0x2075` 未被写。

### 7.2 预设名按小端存储（P2）

`0x2002–0x2009`（预设名 8 词）字节序与信息区相反：

| 读法 | 结果 |
|---|---|
| 按高字节在前（`decodeAsciiWords`，与信息区一致） | `aFtcron1yrPsete1 ` |
| 按低字节在前 | `Factory1 Preset 1` |

上位机当前不读这 8 个词，所以界面无影响；但同一份协议里信息区用大端、预设名用小端，属于数据格式不一致，建议固件统一。

### 7.3 EQ 默认频点与参数表不一致（P2）

V0.0.4 初始化后的 EQ 前 7 段频点：`20 / 20000 / 215 / 1000 / 1000 / 2000 / 10000`；参数表默认：`50 / 20000 / 215 / 1000 / 2000 / 5000 / 10000`。第 1/5/6 段不同（20 vs 50、1000 vs 2000、2000 vs 5000），导致**出厂 EQ 曲线与表内默认曲线不一致**（第 1 段 HPF 20 Hz、第 5/6 段偏低）。同批还发现 `eq.mode` 设备 0 vs 表默认 1。已在本轮收尾还原成表内默认。

### 7.4 校验和与 SN（P3）

- `0x2000` 预设校验和 = 0（`validFlag=1` 但校验和为 0）；若固件用校验和判定预设有效性，需要确认 0 是否为合法值。
- SN 区 `0xFFFF`，界面显示“—”（第五轮遗留，未变）。

## 10. 给固件方的清单（按优先级）

1. **P0/P1：核对预设结构体与协议地址映射的 2 字偏移**（§7.1）。证据是 23 个连续默认值完全对齐 `0x205D = 表 0x205B`。若 DSP 侧也按该结构体取值，`0x205B` 起的 NoiseGate/DRC 参数会整体错位——这比“默认值不一致”严重。
2. **P1：只读与范围校验**（§6.2）：`0x2023` 只读、`0x2025` 域 0–3，目前都接受任意值。
3. **P1：UnitID 失配只回一条 ACK**（§6.1）。现在 3 条（`0x0001,0x0001,0x0003`），且拒绝后仍继续解析补位零。
4. **P1：读地址校验**（§6.4）：`0x3000/0x4000` 回未初始化内存，应按 `0x0005` 拒绝（`0x2076` 已做对，可复用）。
5. **P1：`0x2057` 电平**：给真实电平值或周期上报，否则上位机电平表无法标定。
6. **P2：EQ 默认频点对齐参数表**（§7.3）：50 / 20000 / 215 / 1000 / 2000 / 5000 / 10000，`eq.mode=1`。
7. **P2：预设名统一大端**（§7.2），与信息区一致。
8. **P2：未知功能码不得静默**（§6.1）；`0x2072..0x2075` 与参数表 114 项口径二选一并写进协议。
9. **P3：SN 区写入**；确认 `0x2000` 校验和 = 0 是否为合法状态。

## 12. 下一步建议

1. **固件优先**确认 §7.1 的 2 字偏移（结构体 vs 协议地址表），这是本轮唯一可能影响实际音频处理的发现；

5. DFU 按用户安排另行安排（本轮已排除）。
