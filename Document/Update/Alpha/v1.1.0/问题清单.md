### 置顶区（阶段阻塞，需用户决策）

#### Q1. Bootloader 到底跑哪套协议：SigmaBus（`0xC4` + 累加和 + `CMD 0x0B`）还是已升级成新参数协议
- 问题描述：需求 §1.2 与 §12-Q1 把这条列为"v1.1.0 最大的集成风险"。两套帧格式不兼容（帧首、`Len` 字节序、校验算法、命令码全不同），而参数与 DFU 共用同一条 HID 通道（OUT `0x51` / IN `0x11`）。决定 `device/dfu/**` 的全部实现方向，也决定"进入 DFU 后要不要切换编解码"。
- 建议方案：**按现有 Bootloader 源码的旧协议（SigmaBus `0xC4` + SigmaCRC 累加取反加一 + `CMD 0x0B`）实现 DFU**。证据：DFU 协议材料由 `Document/Protocol/Bootloader/` 源码推导，且我用出厂包逐帧复算通过（84 帧 SigmaCRC 全对、`FwLength 20984`、`FwChecksum 0x4E0621AF`、Gamma 解密后向量表 `SP=0x200041B8 / Reset=0x00004265`，见 §3.3）。同时把镜像层（解析/校验和/Gamma/上界）与帧层（`device/dfu/frame.ts`）拆开，帧层用策略接口，将来换协议只需新增一个实现。
- 备选方案：
  1. **按新参数协议实现 DFU**（假定 Bootloader 已重构为 `0x10–0x13` + Modbus CRC-16）：若固件方已升级，这是唯一正确解；若没升级，发出去的帧设备一个字节都不认，R6 全部作废。
  2. **两套都实现，运行时探测**：进入 DFU 后用两条探测帧（参数协议 `0x12` 读 `0x0000`、SigmaBus `CMD 0x0B` 信息帧）各试一次，谁有回执用谁。代价：多一个 SubStage 与一套对拍用例，收益是消除 Q1 的返工风险。
- 风险预警：选错会在 M4 阶段整体返工（帧层约 300 行 + 单测），镜像/校验和/Gamma/上界/会话状态机可复用。若选"贴源码实现"，而量产固件其实已换协议，症状是"进 DFU 后收不到任何回执"，需要在真机联调清单里写清这条排查路径。
- 置信度：88%
- 分区归属：置顶区
- 归入原因：技术路线分歧，答错即 M4 全部返工。

#### Q2. 参数范围/默认值以哪张表为准：寄存器表 vs 效果器参数范围表（两表在 Gain 与全部默认值上冲突）
- 问题描述：`AGENTS.md` §Reference truth 写"参数数值与范围以 `Document/Protocol/效果器参数范围.xlsx` 为准"，`domain/params.ts:35-80` 的 36 项就是照它写的；而需求 R2-2 写"地址与标定式的唯一真值源是寄存器表"，C5 写"不信任本地默认值，寄存器表默认值与《效果器参数范围.xlsx》大面积冲突"。实读两表后冲突点：
  | 参数 | 效果器参数范围表（现 `params.ts`） | 寄存器表（raw → 实际） |
  |---|---|---|
  | `0x2023` MIC Gain | −27…36 dB，默认 5，只读 | `[0,100]`，默认 100，直通，只读 |
  | `0x205A` HP Gain | −40…0 dB，默认 0，只读 | `[0,100]`，默认 100，直通，只读 |
  | NoiseGate threshold | 默认 −70，步进 1 | raw 0 → −91 |
  | NoiseGate ratio | 默认 0.333 | raw 50 → 0.05 |
  | NoiseGate attack/release | 10 / 200 ms | 5 / 5 ms |
  | NoiseGate knee/hp_freq | 12 dB / 150 Hz | 6 dB / 60 Hz |
  | Comp/Limit Threshold | 默认 −60 dB | raw 580 → **−2.0 dB** |
  | 3BandDrc fc1/fc2 | 1000 / 3000 Hz | 50 / 50 Hz |
  | 3BandDrc preGain/attack/release/ratio | 1.28 / 10 / 20 / 10 | 0 / 1 / 5 / 1（raw 1 → 0.1，**越界**） |
  | ENC Level | 默认 1 | 默认 0 |
  | EQ 7 段 Type/Freq/Q | 全 PEAK，20/63/200/632/2000/6325/20000，Q 0.7 | 4/3/0/0/0/0/0，50/20000/215/1000/2000/5000/10000，Q 0.7/0.7/0.8/1.5/1.0/1.0/0.7 |
  除 Gain 两行外，两表**范围与步进一致**，差异集中在"默认值"与"量纲"。默认值又直接影响界面首屏显示与 `tests/unit/params.test.ts` / `defaults.ts` 的断言。
- 建议方案：**地址 / 标定 / 权限 / 默认值一律以寄存器表为准（含 `G` 列原始值），范围与步进两表一致处直接沿用；Gain 两栏按寄存器表 `[0,100]` 百分比实现，单位留空并在界面标注"量纲待定"（需求 §12-Q7）**。默认值只作"未连接时的兜底显示"，连接后一律用回读值覆盖（C5/C4）。`效果器参数范围.xlsx` 降级为"字段中文标签与单位的参考"，不再进代码。
- 备选方案：
  1. **保留现值（dB 语义）**：`gain.Mic`/`gain.Hp` 仍按 −27…36 dB 显示，收益是不动 v1.0.0 的界面与测试；代价是写 `0x2023` 时无法给出可靠换算（固件未给 raw↔dB 映射），联调必然暴露。
  2. **Gain 显示原始值 0…100 但文案写 dB**：自相矛盾，不可取。
- 风险预警：选建议方案会让首屏参数默认值与 v1.0.0 截图不一致（例如 Comp Threshold 从 −60 变 −2.0、3BandDrc fc1 从 1000 变 50），`params.test.ts` 与 `defaults.ts` 需同步改；若固件后续给出真实量纲，只需改 `domain/registers.ts` 一处标定式与 `params.ts` 的 unit 字段。选备选 1 则 R2-1"表格由代码生成并与寄存器表逐行比对一致"无法通过。
- 置信度：88%
- 分区归属：置顶区
- 归入原因：两份"权威材料"直接冲突，且改动覆盖全部 36 项参数的默认值与 2 项范围、影响界面首屏。

#### Q3. 未连接设备时界面显示什么：Mock 演示数据（现状）还是空态
- 问题描述：v1.0.0 的渲染入口 `src/renderer/src/main.ts` 直接 `new MockTransport({ scene: 'speech', hz: 50 })`，双击运行就在电平表上画假波形、参数区显示本地默认值。v1.1.0 起参数是设备真值，若不连设备仍显示默认值 → 用户会误以为参数已同步（需求 R5-5 只约束了电平，没约束参数）。同时 `src/renderer/src/domain/state.ts:70` 用 `DEFAULT_PARAMS` 填充初始参数，没有任何"是否已同步"的状态位。
- 建议方案：**保留 Mock 为默认通道，但把"数据来源"显式化**：顶栏状态胶囊显示三态（`演示数据` / `同步中` / `已连接`），参数卡与电平卡在非连接态加统一标记；设备抽屉连接成功后参数全部改用回读值、标记消失；通道与桥接地址写入 `localStorage`，下次启动沿用。
- 备选方案：
  1. **默认空态**：未连接时电平画"—"、参数控件禁用，用户必须连接后才能操作。代价：双击体验变差，v1.0.0 的演示资产（`artifacts/shot-*.png`）与场景/EQ 编辑功能失去默认可玩性。
  2. **仅默认 Mock 但不加标记**：等于保留现状，风险最高，不建议。
- 风险预警：若验收方在未连接状态下截图参数与电平，会误判为"已联调"。标记必须进入验收项（验收文档会写"未连接态必须出现演示数据标记"）。
- 置信度：85%
- 分区归属：置顶区
- 归入原因：产品可见行为，且涉及"假装已同步"的诚信风险。

#### Q4. 本版本是否提供"保存到设备"入口（`0x1004 SaveNo`）：需求 §2.2 与 §12-Q6 互相矛盾
- 问题描述：需求 §2.2 把"预设管理（保存/加载/删除，`0x1004`–`0x1009`）"明确列为**不纳入**，理由是"语义在寄存器表里全是查看注释"；但 §12-Q6 的临时处置写"按'立即生效但需 SaveNo 落盘'假设，界面提供显式保存入口"。两者不能同时满足：提供保存入口就等于实现 `0x1004` 的写路径与槽位语义（`0x1002/0x1003/0x1004` 三者关系未定义）。
- 建议方案：**本版本不提供保存入口**，按 §2.2 的明确排除执行；在高级参数抽屉与设备抽屉固定展示一句"写入立即生效；掉电是否保留取决于固件（待确认）"，并把 Q6 保留在遗留问题里等固件答复。
- 备选方案：
  1. **提供"保存到设备"按钮**，写 `0x1004 = 1`（固定槽位 1）：成本低，但 `SaveNo` 的取值语义（要传 N 还是写 1 触发）没有依据，写错可能覆盖用户现有预设；且没有 `0x1005 LoadNo` 回读验证手段，无法证明保存成功。
  2. **本轮按"立即生效"实现，另加一条只读回显 `0x2000` 校验和**：能观察到设备侧校验和是否变化，但仍不能确认落盘。
- 风险预警：不做的后果是"用户改完参数、断电后是否还在"在这版无法承诺；若产品要求"参数能存住"，需在 v1.1.1 补一个 SubStage（按钮 + 写帧 + 回读确认 + 失败文案）。做的后果是可能写坏设备上已有预设槽位（无恢复手段）。
- 置信度：80%
- 分区归属：置顶区
- 归入原因：需求文档内部冲突，且方向影响范围与数据安全。

#### S2. 自决方案：寄存器表用一张结构化表承载，`params.ts` 由它派生
- 问题描述：需求 R2-1 要求"附录 B 的表格由代码生成并与寄存器表逐行比对一致"，而 R2-2 又要求 `domain/params.ts` 只做映射、不重复定义范围。
- 自决方案：新增 `domain/registers.ts`，导出 `REGISTERS: readonly RegisterSpec[]`（`addr`、`name`（中文）、`field`（协议英文名）、`region`（`info|config|preset`）、`min`、`max`、`step`、`unit`、`defaultRaw`、`access`（`r|rw|none`）、`scale`（`{ kind: 'passthrough'|'linear'; a: number; b: number }`，`value = param * a + b`）、`module`（可空）），覆盖设备信息 62 项、设备配置 14 项、当前预设 114 项（含 EQ 35 项、预设名 32 项、保留项 2 项）。`domain/params.ts` 从 `REGISTERS` 里筛出"面向 UI 的参数"生成 `PARAMS`（42 项，见 S3），并保留 `ParamSpec` 现有字段形状以不破坏 `ui/**`。

#### S5. 自决方案：`Transport` 契约扩展（只增不改）
- 问题描述：现有 `device/transport.ts` 只有 `open/close/write/onLevels/onStateChange`，无法表达"回读值"、"同步态"、"参数错误码"、"诊断事件"，R3/R4/R5/R8 都需要。

#### S6. 自决方案：电平表增加"不可用"态

- 风险：`tests/unit/controls.test.ts`/截图取证里"空态"外观变化，需重出 `artifacts/shot-console*.png`。

#### S7. 自决方案：`AppStore` 增加同步门控与本地只读错误
- 问题描述：`state.ts:88-100` 的 `setParam` 对只读参数是**静默 return**（不派发任何事件），R2-3 要求"产生 `readOnly` 本地错误，不发帧"；另外 C4 要求"回读完成前不写"。
- 自决方案：`AppState` 增加 `sync: 'idle'|'syncing'|'ready'|'error'`；`setParam` 对 `spec.readonly` 派发 `LOCAL_ERROR_EVENT`（`detail = { kind: 'readOnly', id }`）后 return；`sync !== 'ready'` 且 transport 为设备通道时，`setParam` 只更新本地并推入待发队列（由 transport 在回读后 flush），不直接 `write`。新增 `applyEcho(id, value)` 用于设备回读回填（不再触发 `write`）。
- 自决理由：门控放在 store（状态唯一写入口）而不是 transport，保持"store 是唯一写入口"的既有架构约束。置信度 90%。
- 风险：`AppState` 加字段会波及 `state.test.ts` 的快照断言与 `shell` 的 `mock` 判定；待发队列与 transport 内部队列存在两处排队，需在设计文档里写清"store 排队只覆盖回读窗口，之后一律直接交给 transport 队列"。

#### S8. 自决方案：写请求合并与节流参数
- 问题描述：R3-6 要求"拖拽 2 秒产生 120 次写调用，实际出帧 ≤ 20 条"。
- 自决方案：transport 内部两级合并——(1) **同 id 节流窗口 100 ms**，窗口内只保留最后值；(2) 窗口结束时把同一批里地址相邻（差 1）且同属预设区的写合并成一条 `0x11` 连续写，其余用 `0x10` 随机写（一条帧最多 2 组 `(Addr,Val)`，因 `Len ≤ 512`）。120 次/2 s → 20 个窗口 → 最多 20 条帧，满足 R3-6。
- 自决理由：100 ms 窗口 ÷ 2 s = 20，正好卡在验收上限，不好再宽；`0x11` 合并减少帧数但不改变语义。置信度 90%。
- 风险：若设备侧对连续写的"数目"处理有 bug（未验证），合并会放大损失；设计里保留"合并开关"，出问题可退化为逐条 `0x10`。

#### S9. 自决方案：电平轮询与写请求共享一条串行队列，轮询可让位
- 问题描述：R5-3 要求轮询低优先级、200 ms 未回即跳过本次；R3-2 要求严格一问一答。
- 自决方案：transport 只有一个在途请求槽；队列按优先级分两段（写段/轮询段），写段非空时轮询帧不入队；轮询帧如果已经等过一次 20 ms 周期未轮到发送则直接丢弃本次（不堆积）。轮询超时 200 ms 计一次"跳过"并计入诊断统计，不触发重试与 `error`；写请求超时 500 ms、重试 2 次后进 `error`。
- 自决理由：同一时间只有一个未完成请求（ACK 不带 Func/地址，无法配对，见参数协议 §附A.4），必须共用队列才安全。置信度 92%。
- 风险：设备侧若把"一次读电平"算作需要心跳保活的业务，可能有隐性耦合（Q3 心跳待确认），本版本不做心跳，靠联调清单兜。

#### S10. 自决方案：虚拟下位机的进程形态与"模式切换"模拟方式
- 问题描述：需求 R7 要求侧车订阅桥接输出事件并注入回执；但桥接（`third_party/web_hid_utils`）实测事实是：`_route_api` 对 `/api/devices` 只允许 `GET`，**没有**动态注册/注销设备的 HTTP 路由，因此无法从设备侧制造一次真实的 USB 重枚举（`hid.disconnect` 事件触发不了）。
- 自决方案：
  - 进程形态：`tools/vdevice/run.mjs` 是唯一入口，内部 `spawn` Python 桥（`python -m virtual_hid serve --config tools/vdevice/profiles/mic-m001.json --port 8765`，`PYTHONPATH` 指向子模块 `packages/virtual-hid`）+ 在本进程内跑协议侧车；Ctrl+C 与异常退出都清理子进程（R10-3）。
  - 侧车：Node ESM（`.mjs`，零依赖，Node 24 自带 `WebSocket`），连 `ws://127.0.0.1:8765/ws`，订阅 `hid.outputReport`（实测**无条件广播**，与 `loopback` 无关，见 §3.4），用 `device.setInput`（WS op 或 `POST /api/devices/{id}/input`）注入 `0x11` 回执。
  - 模式切换：侧车内部维护 `mode: 'app' | 'bootloader'` 两套组帧器；收到参数协议 `0x10` 写 `0x1008=1` 后先把 `0x02 ACK 0x0000` 发完，再切到 bootloader 模式（此后只认 SigmaBus 帧，参数协议帧一律不答）；收到 DFU `0x05` 成功后再切回 `app` 模式并把固件版本寄存器改为镜像里的 `Ver`。上位机侧用"参数帧不再被应答 + DFU 信息帧得到 `0x03`"判定切换完成，**不等待真实断线**。
  - 掉线注入：侧车进入 `silent` 状态（对所有帧不答）持续 N ms，上位机靠超时进 `error` 并重连；恢复后重新应答。
- 自决理由：这是在本仓"不改子模块"约束下唯一能同时满足 R7 与 R6 观测判据的做法；`hid.outputReport` 的无条件广播（源码 `server.py:646-652`）恰好允许 `loopback: none`，避免需求 D.1 警告的"假回执"陷阱。置信度 88%。
- 风险：验收边界必须写清"不模拟真实 USB 重枚举"（R4-4/R6-4 的"设备断开重枚举"以"帧层失联→恢复"表达）；若将来桥接加了设备增删接口，可升级为真实重枚举，只需改 run.mjs。

#### S11. 自决方案：升级包只接受厂商帧序列格式
- 问题描述：出厂包格式是 `EnterDfu(11B) + Info(90B) + N×BlockFrame(265B/末块 257B)`（§3.3 实测），而我们手上没有"裸 App 镜像"样例，也没有 App 侧 `ModelCode`（本目录 Bootloader 是 `P0JY04`/`PD100UGen2`，寄存器表机型码是 `JYM001`，两处不一致）。
- 自决方案：`device/dfu/image.ts` 只解析厂商帧序列格式：逐帧校验 `0xC4` 帧首、`LEN` 与实长一致、SigmaCRC、`ADDR=0`、`CMD=0x0B`、`DFU_CMD ∈ {0x02,0x03}`；`FwLength` 必须等于全部块数据总长且 4 字节对齐；对**明文**（对前 8 KB 逆 Gamma）重算 32 位小端字累加，必须等于 `FwChecksum`；`ModelCode ≠ "Bootld"` 时 `FwLength ≤ 0x30000`，`= "Bootld"` 时 `≤ 0x8000`。发送时**重新编码每一帧**，并与包内原帧做逐字节比对断言（不一致即视为编码 bug，直接拒绝升级）。裸镜像与未知格式一律拒绝并给出明确文案。
- 自决理由：黄金样本可逐字节对拍（§3.3），这比"信任包内容"强得多，也顺带成为帧编码器的回归基准。置信度 92%。
- 风险：若客户实际拿到的是裸 `.bin`，本版本无法直接刷；设计里保留 `image.ts` 的 `wrapRawImage()` 预留口但本版本不接线，并在设备抽屉文案说明"仅支持厂商升级包"。

#### S12. 自决方案：DFU 会话的超时与重来策略取值
- 问题描述：需求 C7 要求歧义态整轮重来；DFU 协议给的是设备侧看门狗（块间 1000 ms、帧内 300 ms）。
- 自决方案：主机侧取值——单块等回执超时 **1500 ms**（设备看门狗 1000 ms + 桥接往返余量）；`EnterDfu` 后探测窗口 **1500 ms**，最多 3 次（含重插提示）；整轮重来上限 **3 次**；收尾等"设备恢复应答"最长 **10 s**（设备侧约 2 s 复位 + 重枚举），期间不发任何帧；收到 `0x02 CODE_ERR`/超时一律整轮重来，绝不补发单块。
- 自决理由：所有数字都可注入（`device/proto/timing.ts`），单测能用假时钟精确断言边界。置信度 90%。
- 风险：真机若 4 KB 扇区擦除耗时超过 1500 ms，首块会误判超时并触发整轮重来（DFU 材料 §5.2 提到进度会"卡住几十到上百毫秒"，未给上界）；联调清单第 1 条就是实测块间回执延迟。

#### S13. 自决方案：诊断面板与配置的位置
- 问题描述：需求 R8 说"设置抽屉或设备抽屉里新增诊断分区，不新增路由"；R9-2 要求白名单可配置。
- 自决方案：设备抽屉新增第 5 张卡「诊断」（默认折叠 `<details>`）：帧日志（环形 500 条，方向/时间/hex/解析字段，CRI 错标红）、统计行（出/入帧、CRC 错、超时、重试、丢弃、队列深度）、自检按钮（回读全量 → 写一个可回滚参数（`0x2025` 降噪强度）→ 读回比对）、复制按钮。设置抽屉新增「通道」卡：桥接地址、是否自动连接、真机白名单（`Usage Page:Usage` 默认 `FF01:01`，可选 VID/PID 列表）、诊断日志上限。配置存 `localStorage['micstudio.channel']`。

- 风险：设备抽屉现有 4 张卡改为 5 张，`device-view` 布局在 `medium` 尺寸下会变长（可滚动），截图取证需更新。

## 3. 取证附录（本轮实测，供后续阶段零上下文引用）

### 3.1 参数协议附录 A.6 的 8 条 CRC 向量
按 `CRC-16(0xA001, init 0xFFFF, 低字节先发)` 逐条复算，**8/8 全部通过**，含 `00 02 00 08 00 05 → 38 1A`。

### 3.2 参数协议附录 A.7 的 11 条业务帧
逐帧复算 `Len`（16 位大端）与 CRC，**11/11 全部通过**；另复算文档正文散落的 7 条帧（`ACK` 五个错误码帧、写只读帧 `00 10 00 0A 20 23 00 01 F2 01`、`0x13` 与 `0x12` 响应帧）同样全部通过。结论：需求文档附录可直接作为单测黄金向量。

### 3.3 出厂黄金包（DFU）
文件：`Document/Protocol/Bootloader/Tools/Py/INNO SoftEmbe_Bootloader(PD100UGen2) MCU [内部使用].bin`，21 823 B。
逐帧解析结果与 DFU 协议材料 §C.5/§7 完全一致：**84 帧**（`11 + 90 + 81×265 + 257`），全部 SigmaCRC 通过；`ModelCode = "Bootld"`、`ModelName = "000000"`、`Ver = 0.0.0`、`FwLength = 20984`、`FwChecksum = 0x4E0621AF`；82 块数据（81×256 + 248）。
加解密与校验和实测：
- 加密（前 8192 B，4 字节粒度）：`c = nibbleSwap(p ^ keyByte[i mod 4]) + 0xA3 (mod 256)`，`key = 0x1C9CBB63`，`keyByte` 按小端取（`0x63,0xBB,0x9C,0x1C`）。
- 解密为其逆：`p = nibbleSwap(c - 0xA3) ^ keyByte[i mod 4]`；8192 之后字节保持明文（`plain[8192..] === cipher[8192..]` 已断言）。
- 校验和 `sum32` = 32 位小端字累加，对**明文**算：得 `0x4E0621AF`，与信息帧一致；对密文算得 `0x1390B00A`（与 DFU 材料 §7 记录一致），不符。
- 解密后向量表：`SP = 0x200041B8`、`Reset = 0x00004265`，与 DFU 材料交叉验证一致。
