## 0. 一句话目标

**在没有真机的前提下，把「参数双向读写」和「固件升级」两条链路做到可联调**：协议帧、寄存器映射、错误处理、升级流程全部落地，并用一套**虚拟下位机**跑通全流程与全部故障分支；真机到位只需改一个通道开关。

---

## 1. 背景

### 1.1 v1.0.0 的边界

v1.0.0 交付的是界面层：`AppStore` 是状态唯一写入口，参数改动经 `Transport` 出站，实际用的是 `MockTransport`（50 Hz 假电平 + 假回执）。HID 侧只留了接口没有实现：

| 文件 | 现状 |
|---|---|
| `device/protocol.ts` | `HID_REPORT_ID = 0`、`MAX_PAYLOAD = 64`，注释写明「映射待确认，不写编码函数」 |
| `device/webhid-transport.ts` | 所有方法 `throw` `WEBHID_NOT_IMPLEMENTED` |
| `device/webhid/session.ts` | 能发现/开关设备、能解码报告，但**不做参数 ↔ 字节映射**，因此不实现 `Transport` |
| `domain/params.ts` | 36 项标量，只有范围和默认值，**没有寄存器地址** |

也就是说：从 UI 到字节的整条链路是断的。

### 1.2 v1.1.0 面对的硬件事实

三份协议材料把断点补齐了，但也暴露出一个必须先决策的结构性事实：

**参数和固件升级跑在两套不同的帧格式上。**

| 维度 | 参数协议（MainApp） | DFU 协议（Bootloader） |
|---|---|---|
| 帧首 | 无起始符，直接 `UnitID` | `0xC4` |
| 长度 | `Len` 16 位**大端**，在 Func 之后，计入 CRC | `Len` 16 位**小端**，在帧首后 |
| 字节序 | **大端** | **小端** |
| 校验 | Modbus **CRC-16**(0xA001) | **16 位累加取反加一** |
| 命令 | `0x10/0x11/0x12/0x13` + `0x02` | `0x0B` 下的 `0x02/0x03` |
| 单帧上限 | 512 B | 1022 B |

两套协议**共用同一条 HID 通道**（OUT `0x51` / IN `0x11`，见 §3.2）。所以上位机必须有两套帧编解码，且在进 DFU 后**切换到另一套**。

→ 这是 v1.1.0 最大的集成风险，§12-Q1 必须先答复。

### 1.3 成功判据

1. 无真机，用虚拟下位机能完整走完：连设备 → 回读全部参数 → 改任一参数 → 下发 → 设备侧确认 → 界面一致。
2. 无真机，用虚拟下位机能完整走完：选固件包 → 校验 → 进 DFU → 分块写入 → 成功 → 设备重启 → 验证新固件在跑。
3. 上述两条链路的**故障分支**全部有可复现的注入用例与明确行为（丢帧、超时、校验错、只读写、超范围、掉线、升级中断电）。
4. 真机到位后，只改「通道 = native」+ 确认 report ID，不再改协议代码。

## 3. 恒定事实

### 3.1 术语

| 术语 | 含义 |
|---|---|
| 参数协议 | MainApp 运行的 Modbus 风格私有协议，读写寄存器 |
| DFU 协议 | Bootloader 运行的 SigmaBus 帧，写固件 |
| 寄存器 / 参数 | 参数协议的最小寻址单位，16 位，地址 `0x0000`–`0xFFFF` |
| 原始值 `param` | 寄存器里存的整数 |
| 实际值 `value` | 经标定式换算后的工程量（dB / Hz / s …） |
| 虚拟下位机 | 本仓自研的设备侧模拟器，跑在独立进程，经桥接与界面交互 |

### 3.2 传输层恒定事实

| 项 | 值 | 依据 |
|---|---|---|
| 报文长度 | 64 字节（report ID + 63 载荷） | DFU 协议 §1.1 报告描述符实测 |
| OUT report ID | `0x51`，63 B 载荷 | 同上 |
| IN report ID | `0x11`，63 B 载荷 | 同上 |
| 字节流语义 | 每个 `0x51` 报文除 report ID 外全部字节追加进接收 FIFO；**帧可跨报文** | Bootloader `drv_uac10_hid.c:193` |
| 尾部填充 | 不足一帧时补 `0x00`，接收方按 `Len` 判定帧尾 | 参数协议 §一 |
| 单帧上限（参数） | 512 B | 参数协议 §一 |
| vendor 集合 | Usage Page `0xFF01`、Usage `0x01` | 报告描述符实测 |

> ⚠ **待确认（§12-Q2）**：参数协议原文没有定义 report ID。上表沿用 Bootloader 侧实测值，理由是两端共用同一份 `drv_uac10` 库与同一套描述符。**实现上必须把 report ID 做成可配置项**，不能硬编码。

### 3.3 地址分区

| 区段 | 范围 | 大小 | 权限 | 本版本用途 |
|---|---|---|---|---|
| 设备信息 | `0x0000`–`0x003D` | 62 | 只读 | 型号码、设备名、固件版本、VID/PID、SN |
| 设备配置 | `0x1000`–`0x100D` | 14 | 读写 | 仅用 `0x1008` 进 DFU、`0x1006` 通讯错误回读 |
| 当前预设 | `0x2000`–`0x2071` | 114 | 读写 | 全部音效参数、电平、监听 |

## 5. 详细需求

### R1 参数协议帧编解码

**要求**

1. 纯函数实现，不依赖 DOM / WebHID / 定时器，可在 Node 与浏览器同时运行。
2. 帧结构严格按附录 A：`UnitID + Func + LenHi + LenLo + Data + CRCLo + CRCHi`。
3. `Len = Data字节数 + 6`，16 位**大端**，计入 CRC。
4. CRC-16：多项式 `0xA001`、初值 `0xFFFF`、无最终异或、**低字节先发**；覆盖 `UnitID..Data` 末字节。
5. 提供 4 个功能码的编码器与解码器：`0x10` 随机写、`0x11` 连续写、`0x12` 随机读、`0x13` 连续读；`0x02` ACK。
6. 解码必须是**流式**的：输入一个字节序列，输出零到多帧 + 剩余未消费字节；不假设一报文一帧。
7. 解码失败要能区分：CRC 错、`Len` 与容量不符、`Len < 6`、未知功能码。

**验收标准**

| # | 标准 |
|---|---|
| R1-1 | 附录 A.6 的 8 条 CRC 自检向量全部通过（含 `00 02 00 08 00 05` → `38 1A`） |
| R1-2 | 附录 A.7 的 6 条业务帧逐字节一致 |
| R1-3 | 把一条 300 B 的 `0x13` 响应拆成 5 个 63 B 报文切片后重新喂入，解出与原帧完全一致 |
| R1-4 | 在帧中间插入随机字节、截断帧、错 CRC，均返回明确错误码且不抛异常 |
| R1-5 | 单测覆盖 `Len` 边界：`Len = 6`（空 Data）、`Len = 512`、`Len = 513`（应拒） |

---

### R2 参数寄存器映射与标定

**要求**

1. `ParamSpec` 扩展为「寄存器规格」：新增 `addr`、`scale`（`param ↔ value` 双向换算）、`readonly`、`block`（所属区段）。
2. 地址与标定式的**唯一真值源**是寄存器表；`domain/params.ts` 只做映射，不重复定义范围。
3. 标定必须双向：`toRaw(value)` 与 `fromRaw(param)`，且 `fromRaw(toRaw(v)) === v` 在步进内成立（受整数取整影响，允许 ±1 原始值误差）。
4. 3BandDrc 段序按寄存器表：**低(`<fc1`) → 高(`>fc2`) → 中(`fc1<freq<fc2`)**，地址 `0x2063`–`0x2071` 顺序展开。现存 `params.ts` 的 low→mid→high 顺序必须改。
5. EQ 只映射 7 段（`0x2027`–`0x2049`）。第 8–14 段无寄存器，改为**本地默认值 + 只读展示**，并在界面上标注「设备不回报」，不得出现在任何读写请求里。
6. 只读参数（`0x2023` MIC Gain、`0x205A` 监听音量）不生成写请求；界面禁用写控件。
7. 保留「未实现/保留」寄存器（`0x2052`、`0x2056`，范围与步进均为 0）的占位，标为不读写。
8. 默认值来源分层：**UI 兜底默认值**取寄存器表 `G` 列（原始值）；**运行时真值**一律来自 R4 回读。

**验收标准**

| # | 标准 |
|---|---|
| R2-1 | 附录 B 的表格由代码生成并与寄存器表逐行比对一致（地址/范围/步进/单位/权限/标定式） |
| R2-2 | 每个可写参数的 `toRaw(fromRaw(x)) == x` 在范围全区间抽样 100 点成立 |
| R2-3 | 写只读参数被拦截，产生 `readOnly` 本地错误，**不发帧** |
| R2-4 | EQ 段 8–14 在任何出站帧里都不出现（用帧日志断言） |
| R2-5 | 3BandDrc 三个区段的地址与寄存器表一致：low `0x2063`、high `0x2068`、mid `0x206D` |

### R3 参数读写传输层

**要求**

1. `WebHidTransport` 由桩变为真实实现，契约不变：`open/close/write/onLevels/onStateChange`，`kind = 'webhid'`。
2. **一问一答，严格串行**：同一时刻只有一个未完成请求。理由：ACK 帧不带原 Func/地址，多请求并行无法配对。
3. 写请求合并：连续拖拽产生的同名参数写，节流窗口内的中间值丢弃，只发最后值；不同参数的写合并成一条 `0x11` 连续写（同地址段内且相邻时）。
4. 超时：单请求默认 500 ms，超时计一次失败并重试，最多 2 次；三次失败后进入 `error` 状态并停止发送，直到用户手动重连。
5. 收到 `0x02` ACK 时按 `CP_ACK` 映射错误：`0x0004` → 只读、`0x0005` → 超范围、`0x0003` → 校验错、`0x0001` → 地址错、`0x0002` → 长度错。
6. 校验错与地址错**自动重发一次**；只读/超范围**不重发**（重发一定还错）。
7. 所有出站帧与入站帧都要能被诊断面板观测（R8），但默认不落盘。
8. 队列深度与丢帧统计要可查，供 R8 展示。

**验收标准**

| # | 标准 |
|---|---|
| R3-1 | 连续写 10 个参数，虚拟设备侧收到的帧序为严格串行，无交叉 |
| R3-2 | 注入 30% 丢帧，最终所有写都成功（靠重试），且没有重复写入产生的不一致 |
| R3-3 | 写只读参数，全程只有 **0 帧**发出（本地拦截） |
| R3-4 | 设备返回 `CP_ACK_DATA_ERR`，界面出现「超范围」提示且不回滚已显示的值以外的东西 |
| R3-5 | 连续 3 次超时后 `state` 变 `error`，且有明确文案 |
| R3-6 | 拖拽 2 秒产生 120 次写调用，实际出帧 ≤ 20 条（合并生效） |

### R4 上电同步与回读

**要求**

1. 连接成功后**必须**回读，不得用本地默认值填充界面。
2. 回读策略：用 `0x13` 连续读整段 `0x2000`–`0x2071`（114 个寄存器，响应 `4 + 2×114 = 232` B，单帧内完成），一次拿全。
3. 同时读 `0x0000`–`0x0005`（型号码 + 设备名）与 `0x000B`–`0x000E`（固件版本 `X.Y.Z.Type`），用于设备摘要与兼容性判断。
4. 型号码与界面期望不一致时**不阻断**连接，但在设备页显示警告（防止把 M001 的参数当成别的机型调）。
5. `0x2000` 校验和与 `0x2001` 有效标志：回读后校验一次，不匹配只告警不阻断（算法待确认，§12-Q5）。
6. 回读期间界面显示「同步中」，禁止发出任何写请求。
7. 断线重连后重新全量回读，不假设设备状态未变。
8. **块读的快照不等于预设内容**：整段里 `0x2057`（MIC 电平）是**实时量**，不是预设字段。回读结果里必须把它丢弃，电平只由 R5 的轮询通道提供；否则会出现「保存预设时把某一瞬间的电平存进去」这类错误。

**验收标准**

| # | 标准 |
|---|---|
| R4-1 | 虚拟设备写入一组已知参数后连接，界面显示值与虚拟设备寄存器完全一致（逐项断言） |
| R4-2 | 回读完成前任何写请求都被排队而非丢弃，回读完成后按序发出 |
| R4-3 | 型号码不匹配时出现警告但连接正常 |
| R4-4 | 断线重连后若虚拟设备已改值，界面同步到新值 |
| R4-5 | 回读结果中 `0x2057` 的值被丢弃，电平显示只跟随 R5 轮询 |

### R5 实时电平采集

**要求**

1. 数据源只有 `0x2057`（MIC 电平，`0..256`，无 dBFS 标定）。
2. 采集方式：周期轮询 `0x12` 单地址读，周期 20 ms（50 Hz），与现有 `MockTransport` 的出帧频率一致。
3. 轮询用**低优先级**：队列里有写请求时轮询让位；一轮询在途超过 200 ms 未回则跳过本次，不排队堆积。
4. 映射到现有 `LevelFrame`：
   - `inputRms` = `param / 256` 归一后线性映射到 `-96..0`（dBFS 假设），**换算公式待确认（§12-Q4）**；
   - `inputPeak` = 同一值的峰值保持（本地 300 ms 衰减）；
   - `outputRms` / `outputPeak` = **不可用**，填 `-96`，界面显示为「—」而非 0；
   - `t` = 本地接收时间戳。
5. 界面必须能区分「电平不可用」与「电平为静音」，不得把无数据画成满格或归零不动。

**验收标准**

| # | 标准 |
|---|---|
| R5-1 | 虚拟设备把 `0x2057` 设为 0/128/256，界面电平分别落在下/中/上三段 |
| R5-2 | 出帧频率实测 50 Hz ±10%，且写参数时轮询自动降频而不阻塞写 |
| R5-3 | 断线后电平在 1 秒内停止更新并置为不可用态 |
| R5-4 | 输出电平两栏显示「—」，不显示 0 dBFS |

### R6 固件升级（DFU）

协议细节见附录 C。本节只定义上位机行为。

**要求**

1. **镜像预检（本地，离线）**：解析升级包 → 校验帧结构 → 校验 `FwLength` 与数据总长一致 → 校验 `FwChecksum`（32 位小端字累加，**对明文算**）→ 校验 `ModelCode` 与设备匹配 → 校验长度上界。
2. **长度上界硬校验**（设备侧完全没有）：
   - `ModelCode ≠ "Bootld"`：`FwLength ≤ 0x30000`（192 KB）
   - `ModelCode = "Bootld"`：`FwLength ≤ 0x8000`（32 KB）
   - 超界直接拒绝，**不发进入 DFU 的命令**。
3. **进入 DFU**：写 `0x1008 = 1`（参数协议）→ 等 ACK → 等设备断开重枚举 → 用 DFU 协议探测。
4. **协议切换**：进入 DFU 后切换到附录 C 的 SigmaBus 帧；退出时切回参数协议。
5. **流控**：一块一个回执，块大小固定 256 B，**不得**流水线连发。
6. **歧义态处理**：块超时或收到 `0x02 CODE_ERR` 时，**不补发单块**，改为重发信息帧从第 0 块整轮重来；重来次数上限 3 次。
7. **收尾**：收到 `0x05` 后停止发送，等 USB 断开 → 重枚举 → 用参数协议回读固件版本 `0x000B`–`0x000D`，确认版本已变。
8. **不可取消确认**：发信息帧前必须让用户明确确认「升级中断后设备将停留在升级模式，需重新升级才能恢复」。
9. **严禁暴露给用户**的路径：`ModelCode = "Bootld"` 的 Bootloader 自升级（出厂包标注「内部使用」，掉电即需 SWD）。
10. 升级期间：阻止睡眠、拦截退出、禁用设备页其它操作。

### R7 虚拟下位机（无设备开发的核心）

**要求**

1. **不改动 `third_party/web_hid_utils`**（子模块只读）。模拟器是本仓新增的独立进程。
2. 组成：
   - **设备配置文件**：一份与真机描述符**逐字节一致**的虚拟 HID 设备（附录 D.1）；

   - 字节流组帧（参数协议 + DFU 协议各一套）；
   - 参数协议的 4 个功能码 + ACK；

6. 虚拟下位机必须能模拟**两种模式**：MainApp 模式（参数协议）与 Bootloader 模式（DFU 协议），并能响应"进入 DFU"发生模式切换（断开→重连→换协议）。

## 6. 跨需求约束（实现时必须遵守）

| # | 约束 | 理由 |

| C1 | 出站帧一律发满 63 B 载荷，尾部补 `0x00` | 解析器靠 `Len` 判定帧尾；补 `0xC4`/`0xFF` 会产生假帧 |

## 8. 附录 A — 参数协议规格

### A.1 帧结构

```
偏移  字段      长度  计入CRC  说明
 0    UnitID     1      ✓     设备地址，本版本固定 0x00
 1    Func       1      ✓     功能码
 2    LenHi      1      ✓     整帧总长高字节（大端）
 3    LenLo      1      ✓     整帧总长低字节
 4..  Data      可变    ✓     大端
 N-2  CRCLo      1      —     CRC-16 低字节（先发）
 N-1  CRCHi      1      —     CRC-16 高字节
```

`Len = Data字节数 + 6`（6 = UnitID + Func + LenHi + LenLo + CRCLo + CRCHi）。

### A.2 功能码

| Func | 名称 | 方向 | 数据段 |
|---|---|---|---|
| `0x10` | 随机写参数 | 写 | `(AddrHi,AddrLo,ValHi,ValLo)` 重复，`len % 4 == 0` |
| `0x11` | 连续写参数 | 写 | `首址(2B), 数目(2B), 数据(2B×N)`，`len == 4 + 2N` |
| `0x12` | 随机读参数 | 读 | 请求：地址序列（`len % 2 == 0`，最多 126 个）；响应：`(Addr,Val)` 序列，`len = 4N` |
| `0x13` | 连续读参数 | 读 | 请求：`首址(2B), 数目(2B)`（N ≤ 251）；响应：`首址(2B), 数目(2B), 数据(2B×N)` |
| `0x02` | ACK / 响应 | 双向 | 2 字节 `CP_ACK` 错误码（大端） |

### A.3 错误码

| 码 | 宏 | 含义 | 上位机动作 |
|---|---|---|---|
| `0x0000` | `CP_ACK_NO_ERR` | 成功 | 完成请求 |
| `0x0001` | `CP_ACK_DEV_ADDR_ERR` | 地址不匹配 | 重发一次 |
| `0x0002` | `CP_ACK_LEN_ERR` | 长度错误 | 不重发，报实现 bug |
| `0x0003` | `CP_ACK_CHECKSUM_ERR` | CRC 错 | 重发一次 |
| `0x0004` | `CP_ACK_READ_ONLY_ERR` | 参数只读 | 不重发，回滚界面 |
| `0x0005` | `CP_ACK_DATA_ERR` | 值超范围 | 不重发，提示 |

### A.4 字符串字段

按 16 位字**大端**存放，每字高字节是前一个字符，右补 `0x00`。
例：`"JY"` → `0x4A59`；机型码 `JYM001` → `0x4A59 0x4D30 0x3031`。

### A.5 标定式速查

| 标定式 | 适用 |
|---|---|
| 直通 `value = param` | 开关、强度档位、EQ Enable/Type/Freq、NoiseGate attack/release/knee/hp_freq、3BandDrc fc1/fc2/attackTime/releaseTime、监听开关、电平 |
| `value = param × 0.1 − 32` | EQ Gain（`0x202A` 起每段 +5） |
| `value = param / 10` | EQ Q、Comp/Limit MakeUpGain/Rate/KneeWidth、3BandDrc ratio |
| `value = (param − 600) / 10` | Comp/Limit Threshold |
| `value = param / 10000` | Comp/Limit Attack、Release（s） |
| `value = param − 91` | NoiseGate `threshold_db` |
| `value = param / 1000` | NoiseGate `ratio` |
| `value = param / 100` | 3BandDrc `preGain` |
| `value = (param − 800) / 10` | 3BandDrc `threshold` |

## 10. 附录 C — DFU 协议摘要

> 完整解析见 `Document/Protocol/JAT1821-Bootloader-DFU协议解析.md`。此处只列实现必需项。

### C.1 帧结构（SigmaBus）

```
0    0xC4 固定
1-2  Len 16 位小端 = 整帧字节数（含 CRC）
3    Addr，必须 0x00
4    Cmd，DFU 固定 0x0B
5    DFU_CMD（0x01 状态 / 0x02 信息 / 0x03 数据块）
6    CHIP_ID，固定 0x00（设备不校验）
7..  Data
末2   SigmaCRC，16 位累加取反加一，低字节先发
```

### C.2 命令与帧长

| 方向 | DFU_CMD | 帧长 | 说明 |
|---|---|---|---|
| 主机 → 设备 | `0x02` | 90 B | 81 B 载荷：ModelCode(6) + ModelName(64) + Ver(3) + Length(4) + Checksum(4) |
| 主机 → 设备 | `0x03` | 265 B | 2 B 头 + 256 B 数据块 |
| 设备 → 主机 | `0x01` | 10 B | `status` |

`status`：`0x01` 信息错 / `0x02` 代码错或超时 / `0x03` 继续 / `0x04` 升级失败 / `0x05` 成功。

### C.3 流控与超时

| 项 | 值 |
|---|---|
| HID OUT 环形缓冲 | 4 × 64 B（写指针不检查读指针，满了覆盖） |
| 一块所需报告数 | 5（63+63+63+63+13） |
| 块间看门狗 | 1000 ms |
| 帧内字节超时 | 300 ms |
| 收尾延时 | 约 2 s 后复位 |

### C.4 镜像处理

```
明文镜像
 → 32 位小端字累加校验和（对明文算）
 → Gamma 加密前 8 KB（key 0x1C9CBB63，4 字节粒度，nibble swap + 0xA3）
 → 切 256 B 块
```

### C.5 黄金样本实测（出厂 Bootloader 包）

| 项 | 值 |
|---|---|
| 总大小 | 21 823 B |
| 帧序列 | `EnterDfu(11)` + `Info(90)` + `81×265` + `257` |
| ModelCode | `"Bootld"` |
| `FwLength` | 20 984 |
| `FwChecksum` | `0x4E0621AF` |
| 全帧 CRC | 84 帧全部通过 |
| 解密后向量表 | `SP = 0x200041B8`、`Reset = 0x00004265` |

## 11. 附录 D — 虚拟下位机规格

### D.1 虚拟 HID 设备

与真机描述符**逐字节一致**（取自 `drv_uac10_lib.c`）：

```
06 01 FF 09 01 A1 01 A1 02 15 80 25 7F 75 08 85 10 95 0F 09 44 81 22
85 11 95 3F 09 45 81 22 85 50 95 0F 09 54 91 22 85 51 95 3F 09 55 91 22
C0 C0
```

| 项 | 值 |
|---|---|
| 设备 id | `mic-m001` |
| 产品名 | `Virtual MIC M001` |
| report（本版本使用） | input `0x11` 63 B、output `0x51` 63 B |
| report（声明但不用） | input `0x10` 15 B、output `0x50` 15 B |
| 回环 | `none`（必须关：真机不回环） |
| 运行 | `virtual_hid serve --config <本仓 profile> --port 8765` |

> ⚠ 回环必须关闭。开启会让主机自己发的帧原样回到自己的接收路径，产生"设备已回答"的假象，掩盖真正的协议错误。

### D.2 协议侧车（signal path）

```
界面 ──sendReport(0x51)──► virtual_hid ──event hid.outputReport──► 侧车
                              ▲                                      │
                              └────── device.setInput(0x11) ◄─────────┘
                                  (event hid.inputReport 推给已 open 的会话)
```

要点：

1. 侧车只监听 `hid.outputReport`，用 `device.setInput` 回写，**不使用 loopback**。
2. `device.setInput` 走 `raw` base64 路径，不经过字段钳制（描述符 `Logical Min −128`，字段路径会把字节钳到有符号区间）。
3. `hid.inputReport` 只推给已 `hid.open` 的会话，所以界面必须先打开设备。
4. 侧车维护一个字节流累积器，两种协议各一套组帧器；模式切换时清空累积器（防止跨模式残留半帧）。

### D.3 故障注入配置

```jsonc
{
  "deviceId": "mic-m001",
  "mode": "app",                    // app | bootloader
  "faults": [
    { "on": { "func": 0x12, "nth": 3 },  "action": "drop" },
    { "on": { "func": 0x13 },            "action": "delay", "ms": 200 },
    { "on": { "dfuCmd": 0x03, "nth": 40 },"action": "dropAck" },
    { "on": { "dfuCmd": 0x03, "nth": 60 },"action": "powerLoss" },
    { "on": { "any": true, "nth": 10 },  "action": "crcError" }
  ],
  "level": { "pattern": "sine", "periodMs": 2000, "min": 0, "max": 256 }
}
```

动作集：`drop`、`delay`、`dropAck`、`crcError`、`ackError(code)`、`powerLoss`、`disconnect`、`sticky`（帧粘连）。
