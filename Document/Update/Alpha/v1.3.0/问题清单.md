## 置顶区（阶段阻塞，需用户决策）

### Q1. MVP 的落地形态：「独立侧车 + 可选桥」还是「应用内最小面板」

- **问题描述**：需求写"这个上位机软件暂时只需要一个MVP实现，不需要融入整个软件中"——这句话有两种互斥读法，交付物差别极大：
  1. **语音能力独立**（Python 侧车跑完整条链路，宿主软件只留一个可选命令入口）；
  2. **宿主软件里最小集成**（新增一个抽屉/面板，唤起与播报在里面，指令直接进 `AppStore`）。

  现状事实：KWS 与 ASR 的成熟生态在 Python（`sherpa-onnx` 只有 py/js/cxx 绑定，py 最完整；本机已实测 pip 装得上）；宿主是 Electron + electron-vite + vitest，`src/` 里没有任何原生依赖；仓库已有"工具不进产品构建"的先例（`tools/vdevice`、`tools/dfu`、`scripts/probes`）。宿主侧唯一写入口是 `AppStore.setParam/setBands/setTone/setActiveScene`（`src/renderer/src/domain/state.ts:196`、`:254`、`:268`、`:275`），跨进程需要新增 IPC（当前 `src/shared/types.ts` 只有 HID 白名单/平台信息/DFU 三条通道）。

- **建议方案（A）**：**独立侧车 + 可选桥，分两步走**
  - 第一步（M1–M5，本版主线）：`tools/voice/` 一个 Python 侧车跑「采集 → 唤醒 → VAD 端点 → ASR → 意图 → VoiceCommand」，落地靶按 dry-run（只写日志）→ 虚拟下位机控制面（`POST /control/registers`，见 `tools/vdevice/sidecar.mjs:792`）→ 真机的顺序验证；**`src/` 一行不改**，`pnpm run test` / `typecheck` 保持全绿。
  - 第二步（M8，可选）：确认准确率达标后，再加"应用内最小面板 + 主进程 spawn 侧车 + IPC 命令通道"，这时命令直接 `AppStore.setParam`，用户才真正"喊一嗓子就改参数"。
  - 理由：先把算法链路的不确定性（语义映射、数值归属、误唤醒）在**零产品副作用**的条件下解决，再谈集成；反之若先做集成，每次调 prompt/规则表都要重打包 Electron。

- **备选方案**：
  1. **B：直接做应用内最小面板**——新抽屉 + `main` 进程 spawn 侧车 + `preload` 新增 IPC + 渲染层执行器。收益是演示效果最好（点开就能喊）；代价是要同时解决三进程接线、侧车生命周期、portable 打包时的模型分发（模型 1.5 GB 级），且与"不需要融入整个软件"的字面要求相悖。
  2. **C：只做离线 CLI**（`wav → 文本 → JSON`，不接任何设备）。收益是最快看到结构化输出；代价是**无法证明"上位机软件可以进行操作"**，验收缺少最关键的一环。

- **风险预警**：选 A 的代价是本期结束时"语音改参数"只在虚拟下位机/探针上闭环，真机上还得再走 M8；同时需要一个执行器把工程量换算成原始值（`registers.ts` 的 `toRaw`）并做回读校验，约 2–3 天。选 B 的代价是：一旦侧车要进 portable 包，1.03 GB 的 GGUF + 228 MB 的 ASR 模型会让安装包从 ~200 MB 涨到 1.5 GB 以上，且 NSIS/SAC 那条已知坑（AGENTS.md 坑 14/29）会重新出现。选 C 则等于不交付"能操作上位机"这件事。

- **置信度**：60%
- **分区归属**：置顶区
- **归入原因**：交付物形态整体不同，答错等于阶段二到阶段四全部返工。

### Q2. 意图层的粒度：语义动作 / 参数直出 / 混合

- **问题描述**：LLM 到底输出什么，决定了 schema、规则表、训练数据与验收指标。

  实测证据（调研 §2.4）：Qwen3-1.7B 在约束解码下 **24/24 次输出都是合法 JSON**，也就是说"格式"根本不是问题；问题是**语义与数值**——同一次测试里：
  - 显式数值能对上（「第 6 段 4.5 分贝」→ `eq.band6.gain=4.5`，「压缩阈值 -18」→ 对）；
  - 自由描述会崩（「人声太闷，把高频提上来」→ 编出 6 条无关动作）；
  - 0.6B 连参数都错（「4.5 分贝」→ `input.gain=45`）。

  而"亮一点应该是几 dB""闷要削哪一段"属于**音频工程常识**，不属于小模型的先验——需求里你自己也点到了这一点（"可能这个小模型先验的知识不足以调参"）。

- **建议方案（A）：语义动作层 + 确定性规则表（推荐）**
  - LLM 只填槽：`target`（brightness / warmth / lowEnd / muddiness / sibilance / noiseFloor / compression / loudness / clarity / tone / scene / rgb …）+ `direction`（up / down / off / on）+ `strength`（slight / medium / strong）+ 可选 `explicit`（用户明确说了数值时才填）。
  - **所有 dB / Hz / 档位由 TS 规则表算出**，再经 `registers.ts` 的 `toRaw` 夹紧到寄存器真值域。模型永远不发明数字。
  - 样例（L1 = 模型输出，L2 = 交给宿主的命令）：

    ```json
    // L1 模型输出（JSON Schema 约束）
    {"v":1,"status":"ok","ops":[{"target":"brightness","direction":"up","strength":"slight"}],"say":"亮一点"}

    // L2 执行器输出（宿主可直接吃）
    {"v":1,"turn":"t-0007","writes":[{"param":"eq.band6.gain","value":2.0}],
     "bandWrites":[{"band":6,"field":"gain","value":2.0}],"say":"亮一点","undo":"t-0006"}
    ```
  - 理由：①可单测（规则表是纯函数，不需要模型在线）；②可解释（用户问"为什么改了这段"，答案是表格的一行）；③可撤销（记 delta 快照）；④训练数据可以只标"目标/方向/幅度"，标注成本与一致性都远好于标 dB。

- **备选方案**：
  1. **B：参数直出**——`{"param":"eq.band6.gain","value":4.5}`，`param` 用 GBNF 枚举 46 个 id（`domain/params.ts` 的 `id` 全表），`value` 用区间描述。实现最短（1 天），但把"多少 dB 合理"交给 1.7B，实测已出现错参数/错数量级；验收也难判对错（数值对不对没有客观标准）。
  2. **C：混合**——语义动作为主，仅当用户说了明确数值/明确参数名时才走直出分支。等于 A 的超集，工作量 +10%。

- **风险预警**：A 需要人工写约 40–60 条映射（1–2 天），并且**这套语义目标一旦定死，将来加参数要同步改契约、规则表、训练数据与验收用例**——缓解办法是把 `target` 定义成开放式字符串 + 规则表按键值扩展，schema 里只约束枚举集合，新增目标不改 schema 版本。若将来发现"用户说的话根本落不进这 13 个目标"（例如"我想要电台主播那种感觉"），需要允许 `target` 之外的 `preset` 回退（映射到已有 5 个场景/4 个音色）。

- **置信度**：88%
- **分区归属**：置顶区
- **归入原因**：这是"小模型任务定义"，改一次要重做 schema、规则表、评测集与（可能的）LoRA 数据，属于重大技术路线分歧。

### Q3. 模型口径：需求点名的模型不存在，按什么口径落地

- **问题描述**：需求写「一个 Qwen3.8-2B-Distill 这种较小模型」。核对结果（调研 §1）：
  - Qwen3 系列发布过 **0.6B / 1.7B / 4B / 8B / 14B / 32B / 30B-A3B / 235B-A22B**，**没有 2B**；
  - "Qwen3.8" 不是任何已发布版本号（可能是"Qwen3-8B"或"Qwen2.5"的笔误）；
  - 带 "Distill" 的知名小模型是 DeepSeek-R1-Distill-Qwen-1.5B/7B，属另一家；
  - 本机实测（同型号 CPU，`-t 14`）：1.7B Q4_K_M pp512 318 tok/s、tg128 43.5 tok/s；0.6B pp 829 / tg 111，但**语义映射质量不过关**（见 Q2）。→ **1.7B 是实用下限。**

- **建议方案（A）**：**基准 Qwen3-1.7B-GGUF Q4_K_M（1.03 GB，`unsloth/Qwen3-1.7B-GGUF`）+ llama.cpp 官方预编译 `llama-b12359-bin-win-cpu-x64.zip`（23.9 MB）**，严格 CPU 推理（`-t 14` 物理核、`--reasoning-budget 0` + `enable_thinking:false`），常驻 `llama-server`（不做每轮冷启动）。0.6B 与 4B 只做**对照档**（同一套 schema 与评测集跑一遍，写进验收报告），不进主线。
  - 理由：1.03 GB 内存、35 token 输出约 1.55 s 的实测速度，是"CPU 上能接受"与"能学会映射"的交点。

- **备选方案**：
  1. **B：直接上 Qwen3-4B Q4_K_M（2.33 GB）**——中文与常识明显更强，适合自由描述；但 CPU 上按 1.7B 的速度线性外推约 20 tok/s，35 token ≈ 1.8 s，加上前缀后整轮接近 3 s，且与宿主软件抢内存（Electron 本身 ~700 MB）。
  2. **C：推理改用 RTX 4070 SUPER**——延迟降一个数量级，但违背需求"放到 CPU 上运行"的原意；可作为**开关**保留（`--device=gpu`），默认 CPU。
  3. **D：等你自己提供一个"2B-Distill"的具体权重**——如果你手上确有一份，请给出仓库/文件名，我按它重做基线（评测集与 schema 可复用，成本 1–2 天）。

- **风险预警**：A 的自由描述能力弱（实测会编动作），必须靠 Q2 的语义层 + Q6 的规则优先兜住；如果你后面要求"什么话都能听懂"，A 会先撞墙，届时可选 B 或 C，或走 M7 微调。B 的关键风险是**延迟超出 2.5 s 预算**，需要重新谈预算。C 的风险是"CPU 上跑"这个卖点消失。

- **置信度**：85%
- **分区归属**：置顶区
- **归入原因**：模型是需求的原话，但原话指向不存在的东西；不确认就动手，等于替用户改需求。

### Q4. 唤醒词引擎：sherpa-onnx（开源）/ Porcupine（商用授权）/ 先热键

- **问题描述**：唤醒词「小唐小唐」是需求的核心触点，三条路线代价完全不同。

  已实测（调研 §2.1 / §2.2）：`sherpa-onnx` 的 `sherpa-onnx-kws-zipformer-wenetspeech-3.3M-2024-01-01`（int8 共 5.0 MB、Apache-2.0）**建模单元是拼音声母+韵母，唤醒词就是一个文本文件**，我写了 `x iǎo t áng x iǎo t áng @小唐小唐` 后：合成语音**检出 1/1**、7 条无关中文语句**误唤醒 0/7**（阳性对照已通过，排除了探针坏掉的可能）。

- **建议方案（A）**：**sherpa-onnx KWS**，关键词文件即配置（改唤醒词不用重训模型），模型 5 MB、纯 CPU、无授权与联网依赖。
- **备选方案**：
  1. **B：Picovoice Porcupine**——控制台训练自定义中文词、效果好、资源低；但需要 **AccessKey**，免费额度面向个人/非商用，**商用要买授权**（与"离线可分发"有摩擦，细节未核）。若你有 AccessKey 或愿意付费，我可以做双引擎适配（约 +2 天）。
  2. **C：先热键/按钮触发**，把唤醒词放到 M8。收益是 M1–M6 完全不碰误唤醒问题；代价是丢了"喊一声"的核心卖点，演示说服力下降。
- **风险预警**：A 的**误唤醒率与远场鲁棒性还没测**——0/7 只是抽样，正式指标需要几十分钟的噪声/对话/电视回放。若实测误唤醒偏高，缓解手段依次是：调 `keywords_threshold`（0.25→0.35）、`num_trailing_blanks`、换成 wenetspeech 的 `epoch-99-avg-1` 权重、或叠加 Silero VAD 门控。B 的风险是授权与联网激活，且用户机器上首次要填 AccessKey，离线场景直接不可用。C 的风险是产品叙事断裂。
- **置信度**：78%
- **分区归属**：置顶区
- **归入原因**：涉及商用授权（法务/成本）与产品形态，不是我能替用户决定的。

### Q5. 执行策略：立即执行 + 撤销 / 一律二次确认（含"助手把自己耳朵关掉"的风险）

- **问题描述**：**语音助手用的就是它要调的这支麦克风**，这里有几个真实的坑：
  1. `mic.mute`（`0x2022`）、`mic.sigMute`（`0x2058`）、`hp.OnOff`（`0x2059`）一旦被语音写字面意义上关闭，**助手下一次就听不见你了**，而恢复只能靠鼠标；
  2. `enc.OnOff`（`0x2024`）/ `noisegate.Enable`（`0x2074`）虽不切断输入，但会改变送进 KWS/ASR 的音频（降噪削弱音节、噪声门切气口），可能让唤醒词与识别率下降；
  3. TTS 播报会被同一支麦克风收回去（半双工或回声消除必须二选一）；
  4. 误识别 + 立即执行 = 用户以为设备坏了。

- **建议方案（A）：分级执行**
  - **一级（立即执行，可撤销）**：音色/曲线/降噪强度/压缩阈值/限幅开关/场景切换 —— 都是可听、可回滚的。保留最近 **5 步** delta 快照，支持「撤销」「刚才那个不要了」「回到上一个」。
  - **二级（二次确认）**：会改变输入链路或不可逆的 —— `mic.mute`、`mic.sigMute`、`hp.OnOff`、`drc3.Enable` 这类全局开关。助手先回问「要静音麦克风吗？静音后我就听不到你了，确认吗」，说「确认/好」才写。
  - **排除（默认不进语音词表）**：出厂复位（`0x100A`）、预设的保存/加载/删除（`0x1004`–`0x1006`）、进入 DFU（`0x1008`）、设备地址与通讯参数 —— 误操作的后果不可逆或会中断链路。
  - 播报期间暂停采集（半双工）；或后续接 AEC。

- **备选方案**：
  1. **B：全部立即执行**——最简单、最像"智能"，但一次误识别就可能让用户当场失聪且语音救不回来。
  2. **C：一律二次确认**——最安全，但每条指令 +1.5 s 往返，用户会懒得用。

- **风险预警**：A 的代价是二级指令多一轮，且"撤销"要做快照与栈（约 1 天）。若把静音类排除在外，用户"用嘴静音"这个高频需求就没有了（可用 UI 一键静音替代）。B 的风险是**演示事故**（我强烈不建议）。C 的风险是体验差、评测量化不出价值。

- **置信度**：82%
- **分区归属**：置顶区
- **归入原因**：产品可见行为 + 有"把自己弄哑"的真实故障模式，属于必须共同拍板的设计。

### Q6. LLM 在链路中的位置：每轮都过 / 规则优先 LLM 兜底 / LLM 只做归一化

- **问题描述**：实测给了三个硬数字——确定性规则解析 **< 1 ms**；1.7B 单轮温缓存 **1.2–2.2 s**；1.7B 对自由描述**会编动作**（调研 §2.4）。所以"LLM 放在哪"直接决定延迟与准确率的上限。

- **建议方案（A）：规则优先 + LLM 兜底（推荐）**
  - 第一层：正则/同义词表（起步 ≥ 60 条中文说法，覆盖"把声音调大/小一点""降噪开到最大""太闷了""齿音太重"等高频表达）→ 命中即走确定性路径，**不经模型**；
  - 第二层：未命中时调 1.7B，输出仍受 JSON Schema 约束（Q2 的 L1 契约），再交给规则表算 dB；
  - 第三层：模型输出无法映射 / 置信度低 → 走**澄清或拒绝**话术（D10），绝不猜。
  - 理由：把延迟与确定性留给高频指令，把模型能力留给长尾表达；同时验收可以分层归因（规则层错 / 模型层错 / 映射层错）。

- **备选方案**：
  1. **B：每轮都过 LLM**——最"AI 原生"。代价：每条指令 +1.2–2.2 s，且自由描述错误率最高，验收时"错在哪一层"极难归因。
  2. **C：LLM 只做归一化改写**（把「听着有点毛」改写成「高频轻微刺耳」），动作仍由规则层出。收益是规则表更容易扩；代价是多一次模型调用 + 一次文本往返，延迟叠加，且改写质量的评测更麻烦。

- **风险预警**：A 的规则覆盖率决定体验下限——起步 60 条覆盖不到的说法会掉到模型层，而模型层对自由描述并不稳（实测会编动作）。**这条必须靠 M6 的评测集量化**：规则层命中率、模型层兜底成功率、总成功率三个数一起看。B 的风险是延迟预算（D8）直接不达标。C 的风险是两段失败会乘起来。

- **置信度**：87%
- **分区归属**：置顶区
- **归入原因**：这是"小模型在这套系统里的角色"，与 Q2 一起决定 schema、数据与验收，属于重大技术路线分歧。

### D7. 意图集边界（"只支持调参"的落地定义）
- **方案**：**可调** = 46 项标量中的 `rw` 项（`domain/params.ts`，含降噪强度 `0..3`、压缩/限幅阈值与时间常数、噪声门、三分频、RGB）+ EQ 7 段（type/freq/gain/q）+ 5 个场景 + 4 个固定音色 + 自定义曲线。**不可调** = 只读项（`gain.Mic`、`gain.Hp`、`micLevel`）、出厂复位、预设存取删、进入 DFU、设备地址/通讯参数、固件升级、信息区。

- **风险**：用户说"把麦克风音量调大"（对应只读的 `gain.Mic`）时助手只能回"这个要旋钮调"——需要话术写清楚（D10）。
- **置信度**：93%｜**分区归属**：自决区

### D8. 延迟预算与预热
- **方案**：唤醒词检出 → 应答音 **≤ 300 ms**；用户停口 → 命令落地 **≤ 2.5 s**（其中 ASR ≤ 300 ms、规则层 ≤ 5 ms、LLM 层 ≤ 1.8 s、落地 ≤ 200 ms）；**服务常驻**（`llama-server` 不重启）、**启动时打一发 warm-up 请求**预热前缀缓存；LLM 输出**硬上限 96 token**（典型 50–70），`say` 字段 ≤ 30 token（实测 reply 才是超时元凶；上限过小则截断，而截断是唯一能破坏约束解码合法性的途径）。
- **理由**：本机实测数字（pp/tg、cache_n、1.55 s/35 token）反推的预算；不预热的话首轮 4.6 s 直接爆预算。
- **风险**：4B 或开思考模式会直接击穿预算——所以 Q3 选 A 且必须双开关关思考。
- **置信度**：92%｜**分区归属**：自决区

### D9. 多轮与上下文
- **方案**：支持相对指令（"再亮一点""稍微回来一点"）——把**当前参数快照**放进提示词上下文；唤醒后 **6 s 无人说话**则退出聆听并播报"我先退下了"；单次会话最多 **3 轮**；「取消/不用了/算了」立即退出且不写任何参数；撤销栈深度 5。
- **理由**：常见语音助手的默认交互（唤醒—指令—播报—退出），并覆盖"说完就后悔"这一最高频的纠错需求。
- **风险**：上下文注入会让提示词变长（每次多 ~120 token 的当前值），但实测 prefill 318 tok/s，可接受。
- **置信度**：90%｜**分区归属**：自决区

### D10. 拒绝与澄清话术
- **方案**：模型输出两类终态——`status:"unsupported"`（与调参无关："放首歌""今天天气"）与 `status:"clarify"`（相关但没说清："调一下"）。`unsupported` 回复固定话术 + 举两个能做的例子；`clarify` **最多问一次**，仍不清则退出。**任何情况下都不猜参数**。
- **理由**：需求明确要求"和功能无关的需要排除"；"澄清只问一次"避免像坏掉的客服。
- **风险**：拒绝率过高会显得笨——用 M6 的"过度拒绝率"指标盯住（目标 < 5%）。
- **置信度**：91%｜**分区归属**：自决区

### D11. 评测方案与门禁线
- **方案**：三层——
  - **L1 文本级（主门禁）**：150 条中文指令（含 30 条范围外、20 条模糊）+ 期望动作集，直接喂意图层，指标 = 动作集 F1 / 数值容差命中（|Δgain| ≤ 1 dB、档位精确）/ 拒绝准确率 / 过度拒绝率；
  - **L2 音频级**：30 条用 SAPI 合成 wav（已验证转写 100% 正确）走"唤醒→VAD→ASR→意图→落地"全链路，指标 = 端到端成功率 + 各段延迟；
  - **L3 真人抽检**：10 条现场口述（不进门禁，只做体验记录）。
  - **门禁线**：L1 动作集 F1 ≥ 0.85、拒绝准确率 ≥ 0.95、过度拒绝率 ≤ 0.05；L2 端到端 ≥ 0.70；无崩溃、无越界写。
- **理由**：没有真人录音素材，合成语料是唯一能自动化且可复现的路；文本级与音频级分开，出问题能定位到"识别错"还是"理解错"。
- **风险**：合成语音比真人干净，L2 会系统性高估。所以 L1 是主门禁，L2 只作链路验证。
- **置信度**：90%｜**分区归属**：自决区
