# 场景「复位」不随防爆音阈值点亮（2026-11-25）

- 反馈：「这个拖动条，有些就算改了值也没能触发总的恢复按钮点亮，似乎只改一个是不能触发的」（用户，2026-11-25）
- 结论：**复现属实**——只拉「防爆音」阈值时场景「复位」不亮，另外两条（噪声门 / 压缩器）会亮
- 归属：上位机，本轮修复（场景预设里仍然不写这个阈值，`R-19` 不动）

## 1. 复现

真机 / mock 都一致（`artifacts/tmp-diag/restore-buttons/report.json`，选中「播客」后逐条改值）：

| 拖动条 | 行内「恢复」 | 场景「复位」 |
|---|---|---|
| 噪声门阈值 `noisegate.threshold_db` | 亮 | **亮** |
| 压缩器阈值 `comp.Threshold` | 亮 | **亮** |
| 防爆音阈值 `limit.Threshold` | 亮 | **不亮** |

「只改一个不触发」正好说的是第三行：先把前两行改回基准，再单独拉防爆音，场景复位仍然是灰的。

## 2. 根因

场景「复位」的可用态由 `sceneIsDirty()` 决定：

```ts
hasSceneOverride(overrides, sceneId) || !store.isAtSceneBaseline(SCENE_PARAM_IDS)
```

`SCENE_PARAM_IDS` 是各场景 `scenePatch()` 的并集，**不含 `limit.Threshold`**——
这是有意的（设计文档 R-19：`domain/scenes.ts` 的防爆音从写阈值改成写 `limit.Enable`，
"点一次场景就会悄悄改掉设备限幅阈值"）。于是：

- 用户改 `limit.Threshold` → `onParamChanged` 里 `SCENE_PARAM_IDS.includes(id)` 为假 → 直接 return，
  既不记覆盖值，也不进"偏离基准"的比较；
- 场景「复位」自然保持灰色。

行内「恢复」没受影响，因为它比的是**基准**（`isParamAtSceneTarget`），与场景作用域无关。

## 3. 修法（不破坏 R-19）

给"调乱了没有"单独一套参数集合，比自动保存的范围多一项：

```ts
// domain/scenes.ts
export const LIMITER_THRESHOLD_ID = 'limit.Threshold';
export const SCENE_DIRTY_PARAM_IDS = [...SCENE_PARAM_IDS, LIMITER_THRESHOLD_ID];
```

- `sceneIsDirty()` 与 `resetScene()` 的早退判断改用 `SCENE_DIRTY_PARAM_IDS`：防爆音阈值一变，场景「复位」就亮。
- `resetScene()` 复位时把防爆音阈值退回**应用场景时**的值（`store.sceneTargetParam()` 取基准），
  再应用出厂预设——顺序很重要：先撤这个值、再 `applySceneValues()`，基准快照才带上它，
  复位完按钮才会转灰。**不是**退参数表默认 `-2 dB`：用户可能应用场景前就调过它。
- `onParamChanged()` 里把 `editedSinceBaseline = true` 挪到全局开关早退**之前**：用户动过任何一项
  （含全局开关）都不再让设备回读挪基准，否则回读一次就把"应用场景时"的值覆盖掉。
- **自动保存的范围不变**：`limit.Threshold` 仍然不进 `scenePatch` / 覆盖表，切场景不会换掉它（R-19），
  也不会被写进任何场景预设。也就是说它的语义是"全局参数 + 场景复位会撤销本次改动"。

## 5. 独立审查补漏（2026-11-26）

这一轮的全量测试由一个独立审查者只读代码复查，发现同类的几处漏项，已在交付前补掉：

| 问题 | 现象 | 处置 |
|---|---|---|
| `comp.Enable` 同类漏项 | 压缩器**开关**与阈值同一行，但场景只写阈值；只拨开关时行内「恢复」亮、场景「复位」不亮 | `SCENE_BASELINE_ONLY_IDS` 从「只有 `limit.Threshold`」扩成 `limit.Threshold + comp.Enable`，复位时一起退回"应用场景时"的基准；场景预设仍不写它们 |
| 换回出厂音色后误亮 | 点场景（出厂 vocal）→ 点明亮 → 再点人声增强：值全回到基准，但场景「复位」还是亮的，点了也没变化 | `applyTone()` 里若选的是本场景出厂音色就走 `forgetSceneTone()`（与 `restoreTone()` 对称），摘掉 tone 覆盖 |
| 语言切换丢基准 | 只改防爆音阈值后切「中/EN」，工作台重建时把"当前值"重新记成基准，复位与行内恢复一起转灰、撤销目标丢失 | 视图构造里改成 `if (!store.sceneBaseline()) store.setSceneBaseline(...)`：基准属于会话（存在 store 里），重建不再覆盖 |
| 双击「复位」被当成取消 | 第一次点击同步插入确认框，双击的第二下落在遮罩上 → `close(false)`，看起来"没反应" | `confirm-dialog.ts` 记录打开时刻，250 ms 内的遮罩点击忽略 |
| 文案与行为不一致 | 文案说"恢复到出厂预设"，但防爆音阈值/压缩器开关实际回"应用场景时的值" | `console.scene.resetHint` / `resetBody` 补一句说明（中英同步） |

顺带修掉审查里指出的既有 P1（不属于本次两处修复，但在同一段代码里）：**语言切换重建工作台时会把
`localStorage` 的 `micstudio.customEq` 无条件套到 7 段**，若当前是固定音色且 `sync==='ready'`，会经
`diffBands` 把设备 EQ 改写成自定义曲线（`customEq` 全 0 时等于把「温暖」拉平）。现在用模块级
`bootCustomEqApplied` 只在进程内第一次构造时套一次。该缺陷在 HEAD `7754e54` 同样存在。

新增用例：

- `console-view.test.ts`「lights the scene reset when only the compressor switch changed」；
- 「drops the dirty flag when the factory tone of the scene is chosen again」；
- 「keeps the scene baseline when the workbench is rebuilt (language switch)」——同一个 store 上销毁再建，
  复位仍可用、点完能把阈值退回基准；
- `confirm-dialog.test.ts` 的遮罩用例改成"刚打开时忽略、250 ms 后可取消"。

仍然接受、不修的两条（记录在案）：

- 高级参数里把某段类型从 PEAK 改成 HPF/LPF 时增益被清 0，改回 PEAK 不会恢复（`EqBand` 没有地方存旧值）；
- 设备里已经存在的 `band1.gain`/`band2.gain` 非 0 值不会被新版本清零（`applyBands` 按设计不回写），
  若固件确认高低通不吃 gain，则只是寄存器脏值。

## 6. 遗留

1. 真机这一轮跑探针时又撞上固件"写多了被压住"（切场景 4 次后链路掉线、`WriteFile timeout`、product string 变空），
   需物理拔插；这条属于既有固件问题（见 `修复记录-界面问题单20261122.md` §5），与本修复无关。
2. 如果产品希望防爆音阈值**跟着场景保存**（切场景换回该场景的值），那会推翻 R-19，需要先改设计文档再动
   `scenes.ts` 的 `ScenePreset`；本轮没有做。
