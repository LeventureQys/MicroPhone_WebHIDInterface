# V0.0.6 固件刷写失败记录（2026-11-21）

> **后续（2026-11-21 晚）**：设备已用 J-Link 烧整片 V0.0.6 hex 恢复，现为 `0.0.6.0` 且参数链路正常。
> 诊断与复测方案见 `固件升级诊断与复测方案-20261121.md`：包与 hex App 区逐字节一致（包没问题）、
> V0.0.6 的 Bootloader 与 V0.0.5 字节完全相同（擦写缺陷未修）、主机侧另修掉一个"回读失败却报出旧版本"的缺陷。
> 本文的现场记录保持不变，作历史留档。

- 目标：用界面内的「固件升级」（DFU）把 M001 从 `0.0.5.0` 升到 `0.0.6`
- 包：`Document/Update/hardware/v0.0.6/dfu_M001 MCU V0.0.6_2026-11-16_Rev0.bin`
  （`174414 B`，sha256 `6D9871DDB0088ACD05560489DD6A407E35181DAB147DC800CF5A3AF3A19171F4`）
- 结果：**没有刷成功**。设备现在停在 Bootloader（App 未启动），刷新过程的失败点**每次不同**，
  与 `Document/Update/Alpha/v1.1.0/真机DFU首刷记录.md` §8 记录的「QSPI XIP 擦写与取指互锁」一致
- 取证：`artifacts/dfu-v006/`、`artifacts/dfu-v006-recover/`、`artifacts/real7/*.log`、`artifacts/jlink/`

## 1. 三次尝试

| # | 入口 | 结果 | 关键证据 |
|---|---|---|---|
| 1 | 界面 DFU（App 模式 → 自动进 Bootloader） | 预检 `JYM001 / M001 / 0.0.6 / 168392 B / 658 块 / 0x74DC17F3` 全对；**658/658 块写完（19.0 s，95%）**；设备重启后版本回读仍是 `0.0.5` → 报「升级已完成但版本未变，设备已回到正常模式」（`device 0.0.5 does not match image 0.0.6`），随后设备以**仅 HID（无 USB 音频 MI_00）**的形态重新枚举 | `artifacts/dfu-v006/summary.json`、`06-failed.png`、`startup.log` |
| 2 | 界面 DFU（从 Bootloader 续刷，救砖通道） | 写到约 **66/658 块**（18%）时句柄失效：`Failed to write the report`，会话重启后长时间探测，最终「设备通道异常，升级中止」 | `artifacts/dfu-v006-recover/summary.json` |
| 3 | `tools/dfu/m001-dfu.py flash`（ctypes 直连，Bootloader） | 第 1 次：**1089/2631 块 @ `0x19000`** 无应答；复测：**2275/2631 块 @ `0x2B880`** 无应答（`--timeout-ms 8000 --retries 8`） | `artifacts/real7/dfu-python-v006*.log` |

三次的共同点：**写进去的块数不同、挂死偏移不同**，挂死后 USB OUT 仍能发（HID 不报错），但固件主循环不再应答——
这正是首刷记录里那次「三次在不同偏移挂死，只能断电」的同一现象。

另外两点值得固件方注意：

1. 第 1 次界面 DFU 把 658 块全写完、回执也都是 `0x03`，但设备重启后**没有跑新镜像**（版本仍是 0.0.5），
   且 USB 描述符从「音频 + HID 复合」变成「仅 HID」——说明那次写入把 App 区写成了**不完整的镜像**，
   Bootloader 的 CRC/状态字判定没过，设备留在 Bootloader（对外仍能枚举）。
2. 之后从 Bootloader 续刷，两次都在**不同偏移**挂死，与写入节奏无关（64 B 块 + 3 ms 间隔 / 256 B 块 + 2 ms 报告间隔都试过）。

## 2. 根因判断（沿用首刷记录 §8）

J-Link 器件定义显示本机是 **QSPI Flash（`BaseAddr = 0x10000000`）**，CPU 从同一片 QSPI 取指（XIP）。
Bootloader 擦/写 Flash 期间，SPI 控制器忙，而 CPU 仍在同一条总线上取指 → 一旦发生取指就可能互锁：
USB 中断还活着、主循环再也不返回。表现就是「挂死点随机、与主机节奏无关、只有断电恢复」。

对固件的诉求（与首刷记录一致）：

1. 把 `hal_flash_write` / 擦除的等待逻辑放 RAM 跑（`__RAM_CODE`），擦写期间关中断，或改用后台编程接口；
2. 擦写失败时回明确的失败状态，而不是静默挂死；
3. 校验整片 CRC 后再置「可跳转」状态字——第 1 次那种「全写完却启动不了」对产线和售后都不可接受。

## 3. 现在的设备状态与恢复路径

- 现状：**Bootloader**。`m001-dfu.py state` → `mode: Bootloader`，DevInfo 回 `JYM001`/`M001`；Modbus 无应答；
  某次挂死后连 DevInfo 都不回（`send-fail`），**拔插 USB 才能恢复**。
- 恢复只有两条路：

### 3.1 SWD / J-Link（推荐，也是厂商官方路径）

按 `Document/Update/Alpha/v1.1.0/真机DFU首刷记录.md` §7：

1. 装 J-Link：仓库内 `third_party/设备相关/Release/JLink_Windows_V696.exe`（静默：`/S /D=D:\Tools\JLink696`）；
2. 装器件定义：`node scripts/probes/install-jlink-devices.py`（把 JinAudio AP5532/AP5540/AP5980 的 FLM +
   JLinkScript 并进 `JLinkDevices.xml` 与 `Devices/JinAudio/`）；
3. 接线：**GND / RESET / TCK / TMS**（RESET 可不接），板子 USB 供电、仿真器 USB 接电脑；
4. 烧整片 hex（0x0000 Bootloader、0x8000 App、0x38000 状态字 `A5 FF 00 00`，烧完直接进 App）：

   ```powershell
   node scripts/flash-jlink.mjs --hex "Document/Update/hardware/v0.0.6/JYM001_Firmware_M001 MCU V0.0.6_2026-11-16_Rev0.hex"
   ```

   `scripts/flash-jlink.mjs` 会自动找 JLink.exe、检测仿真器、依次尝试 AP5540 → AP5532 → AP5980，
   执行 `erase → loadfile → verify → r → g`，日志落 `artifacts/jlink/`。
   本机**当前没有插 J-Link**（`ShowEmuList` 为空、USB 里没有 VID_1366），所以这一步还没执行。

   若 V0.0.6 的 hex 也进不去 App，用同一脚本刷 `Document/Protocol/JYM001_Firmware_M001 MCU V0.0.5_2026-11-07_Rev0.hex` 回退。

### 3.2 继续用 DFU（不推荐）

设备已经证明这条路径会随机挂死；每次挂死都要人工拔插。若一定要试，唯一比之前更保守的节奏是
`--chunk 32 --gap-ms 8 --post-ms 12 --timeout-ms 10000`（尚未验证）。
