# M001 固件刷写逻辑说明（v1.1，2026-11-28 更新）

本文是上位机固件升级（DFU）的**行为规格**：界面上什么时候允许点、点下去按什么顺序发什么、什么算成功、
失败后该让用户做什么。代码实现以本文为准，冲突时改代码不改本文；要改本文必须同时改
`tests/unit/dfu/baseline.test.ts`（参数守卫）与复测记录。

配套：`固件升级诊断与复测方案-20261121.md`（根因与实测数据）、`Document/Protocol/DFU固件升级通讯协议说明_20261026.md`（协议）。

---

## 1. 责任划分

| 层 | 文件 | 只做这些 |
|---|---|---|
| 镜像层 | `device/dfu/image.ts` | 解析升级包、Gamma 解密、长度/校验和/型号/上界校验。**拒绝即一帧不发** |
| 帧层 | `device/dfu/frame.ts` | SigmaBus 组帧 / 流式拆帧 / CRC |
| 会话层 | `device/dfu/session.ts` | 状态机、逐块写入、超时与重试、发帧上限 |
| 编排层 | `device/dfu/controller.ts` | 串起"选包 → 确认 → 挂起参数链路 → 主进程守卫 → 会话 → 收尾 → 版本比对" |
| 连接层 | `device/link.ts` | 重枚举、换句柄、全量回读、失败收场（保留裸通道供续刷） |
| 界面层 | `ui/views/firmware-view.ts` | 只画状态与按钮，不做协议判断 |

主进程只负责窗口守卫（升级中不允许关窗）。**渲染进程是唯一业务层**。升级前等后台重连结束，丢弃尚未发送的参数请求，排空在途参数请求并停止音频采集后才进入 DFU。

## 2. 状态机

```
idle ──selectFile──> preflight ──ok──> ready ──start──> entering
                                                          │
                                       ┌── EnterDfu 有 ACK ──> 等重枚举 8 s ──> 稳定 1 s ─┐
                                       └── 无 ACK（设备已在 Bootloader）─────────────────┤
                                                                                        v
                                                                    probing ──信息帧回 0x03──> writing
                                                                       │                        │
                                                              3 次无回执│               收到 0x05 │
                                                                       v                        v
                                                                    failed                  settling
                                                                                                 │
                                                         重连 + 回读 + 版本比对 ────────────────┤
                                                                                                 v
                                                                                        done / failed
```

`abort` 只在 `entering / probing / writing` 三个相位有效；`0x05` 之后设备已经在写状态字并复位，主机打断只会更糟。

## 3. 两条路径（自动判定，不需要用户选）

| 设备当前状态 | 判定依据 | 路径 | 差异 |
|---|---|---|---|
| App 模式（能答 Modbus） | 链路 `sync === 'ready'` 且 `device !== null` | **正常升级** | 先发参数协议 `0x10` 写 `0x1008=1`，收 ACK 后**等重枚举**再发信息帧 |
| 停在 Bootloader（只说 SigmaBus） | 有句柄但 Modbus 无人应答（`sync === 'error'`） | **续刷（救砖）** | `0x1008` 那一帧注定无人应答，**不判失败**，直接进信息帧探测 |

关键约定：`EnterDfu` 没有 ACK **不等于**失败（DFU 材料 §6 ⑬）。是否真的进了升级模式，由下一阶段的信息帧应答确认。

界面上必须把这个判定显示给用户（`fw.device.app` / `fw.device.bootloader` / `fw.device.none`），
否则用户在"设备已连不上"的时候不敢点，或者在正常模式误以为在救砖。

## 4. 逐阶段动作与判据

| 阶段 | 主机动作 | 通过判据 | 失败判据 |
|---|---|---|---|
| `preflight` | 只读包，不发帧 | 结构 / 信息帧唯一 / 块尺寸 / 型号可打印 / 长度 ≤ `0x30000` / 长度一致 / 校验和一致 | 任一项不过 → `fw.error.preflight`，**零出帧** |
| `entering` | 发 1 次 `0x1008=1`（超时再发 1 次），等 ACK | ACK `0x0000` → 等重枚举 | 通道错误；重枚举 8 s 内没出现 → `reenumerate` |
| `probing` | 发信息帧（90 B），等状态帧 | 状态 `0x03` → 继续 | 3 次无回执 → `probeFailed`；`0x01` → `statusInfo`；`0x04` → `statusFail` |
| `writing` | 逐块发 265 B 帧（256 B 数据 + 9 B 头），发一块等一块 | 每块状态 `0x03` | 末块 `0x05` → 进入 `settling`；块状态超时或发帧失败/阻塞 → 保留失败块并立即终止 |
| `settling` | 停发一切帧，重连并全量回读 | 回读成功 → `verifying` | 20 s 内没走完 → `settle` |
| `verifying` | 比对设备回读的 `x.y.z` 与包版本 | 一致 → `done` | 不一致 → `verify` |

## 5. 固定参数（改动必须同步 `tests/unit/dfu/baseline.test.ts` 与本文档）

| 参数 | 值 | 为什么是这个值 |
|---|---|---|
| 报告载荷 `PAYLOAD_BYTES` | 63 B | 需求 C1：每帧发满 63 B |
| 块数据 / 块帧 | 256 B / 265 B | 656×256 + 200 = 168392 B（V0.0.6 共 658 块） |
| 每块报告数 | 5 | `ceil(265/63)`；设备 OUT 环形缓冲只有 4 槽，所以必须留间隔 |
| `dfuReportGapMs` | 2 ms | 不留间隔时第 5 个报告会被丢，表现为块回执超时（第五轮已定） |
| `dfuEnterSettleMs` | 1000 ms | 设备刚重枚举就写会在第 11/44 块丢回执（第五轮已定） |
| `dfuBlockTimeoutMs` | 1500 ms | 正常块 ACK 是 25–30 ms，1.5 s 已是 50 倍余量 |
| `dfuProbeTimeoutMs` | 1500 ms | 同上 |
| `dfuProbeAttempts` | 3 | 信息帧是协议里唯一的"复位指针"原语，允许重发 |
| `dfuRoundRestarts` | 3 | 只对设备明确回送的可恢复错误整轮重来，避免失联时反复写失败标志 |
| `dfuSendTimeoutMs` | 5000 ms | 设备挂死后 `WriteFile` 不返回；没有它会话会永久卡死（2026-11-21 R3 实测 73 s） |
| `dfuReenumTimeoutMs` / `PollMs` | 8000 / 200 ms | 协议 §1：复位后 1–3 s 出现，8 s 覆盖最坏情况 |
| `dfuSettleTimeoutMs` | 20000 ms | 覆盖"重枚举 8 s + 两次全量回读" |
| App 区上限 `APP_MAX_BYTES` | `0x30000` | 写超会覆盖 `0x38000` 状态字与 `0x39000` 信息区，只能 SWD 救 |

**不要去调这些值"求稳"**：2026-11-21 五次实测，两次失败挂死点相差 287 块（365 / 652），
与节奏无关；失败根因在 Bootloader 擦写。改参数只会让复测数据失去可比性。

## 6. 失败分类与处置（界面必须给出下一步）

| `DfuError.kind` | 含义 | 界面动作 |
|---|---|---|
| `preflight` | 包不合法，零出帧 | 重新选包；设备无感 |
| `enterTimeout` | 进 DFU 没 ACK 且信息帧 3 次无回执 | 拔插后重试 |
| `reenumerate` | 设备复位后 8 s 没重新出现 | 拔插后重试 |
| `probeFailed` | 进了升级模式但信息帧没人答 | 拔插后重试 |
| `statusInfo` / `statusFail` / `statusCode` | 设备侧拒绝（型号/校验/未知码） | 换正确的包；设备仍在升级模式，可直接重试 |
| `timeout` | 完成发送后等待块回执超时 | 保留失败块、拔插后再试 |
| `restartExhausted` | 整轮重来 3 次仍失败 | 设备仍在升级模式，重试或联系支持 |
| `settle` | 等重启超时 | 重连后确认版本 |
| **`noReadback`** | **收尾后一句都没读到**（设备可能仍在升级模式，或新固件没起来） | **拔插 → 重试（自动走续刷）** |
| `verify` | 读到了设备，但版本没变 | 报告实测版本；**不要**说"设备已回到正常模式"除非回读确实成功 |
| `channel` | 通道异常 / 发帧 5 s 不返回 | 拔插后重试 |
| `unplugged` | 还没发第一帧就判定设备不可用 | 插回后在设备页重新连接 |

`noReadback` 与 `verify` 必须分开：前者连"设备在哪个模式"都不知道，后者是设备活着但镜像没生效。
混在一起会把用户引向"再刷一次"（2026-11-21 就是这么误判的）。

## 7. 重试与中止规则

1. **单块状态超时** → 保留失败块号并结束本次会话。V0.0.7 实机在块回执超时后直接重新探测，后续 HID 发送也超时。此时不得重发块或重新发信息帧，等待用户重新插拔设备。
2. **发帧失败或 5 s 不返回** → 立即按 `channel` 终止，取消尚未提交的分片。状态回执计时从该帧的最后一片发送完成后开始。收到明确可重试的错误（如 `0x02` 或 SigmaBus 拒绝应答）可整轮重试，保持 3 轮上限。
3. **信息帧探测**最多 3 次；3 次无回执即 `probeFailed`。
4. `abort` 只在 `0x05` 之前生效；之后按钮隐藏（设备在收尾，主机插不上手）。
5. **同一个 `done` 会话不允许再次点击「开始升级」**：要重刷必须重新选包（`selectFile` 会把相位重置为
   `idle` 并要求重新勾确认）。否则用户以为"再点一次更保险"，实际是在多刷一遍 Flash。

## 8. 成功判据

**软件侧（决定界面显示什么）**：

1. 收到 `0x05` → `settling`；
2. 重枚举成功 + `readAll()` **真的读到设备**（`resumeAfterDfu()` 返回 true，否则 `noReadback`）；
3. 回读版本 `x.y.z` 与包版本一致 → `done`，显示"设备新版本 X.Y.Z"。

**验收侧（决定这一轮测试算不算过）**——比软件侧更严格，需独立工具核验：

1. 重枚举成**复合设备**（`MI_00` 音频 + `MI_03` HID）；只有 HID 说明还在 Bootloader；
2. `python scripts/probes/real8-health.py <tag>` 能读到型号与版本；
3. 预设区 **118 项**全读通；
4. 界面顶栏「已连接 / 已同步」。

## 9. 禁止事项

- 不要用界面 `done` 状态重复刷写；要复测请重新选包（见 §7.5）。
- 设备停在 Bootloader 时，**同一次上电内不要连续续刷超过 1 次**：每次都会重写 `END_FAIL` 状态字并重新擦写。
- 不要把 `tools/dfu/m001-dfu.py`（裸 HID）当作交付验证路径——它绕过界面层，只用于对照与诊断。
- 不要在没有退路的情况下刷写：退路 = SWD 可用，或确认能从 Bootloader 续刷。
- 不要改 §5 的参数而不改基线测试与本文档。

## 11. 变更流程

改动本文件涉及的任何一条（相位、判据、参数、文案里的处置动作）都必须：

1. 改代码 + 改本文档；
2. 改 `tests/unit/dfu/baseline.test.ts` 的期望值与注释（它会在参数漂移时失败）；
3. 在 `固件升级诊断与复测方案-20261121.md` §7 追加一轮实测（至少 3 次，记录成功/失败/挂死块）；
4. 真机复测通过后才能改版本号。
