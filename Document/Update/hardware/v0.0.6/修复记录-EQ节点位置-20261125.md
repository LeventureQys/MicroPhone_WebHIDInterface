# HPF / LPF 节点位置修复（2026-11-25）

- 反馈：「EQ 的 HPF 和 LPF 点应该在横轴上，显示有误」（用户，2026-11-25）
- 结论：**上位机显示 + 模型 + 写入三处的规则统一了**；高低通没有增益，节点钉在 0 dB 轴上
- 影响版本：1.1.4（本轮之后）

## 1. 根因

曲线节点原来一律按 `band.gain` 画：

```ts
// eq/render.ts（改前）
const y = safeY(band.gain);
```

而 7 段音色预设是"每段一个增益"，把第 1、2 格也填了值：

```ts
warm:   [4, 3, 2, 0, -1, -2, -3]
vocal:  [-3, -2, -1, 1, 3, 2, 0]
bright: [-2, -1, 0, 1, 2, 4, 5]
```

第 1 段是 HPF（50 Hz）、第 2 段是 LPF（20 kHz），`eq/curve.ts` 的响应计算走 BLT Butterworth 分支，
**根本不读 gain**。于是出现两个后果：

1. 节点按 +4 / +3 dB 画，飘在 0 dB 横轴上方（用户看到的那张图，选「温暖」时最明显）；
2. 这个无效增益还会经 `store.setBands` → `diffBands` 写进设备的 `band1.gain` / `band2.gain`
   （参数表里它们是 `[−32, 12]` 的 rw 项，默认 0 dB）。

## 2. 处置（一条规则，五处落地）

`eq/types.ts` 新增判别函数：

```ts
export function bandHasGain(type: EqFilterType): boolean {
  return type !== 3 && type !== 4; // 3 = LPF, 4 = HPF
}
```

| 位置 | 改动 |
|---|---|
| `eq/render.ts` | 节点 y 坐标：`bandHasGain(band.type) ? band.gain : 0` |
| `eq/interactions.ts` | 命中判定用同一规则；上下拖 / ↑↓ 键不再改增益（左右拖频点、滚轮调 Q 照旧） |
| `eq/model.ts` | 构造与 `setBand` 里，类型是 HPF/LPF 时 gain 归 0（含"切成高通"那一下） |
| `domain/state.ts` | `normalizeBand` 同规则：设备回填、场景/音色应用、复位全部走这里，脏值进不来 |
| `domain/quick-controls.ts` | 4 个固定音色前两格改 0（`warm` 4/3 → 0/0、`vocal` −3/−2 → 0/0、`bright` −2/−1 → 0/0），3–7 段不变 |
| `domain/eq-reset.ts` | `defaultEqBands()` 丢弃前两格的默认增益 |
| `ui/views/eq-band-table.ts` | 高级参数里 HPF/LPF 行的增益输入框禁用，`title` 提示 `eq.gain.na` |
| `i18n/{zh,en}.ts` | 新增 `eq.gain.na`：`高通 / 低通没有增益，节点固定在 0 dB 横轴上` |

**听感不变**：高通 / 低通本来就只吃截止频率与 Q。真正的行为差异只有一条——`band1.gain` / `band2.gain`
现在写 0（与参数表 G 列默认一致），以前会被音色预设写成 +4 / +3。

新增 / 改写的用例：

- `eq-render.test.ts`「pins HPF / LPF handles to the 0 dB axis」：前两段喂 +4/+3，`arc` 的 y 必须等于
  `gainToY(0)`，第 3 段照旧按自己的增益画；
- `eq-model.test.ts`「pins the gain of HPF / LPF bands to 0」：HPF 给 +6 → 0；切 PEAK → 6 生效；
  再切回 LPF → 归 0；
- `state.test.ts`「drops the gain of HPF / LPF bands instead of writing it」：前两段塞 ±6 既不进状态也不出
  `bandWrites`，第 3 段照常写；
- 受影响的旧用例改到 PEAK 段（`eq-model` 的钳位/事件、`state` 的量化/快照、`link` 的设备上报），
  `console-view` 的人声增强默认曲线期望值改成 `[0, 0, -1, 1, 3, 2, 0]`。

- 把 1 号节点往上拖 96 px：增益仍是 0、节点不动（只会按光标位置改截止频率）。

## 4. 独立审查补漏（2026-11-26）

全量测试时由独立审查者只读复查，指出"只设 `disabled` 不等于置灰"：`.eq-input` 自己定义了
`background/color/border`，会盖掉浏览器对 disabled 控件的默认外观，仓库里也没有 `.eq-input:disabled`。
结果 HPF/LPF 的增益框看起来和可编辑的一模一样，点进去敲字没反应，解释还只挂在被禁用元素自身的
`title` 上（Chromium 对 disabled 表单控件不派发鼠标事件，悬停提示不可靠）。

已补（`styles/components.css`）：

```css
.eq-input:disabled,
.eq-select:disabled {
  color: var(--text-dim);
  border-color: var(--line-1);
  background: rgba(255, 255, 255, 0.02);
  cursor: not-allowed;
}
```

并新增 `tests/unit/eq-band-table.test.ts`：
① HPF/LPF 行增益框 `disabled` + 值 0 + 有提示，PEAK 行可编辑；
② 把 PEAK 段切成 LPF 后增益被清 0 且禁用，切回 PEAK 恢复可编辑；
③ 整片旁通时全部禁用，取消旁通后 PEAK 恢复、HPF 仍禁用。

审查里另外两条**接受不修**、记录在案：

- 类型从 PEAK 切到 HPF/LPF 时增益被清 0，改回 PEAK 不会恢复（`EqBand` 没有地方存旧值）；
  若产品在意，可以加一次确认或加 `gainBefore` 影子字段，本轮不做。
- 设备里已经存在的 `band1.gain`/`band2.gain` 非 0 值不会被新版本清零（`applyBands` 按设计不回写）；
  固件确认高低通不吃 gain 的话，只是寄存器脏值。

## 5. 遗留 / 口径

1. 老配置（localStorage 里的场景曲线覆盖）如果存过前两段的非 0 增益，应用时会被 `normalizeBand` 归 0，
   不需要单独迁移。
2. 高级参数里把某段类型从 PEAK 改成 HPF/LPF 时，该段增益会被就地清 0；改回 PEAK 后需要重新设增益。
3. 如果产品以后想给高通 / 低通配"输出补偿"一类的增益，得先在固件/DSP 侧定义语义，再放开 `bandHasGain`
   与音频链路，不能只改界面。
